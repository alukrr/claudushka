и не «если попросят» — это часть любой задачи, напоминать не будут.

   список команд, инварианты, известные грабли, workflow, зависимости, модели.

   (новые/удалённые команды, изменение поведения).

4. **Синтаксис проверен**: `python3 -c "import ast; ast.parse(open('bot.py').read())"`
   для каждого изменённого .py.

### Рисование: два пути входа
Вся генерация+отправка картинки инкапсулирована в `_draw_and_send(update, context, chat_id, is_group, draw_prompt, en_prompt=None, author=None)`. Если `en_prompt` не передан — `draw_prompt` переводится на английский через Haiku. Два способа запустить рисование:
1. **Команда «нарисуй …»** (`DRAW_TRIGGERS`) — явный запрос пользователя. Вызывает `_draw_and_send` с русским `draw_prompt`, переводом и автором.
2. **Маркер `[[DRAW: english prompt]]`** — Клодушка сама решает нарисовать внутри текстового ответа. В system-prompt ей сказано: НЕ писать «нарисовала» просто так (иначе картинка не появится), а добавлять маркер в конец ответа. `DRAW_MARKER_RE` парсит ответ в main conversation: маркер вырезается из текста (пользователь его не видит), остаток отправляется как реплика, затем `_draw_and_send` реально рисует. Если весь ответ был маркером — текст не шлётся, в группу пишет `_draw_and_send`. ЭТО ФИКС бага «Клодушка верит что нарисовала, но никуда не отправляет». Маркер обрабатывается только в текстовой ветке main conversation, не в фото/документах.
   Регекс лениво ловит 1 ИЛИ 2 скобки с обеих сторон, а если закрытия нет вообще —
   берёт до конца строки (`\[{1,2}DRAW:\s*(.+?)(?:\]{1,2}|$)`) — модель иногда сама
   сбивается на одинарную скобку без закрытия (`[DRAW: ...` до конца ответа), и старый
   строгий `\[\[DRAW:...\]\]` такое не ловил — маркер вываливался в чат текстом (v0.11.0).
   Известное ограничение: нелэйзи-стоп на первой `]` внутри промпта, если она там
   случайно есть — маловероятно для промптов на английском, не чинить, пока не встретится.
- fastapi 0.115.0 + uvicorn 0.30.0 — WhatsApp webhook
- httpx 0.27.0
- SQLite (через stdlib sqlite3, обёртка в db.py)
- Docker Compose (без Dockerfile)

## Групповой чат (мультиперсональный контекст)
В группах бот — участник беседы нескольких людей, а не личный диалог 1:1.
- Контекст для модели строит `build_group_messages()` (bot.py) из `db.get_group_transcript(chat_id, GROUP_TRANSCRIPT_LIMIT)` (лимит = 50): реплики людей → user-блоки с подписью «Имя: текст» (подряд идущие склеиваются), ответы Клодушки → assistant-блоки. Гарантируется чередование ролей и user первым. Текущее сообщение-триггер уже лежит в `group_messages` (сохранено в начале `handle_message`) и идёт последним user-turn — повторно НЕ добавляется (иначе вернётся баг «ты уже говорила»).
- Групповой контекст идёт в `messages`, НЕ в system-prompt. Старый дамп `get_group_history` в system удалён — не возвращай его обратно, иначе модель снова начнёт сливать собеседников в одного.
- Контекст реплая привязывается inline к текущей реплике (`[в ответ на сообщение Имя: «…»]`), а не в system.
- Ответы Клодушки во всех ветках (текст / фото / документ / рисование) сохраняются в `group_messages` с `is_bot=True` — чтобы она видела собственные реплики.
- Инструкции про групповой режим — в `get_system_prompt(..., is_group=True)`.
- Личка (ветка `else` в `handle_message`) и WhatsApp работают по-старому (личный тред) — их не трогать.
- ГЕЙТИНГ ДОСТУПА разный для группы и лички (намеренно):
  - Группа — на уровне ЧАТА: если `WHITELIST_ENABLED` и чат не `approved` → молчим; иначе отвечаем ВСЕМ участникам. Никакой персональной капчи/допуска/дневного лимита по `user_id` в группе — единственное исключение: opt-in лимит частоты через `/ratelimit`, см. ниже. Бан (`role='banned'`) — глобальный, проверяется в начале `handle_message` и действует везде.
  - Личка — персональный гейтинг: `needs_captcha` (admin-approval), `is_allowed_in_chat`, `check_daily_limit` (лимит для street).
  - Веб-поиск (`can_search`) остаётся привилегией роли и в группе тоже (стоит денег). Если захочется «в разрешённом чате ищут все» — снимать гейт отдельно.
  - `handle_captcha()` (интерактивная капча) — мёртвый код, нигде не вызывается; активен только admin-approval путь.
- Схема: `group_messages.is_bot INTEGER NOT NULL DEFAULT 0`, миграция идемпотентная в `init_db()`. Сигнатура `save_group_message(chat_id, user_id, sender_name, content, is_bot=False)`.
- `db.get_group_history()` (строки «Имя: текст») оставлена специально — её используют `daily_chat_review` и `cmd_review`. Не удалять и не путать с `get_group_transcript()`.

### Лимит частоты сообщений per-user в группе (`/ratelimit`, v0.10.0)
Просили ограничить отдельных «спамящих» участников группы, не трогая остальных.
- Таблица `chat_rate_limits(chat_id, user_id, interval_seconds, last_ts)`, PK `(chat_id, user_id)`.
  **Отсутствие строки = без ограничений** (это дефолт для всех) — не «0 = безлимит» и не
  отдельный флаг, просто нет записи.
- `db.check_group_rate_limit(chat_id, user_id)` — True можно отвечать (и сразу обновляет
  `last_ts`), False — лимит не истёк. Вызывается в `handle_message` СРАЗУ после проверки
  `is_bot_mentioned` и `WHITELIST_ENABLED`/`is_chat_allowed`, ДО любых API-вызовов — это
  самая ранняя точка, где уже известны `chat_id`/`user_id` и бот точно был адресован.
  При `False` — обычный `return`, **без сообщения пользователю** (так просили: превышение
  лимита должно быть незаметным, а не «подожди ещё 3 минуты»).
- `db.set_group_rate_limit` / `remove_group_rate_limit` (`user_id=None` — снять со всех
  разом) / `get_group_rate_limits` — CRUD для команды.
- **Новый уровень админства**: `is_chat_admin(context, chat_id, user_id)` (bot.py) — ПОМИМО
  глобальных `ADMIN_IDS` разрешает управлять лимитом реальным админам/creator'ам ЭТОГО
  Telegram-чата через `context.bot.get_chat_member().status`. Раньше в кодовой базе не было
  понятия «админ группы», только `is_admin()` = глобальный админ бота — не путать эти два
  уровня при добавлении новых групповых команд.
- `/ratelimit` без аргументов — список лимитов чата. Ответом на сообщение участника без
  доп. аргументов — его текущий лимит (`db.get_group_rate_limit`, без побочных эффектов,
  не путать с `check_group_rate_limit`). Ответом + `/ratelimit <N>` (минуты) или
  `/ratelimit off` — установить/снять лимит этому участнику. Без ответа — то же самое
  по ID первым аргументом (`/ratelimit <user_id> <N|off>`), как в `/ban`/`/promote`.
  `/ratelimit off` без ответа и без ID — сброс всех лимитов чата разом.
- Команда видна в `USER_HELP` (не в `ADMIN_HELP`, который показывается только глобальным
  админам через `is_admin()`) — иначе админы группы, не являющиеся админами бота, не
  увидели бы её в `/help` вообще.
- **`check_group_rate_limit` вызывается и в `cmd_search`/`cmd_imagine`**, не только в
  `handle_message`: это отдельные `CommandHandler`, а не текстовая ветка, и лимит туда
  не долетал бы без явной проверки — а это самые дорогие по деньгам команды (Tavily +
  Claude / Gemini). Один и тот же `last_ts` на пользователя в чате — лимит общий на
  «любое обращение к Клодушке», не отдельный счётчик на каждую команду.
- Найдено при первом деплое (server-side тест, ещё до тега v0.10.0), исправлено сразу:
  1. `cmd_search`/`cmd_imagine` изначально лимит не ловили — см. выше, починено.
  2. Реплай на сообщение + `/ratelimit` без аргументов раньше показывал usage вместо
     лимита этого конкретного участника — тоже починено (см. выше).
- **Известные, осознанно НЕ починенные, ограничения:**
  - Анонимные админы группы (`GroupAnonymousBot`, `user_id=1087968824`) в `is_chat_admin`
    получат `get_chat_member(...).status == "left"` и отказ «может только админ этого
    чата» — fail-closed, не дыра, но обычному анонимному админу команда покажется
    сломанной. Если у Алексея в чатах заведутся анонимные админы — тогда разбираться,
    как их отличать от реально вышедших пользователей.
  - `cmd_ratelimit` не проверяет `WHITELIST_ENABLED`/`db.is_chat_allowed(chat_id)` —
    в неодобренном чате команда всё равно отработает и запишет лимит в БД, хотя бот там
    и так всем молчит. Безвредно (лимит просто никогда не применится), но непоследовательно
    по сравнению с `handle_message`. Не чинить, пока не попросят явно.

## Голос, кружочки и видео (v0.11.0)

Три новых типа Telegram-сообщений: `voice` (голосовое), `video_note` (кружочек, mp4 со
звуком), `video` (обычное видео). Ноль новых pip-зависимостей: расшифровка речи идёт через
уже подключённый Gemini (`GEMINI_API_KEY`, тот же REST-паттерн, что и рисование), кадры из
видео — через системный `ffmpeg` (добавлен в `docker-compose.yml`, не Python-пакет).

### Расшифровка речи (voice, video_note) — Gemini
`_transcribe_audio_gemini(audio_bytes, mime_type)` — POST на
`generativelanguage.googleapis.com/.../{GEMINI_AUDIO_MODEL_NAME}:generateContent` с
`inline_data`, в отличие от `_try_gemini_image` вызывается через `asyncio.to_thread` (не
блокирует event loop). `GEMINI_AUDIO_MODEL_NAME = "gemini-3.6-flash"` — **проверено живым
запросом 31.08.2026** (curl с сервера, тот же `GEMINI_API_KEY`): `gemini-2.5-flash` отдаёт
404 «no longer available to new users», Google сам предлагает `gemini-3.6-flash`; и текст,
и `audio/wav` inline_data вернули 200. **Модель галлюцинирует на чистой тишине** —
вместо пустой строки выдаёт правдоподобный, но полностью выдуманный текст (проверено:
1 секунда цифровой тишины → связная фраза на английском). Транскрипту доверять нельзя
на 100%, особенно для коротких/тихих войсов — это поведение самой модели Google, не баг
парсинга на нашей стороне, чинить нечем. Транскрипт режется до
`GEMINI_AUDIO_TRANSCRIPT_MAX_CHARS` (1500) — уходит в `group_messages`, которая
копируется в каждый следующий промпт чата (см. общий инвариант про лимит по размеру в
разделе памяти).

### Кадры из видео (video_note, video) — ffmpeg + Haiku
`_extract_video_frames(video_bytes, count, duration)` — синхронная, звать только через
`asyncio.to_thread`: пишет байты во временный файл, `ffmpeg -ss <t> -frames:v 1` на трёх
равномерных таймстемпах (10/50/90% длительности — надёжнее fps-фильтра при непостоянном
FPS), возвращает JPEG-байты. `_describe_media_haiku(images_b64, hint)` — Haiku-описание,
**всегда `DEFAULT_MODEL_ID`, не `get_chat_model(chat_id)`**: фоновое распознавание не
должно платить по цене Opus/Fable, даже если у чата выставлена дорогая модель для
основного диалога (тот же принцип, что "вспомогательные вызовы — всегда Haiku"). Вызов
через `aux_create`, не `call_claude` — нет реплая пользователю, не нужен keep-alive
индикатор. `max_tokens=MEDIA_DESCRIPTION_MAX_TOKENS` (250) и промпт "1-2 предложения" —
описание тоже копируется в каждый следующий промпт чата, длинное раздувает контекст
(тот же класс проблемы, что инцидент 2026-07-26).

Guardrails по длительности (не тратим ffmpeg/API на марафонские файлы): `MAX_VOICE_SECONDS`
(300), `MAX_VIDEO_NOTE_SECONDS` (60 — кружочки и так капаются клиентом Telegram, это
подстраховка от нестандартных клиентов), `MAX_VIDEO_SECONDS` (120). Длиннее — распознавание
пропускается, сохраняется голый плейсхолдер.

### Два разных пути в `handle_message`
- **Фото** (существующая ветка, bot.py `has_photo`) не тронута — отдельная Q&A-ветка,
  отвечает моделью ЧАТА (`get_chat_model`), с разбивкой на части >4096 символов.
- **Voice/video_note/video — НЕ отдельная ветка.** Расшифровка/описание подставляется
  прямо в `user_text` (сразу после `user_text = update.message.text or ...`) и идёт по
  ОБЫЧНОМУ диалоговому пайплайну — «как будто написал текстом» (идея Алексея). У `video`
  (в отличие от voice/video_note) нет собственной Q&A-ветки даже для обычных файлов —
  осознанное упрощение; если понадобится вёрстка один-в-один с фото (модель чата, разбивка
  на части) — отдельная небольшая доработка. **Известное ограничение:** если `video`
  отправлен с caption, описание кадров не подмешивается — работает только "видео без
  подписи" (`if update.message.video and not user_text`). Voice с caption игнорирует
  caption целиком (транскрипт замещает, а не дополняет) — то же упрощение.
- **GIF (`update.message.animation`, тег `[GIF: описание]`) добавлен той же правкой, что
  и разбор — переиспользует `_recognize_video` как есть**: Telegram-класс `Animation`
  несёт те же `.file_id`/`.duration`, что `Video`, ffmpeg не различает GIF и обычное видео
  на уровне кадров. Путь идентичен `video` (не отдельная Q&A-ветка, то же ограничение
  «не подмешивает описание, если есть caption»).

### Пассивное распознавание в группе (даже без упоминания бота)
В блоке `if is_group and update.message:` (самое начало `handle_message`, работает ДО
проверки `is_bot_mentioned` — то же место, что пишет плейсхолдеры `[Фото]`/`[Файл: ...]`
и триггерит `extract_all_participants_memory`) добавлены ветки для voice/video_note/video.
Гейтинг **сознательно отличается** от остального этого блока (текст/фото-плейсхолдер и
`extract_all_participants_memory` там работают безусловно, в любом чате, даже неодобренном
— см. WHITELIST_ENABLED в разделе выше): новое распознавание голоса/видео стоит реальных
денег на КАЖДОЕ медиа-сообщение, поэтому гейтится через
`WHITELIST_ENABLED and not db.is_chat_allowed(chat_id)` — в неодобренном чате (когда
whitelist включён) сохраняется только голый плейсхолдер, без API-вызова. При дефолтном
`WHITELIST_ENABLED = False` гейт не действует, распознаётся всё.

**Фото/видео/GIF распознаются в пассивном блоке ВСЕГДА, независимо от упоминания бота**
(до v0.11.2 было наоборот: пропускалось при упоминании, чтобы не платить дважды — из-за
этого адресованное фото получало настоящий ответ от has_photo-ветки, но сырая строка в
`group_messages` оставалась голым `[Фото]` без описания; в СЛЕДУЮЩЕЙ реплике модель видела
рядом свой же содержательный ответ и пустой тег и решала, что сама всё выдумала — хотя
реально видела фото. Инцидент 2026-08-31, "до меня прилетело просто «Фото»"). Для **видео и
GIF** результат кэшируется в `video_description_cache` и переиспользуется в user_text-пути
ниже (нет отдельной более богатой Q&A-ветки, которую жалко терять — двойной вызов был бы
чистой тратой). Для **фото** переиспользовать нечего: у has_photo своя, более богатая
ветка (модель чата, а не Haiku), поэтому адресованное фото сейчас честно платит за ДВА
Haiku/чат-модель вызова — недорого, и это цена корректности тега. Для **voice/video_note**
та же кэш-логика была с самого начала (`voice_transcript_cache`/`video_note_description_cache`).

`get_system_prompt(is_group=True)` объясняет модели теги `[Фото: ...]`/`[Видео: ...]`/
`[Кружок] Сказано:.../Видно:...`/`[Голосовое] ...` — что это распознанное ботом содержимое
медиа, а не текст, который написал участник (раньше подобных тегов — `[Фото]`, `[Файл:
...]` — модели вообще не объясняли, они просто плыли как текст).

## Модели per-chat (реестр MODELS, v0.9.0)

**`MODELS` в bot.py — единственный источник правды.** Команды, цены, гейтинг по ролям,
окна контекста, `/models` — всё оттуда. Строки моделей по месту больше не писать.

| ключ | id | label | $/MTok in/out | окно | кому |
|---|---|---|---|---|---|
| `haiku` | `claude-haiku-4-5-20251001` | Haiku 4.5 | 1 / 5 | 200k | всем (дефолт) |
| `sonnet` | `claude-sonnet-5` | Sonnet 5 | 3 / 15 | 1M | всем |
| `opus` | `claude-opus-5` | Opus 5 | 5 / 25 | 1M | только админ |
| `fable` | `claude-fable-5` | Fable 5 | 10 / 50 | 1M | только админ |

Пул `api.apitoken.sale` принимает эти строки — проверено живым запросом 29.07.2026
(плюс старые `claude-sonnet-4-6`, `claude-opus-4-8`, `claude-opus-4-7`).
Цены — официальный прайс Anthropic, прокси даёт скидку сверху. **Sonnet 5: до 31.08.2026
действует вводная цена $2/$10**, в реестре стоят постоянные $3/$15 — до конца акции
`/cost` слегка завышает, после она станет верной сама.

- `model_meta(model_id)` → метаданные по API-строке; неизвестная модель → дефолт,
  без исключения (в `chat_models` могли остаться строки прошлых поколений).
  В `/cost` такая модель помечается «нет в реестре» — иначе цифра выглядела бы точной.
- `db.get_chat_model_db / set_chat_model_db`, обёртка `get_chat_model(chat_id)` в bot.py.
- **Окна различаются: Haiku 200k, пятое поколение 1M. Лимиты памяти/истории калиброваны
  под МИНИМАЛЬНОЕ (200k) — не поднимать их, ссылаясь на 1M.** Дефолт остаётся Haiku;
  поднять потолок значит вернуть июльский инцидент всем, кто сидит на `/haiku`.
  См. «Потолок на чтении».
- Вспомогательные вызовы (капча, should_search, перевод, greet, групповая память) —
  всегда Haiku. `extract_memory` в личке — Sonnet из реестра (осознанно: аналитическая
  задача). `daily_chat_review` и `cmd_review` — модель чата.
- whatsapp.py собственного реестра не имеет и остаётся на `claude-sonnet-4-6`
  (пул принимает). Захочется синхронизировать — выносить `MODELS` в общий модуль.

### Команды и гейтинг
Все четыре — через общий `_set_chat_model(update, context, key)`, где `key` — ключ
реестра, а не API-строка.
- `admin_only` из реестра: Opus и Fable только админам, отказ с объяснением и ценой,
  а не молчанием (раньше вся функция молча делала `return` для не-админа).
- **Без аргумента → текущий чат, доступно всем.** С аргументом `/opus -1001109809707` →
  указанный чат, **ТОЛЬКО АДМИНУ**: иначе любой участник менял бы модель в чужом чате,
  зная только ID. Раньше аргумент читался лишь из лички и вся команда была admin-only.
- Аргумент валидируется: не парсится в int → подсказка по формату; чата нет в
  `allowed_chats` → предупреждение, но запись разрешена (чат мог ещё не попасть в таблицу).
- В ответе всегда имя + ID чата, чтобы админ не переключил не тот.
- **Перед записью — пробный запрос** (`_probe_model`, `max_tokens=1`, «hi») через
  `call_claude`. Не прошёл → «модель сейчас недоступна», в БД НЕ пишем. 529 при этом
  ретраится и не выглядит как «модели не существует» (для 404 отдельная фраза).
- `/models [chat_id]` — список с ценами и окном, `▸` = текущая модель чата. Обычному
  пользователю видны только доступные ему, админу — все с пометкой «только админ».

### Учёт токенов
`_track_response()` вызывается ВНУТРИ обёрток `call_claude()` и `sync_create()`, а не по
месту. До v0.9.0 половина путей (should_search, перевод, капча, extract_*, `/search`)
не считалась вовсе и `/cost` занижал расход. Новый вызов API попадает в учёт
автоматически — не возвращать ручные `_track_tokens` по месту, это ведёт к двойному счёту.

**`/cost` занижал расход ещё и по другой причине (нашли и починили в v0.11.7, при
разборе `dedup_memory.py`): пул этого ключа автоматически кеширует любой достаточно
большой вход, не только системные промпты.** У больших групповых system-prompt'ов
(20-30k+ символов — обычное дело, см. `PROMPT` в логах) это регулярный случай.
`usage.input_tokens` при таком кешировании почти пустой (единицы токенов), а реальный
вес — в `usage.cache_creation_input_tokens`/`cache_read_input_tokens`, которые
`_track_tokens`/`/cost` раньше вообще не видели. Порядок занижения подтверждён живьём
в `dedup_memory.py`: 40690 символов входа -> `input_tokens=2`,
`cache_creation_input_tokens=16186` — не проценты, порядки. Теперь `_track_tokens`
принимает `cache_write`/`cache_read` отдельными полями, `/cost` считает их с теми же
множителями, что и `dedup_memory.py` (`CACHE_WRITE_MULTIPLIER`=1.25x, `CACHE_READ_MULTIPLIER`=0.1x,
стандартные цены Anthropic за 5-минутный ephemeral-кэш — запись дороже обычного input,
чтение дешевле). `token_usage` в памяти, сбрасывается при рестарте — старые (заниженные)
цифры за это не пересчитать, только новые с этого деплоя.

### Миграция chat_models
В `init_db()`, идемпотентная, вместе с остальными:
`UPDATE chat_models SET model='claude-sonnet-5' WHERE model LIKE 'claude-sonnet-4-%'`
и то же для `claude-opus-4-%` → `claude-opus-5`. Haiku не трогается.

## Обработка ошибок API (v0.8.2)

**Инвариант: пользователь НИКОГДА не видит сырой текст исключения.** Паттерн
`except Exception as e: reply_text(f"Ошибка: {e}")` выпилен целиком — не возвращать.
Всё идёт через `api_errors.reply_api_error(send, exc, *, context_label, default=None,
clear_hint=...)`: полный traceback (`exc_info=True`) в `logger.error`, пользователю —
короткая фраза в характере Клодушки.

### Классы ошибок (проверено на anthropic 0.43.0)
- **529 overloaded / любой 5xx → `anthropic.InternalServerError`.** Отдельного класса под
  529 в SDK нет, ловится весь 5xx одним типом. Ретраебельно, тон «не наша вина».
- **429 → `RateLimitError`** — ретраебельно, «притормози».
- **401/403 → `AuthenticationError` / `PermissionDeniedError`** — пользователю нейтрально,
  в лог явное «ПРОВЕРЬ ANTHROPIC_API_KEY».
- **400 с `prompt is too long` → `BadRequestError`**, ловится `api_errors.is_prompt_too_long()`.
  Проверяет И текст исключения, И `exc.body`: SDK обычно кладёт тело в сообщение
  (`Error code: 400 - {...}`), но в ветке «ответ закрыт до чтения» строит голое
  `Error code: 400` с `body=None` — тогда распознать невозможно и сработает общая ветка.
- **402 «insufficient balance» → голый `APIStatusError`** (своего класса в SDK нет),
  ловится `api_errors.is_insufficient_balance()` по `status_code`. Это баланс ключа
  на пуле `api.apitoken.sale`, а не на Anthropic напрямую. НЕ ретраебельно: чинится
  только пополнением. Пользователю — шутка про «скиньтесь на токены», в лог —
  «ПОПОЛНИ БАЛАНС», админу — сообщение в личку. До v0.9.2 падало в общую ветку,
  и пользователь видел «сломалось на моей стороне» (41 раз 2026-08-03).
  - Админа зовёт `api_errors.set_admin_notifier(fn)` — хук, а не прямой вызов бота:
    модуль общий с whatsapp.py и про `Application`/`ADMIN_IDS` знать не должен.
    Telegram регистрирует `notify_admins` в `post_init`; whatsapp.py хук не ставит
    (некому слать) и просто молчит.
  - **Кулдаун `BALANCE_ALERT_COOLDOWN` (30 мин) не убирать**: 2026-08-03 прилетел
    41 такой ответ за два часа — без кулдауна это 41 сообщение в личку подряд.
  - Уведомление висит на `reply_api_error`, то есть только на пользовательских путях.
    Фоновые вызовы (память, `should_search`) 402 лишь логируют — это осознанно.
- **`APIConnectionError`** (и наследник `APITimeoutError`) — ретраебельно.
- Всё остальное — общая фраза + полный лог.

### ГЛАВНОЕ ПРАВИЛО: никаких блокирующих вызовов API из event loop
`client.messages.create` синхронный. Прямой вызов из async-хендлера вешает ВСЕГО бота
на всё время запроса плюс всю лестницу SDK-ретраев. Три легальных способа:

| Что | Как звать | Ретраи |
|---|---|---|
| Пользовательский запрос (диалог, фото, файл, /search, /review) | `await call_claude(context, chat_id, label=..., **kwargs)` | свои, с «печатает…» |
| Служебный `messages.create` из async-кода (перевод, капча, приветствие, дневной обзор, фильтр фактов) | `await aux_create(**kwargs)` | SDK-шные |
| Синхронная функция целиком (`should_search`, `web_search`, `check_captcha_answer`) | `await call_claude_aux(fn, *args)` | SDK-шные внутри |
| `messages.create` внутри синхронной функции | `sync_create(**kwargs)` | SDK-шные |

`call_claude` и `sync_create` — единственные две точки входа в API; обе считают токены.

Фоновые (`extract_memory`, `extract_all_participants_memory`) — `asyncio.create_task(asyncio.to_thread(...))`.
Прямой `client.messages.create(` остался ровно в одном месте — внутри `sync_create`.
Добавляешь новый вызов — выбери строку из таблицы, не пиши напрямую.

### Ретраи: два уровня, не путать
1. **SDK-ретраи** (`ANTHROPIC_SDK_RETRIES = 3` в конструкторе `anthropic.Anthropic`) —
   для служебных вызовов. SDK ретраит 408/409/429/5xx, бэкофф 0.5→8с, блокирующий —
   поэтому и они обязаны идти через поток (см. таблицу выше).
2. **Свои ретраи** (`api_errors.call_with_retry`, паузы `RETRY_DELAYS = (2, 6, 15)`) —
   для пользовательских вызовов. Работают на `client_noretry`
   (`client.with_options(max_retries=0)`), иначе задержки перемножились бы.

**Индикатор держится ВСЮ паузу, а не дёргается после неё.** `send_chat_action` живёт в
Telegram ~5 секунд, а пауза бывает 15 — поэтому `_sleep_with_keepalive` поднимает фоновую
задачу `_keep_chat_action`, тикающую каждые 4 секунды, и гасит её по окончании сна.
`_keep_chat_action(bot, chat_id, action, stop_event)` общий и для «печатает…», и для
«отправляет фото…» в рисовании — не разводить обратно на две функции.

### 400 prompt is too long: резать ТОТ компонент, который весит
`db.save_message()` вызывается ПОСЛЕ успешного запроса, поэтому упавший запрос не пишет
историю — следующее сообщение собирает тот же промпт и падает снова, чат заклинивает
навсегда (инцидент 2026-07-26).

Лечение: сравнить `len(system)` и `history_chars`, и резать доминирующий компонент.
- **История больше** → `api_errors.halve_history()`, подсказка про `/clear`.
- **System больше** → пересборка `get_system_prompt(..., include_memory=False)`,
  подсказка про `/forget`. В инциденте 26.07 вес был именно здесь: 236k токенов
  групповой памяти против ~7k истории — обрезка истории не спасла бы, а совет «/clear»
  был бы бесполезен, потому что `/clear` чистит `conversations` и НЕ трогает память.
- **Обрезка ничего не изменила** (`halve_history` вернул `None`, пересборка не ужалась) →
  повтора НЕТ, сразу сообщение. Иначе это лишний вызов с гарантированным тем же 400.

`halve_history` возвращает `None`, когда резать нечего, и откатывается к ПОСЛЕДНЕМУ
user-сообщению (не к последнему вообще) — иначе на хвосте из одних assistant вернулся бы
одинокий assistant и API отдал бы другой 400, про чередование ролей.
Повтор ровно ОДИН. В лог — `PROMPT TOO LONG` с размерами по каждому компоненту ДО и ПОСЛЕ.

### Разбор ответа: никогда не `content[0].text`
`content` — список блоков, и первым может идти НЕ текст. У пятого поколения адаптивное
мышление включено по умолчанию, поэтому `content[0]` — thinking-блок (при
`display="omitted"` вообще с пустым текстом). `response.content[0].text` на таком ответе
падает с `AttributeError`, а при отказе модели (`stop_reason="refusal"`, пустой `content`)
— с `IndexError`. Оба — не ошибки API, поэтому пользователь видел «Что-то сломалось
на моей стороне» при полностью успешном запросе. Так сломался групповой чат сразу после
миграции на `claude-opus-5` (v0.9.0).

Всегда `api_errors.response_text(response)` — перебирает блоки и склеивает текстовые.
Пустая строка — ЛЕГАЛЬНЫЙ результат (отказ / только thinking / упёрлись в max_tokens),
и её обязан проверить каждый вызывающий: пустой `reply_text("")` роняет отправку.
Диагностика для лога — `api_errors.response_debug(response)` (stop_reason, типы блоков,
output_tokens, модель).

### Уровень логов httpx: не поднимать обратно на INFO
`logging.getLogger("httpx").setLevel(logging.WARNING)` рядом с `basicConfig` в bot.py.
На INFO httpx печатает полный URL каждого запроса, а в URL Telegram API лежит **токен
бота** — 51 069 строк из 57 066 (89% лога) содержали его открытым. Это и утечка токена
всем, у кого есть доступ к `docker logs`, и шум, в котором тонут настоящие ошибки.

### Логирование размера промпта
Перед каждым основным вызовом:
`PROMPT uid=... chat=... model=... system=... history_chars=... msgs=... imgs=...`

`api_errors.history_stats()` считает **только текстовые блоки**, картинки — отдельным
счётчиком `imgs`. base64 изображения в `history_chars` включать нельзя: одна картинка —
сотни килобайт, метрика распухает и перестаёт соотноситься с токенами. Именно этих цифр
не хватало при разборе июльского инцидента — не удалять и не «упрощать» обратно
до `str(content)`.

## Версионность
Текущая версия: v0.10.0. Теги ставит Алексей вручную: `git tag -a vX.Y.Z`. Не создавай теги самостоятельно.
Версия доступна через `/version` в боте. Команды `cmd_update` и `cmd_version` используют хелпер `_git()` — не переписывай их без необходимости.

SemVer:
- **patch** (0.8.x) — багфиксы, поведение для пользователя не меняется
- **minor** (0.x.0) — новые команды/фичи, обратно совместимые
- **major** — несовместимые изменения схемы БД или поведения

`git describe --tags --always --dirty` питает `/version`. Строка «(vX.Y.Z)» в сообщении
коммита БЕЗ реального тега — ошибка: так уже случилось с v0.7.0, тег пришлось ставить
ретроспективно. Предлагая версию, всегда давай готовую команду `git tag -a ... -m "..."`.

## Трёхуровневая память (секретность личка/группа)

### Схема
Факты хранятся в таблице `memory` (`context` + `chat_id` + `tier` + `expires_at`):
- `context='private', chat_id=NULL` — сказано боту в личке.
- `context='group', chat_id=<id>` — узнано в конкретной группе.
- `tier='long'`, `expires_at=NULL` — долгосрочные факты (не протухают).
- `tier='medium'`, `expires_at=<unix+7d>` — среднесрочные, TTL 7 дней. Автоматически исключаются из выборок после истечения.

### Три уровня (группа)
1. **Краткосрочная** — `group_messages` (последние 50 реплик) → `build_group_messages()` → `messages` в API. Не персонализирована, весь чат.
2. **Среднесрочная** (`tier='medium'`) — события и временные состояния этой недели (попала под дождь, поругалась с Валерой, купила клубнику). TTL 7 дней.
3. **Долгосрочная** (`tier='long'`) — устойчивые факты о людях: кто они, где живут, чем занимаются, интересы, возраст, взгляды. Без TTL.

### Извлечение
- **Личка** — `extract_memory()` по личному треду (каденс: `len(messages) % (MEMORY_EXTRACT_EVERY*2) == 0`). Модель Sonnet (hardcoded — осознанно, это аналитическая задача).
- **Группа** — `extract_all_participants_memory(chat_id)`: один вызов Haiku на весь 50-реплик транскрипт, извлекает **оба уровня** сразу для **ВСЕХ видимых участников**. Атрибуция: по `sender_name` → `user_id` через `db.get_user_id_by_name_in_chat()`. Каденс: `db.should_extract_chat_memory(chat_id, MEMORY_EXTRACT_EVERY_CHAT)` (каждые 15 сообщений в чате). Вызывается **до** проверки `is_bot_mentioned` — работает даже когда бота не упоминают. Запускается в фоне через `asyncio.to_thread`, чтобы не блокировать ответ.

### Асимметрия чтения (намеренная, не баг)
- В личке `get_system_prompt(is_group=False)` зовёт `db.get_memory_for_private(user_id)` — личные факты ПЛЮС все групповые факты про этого человека из всех чатов (с дедупом). Группа течёт вверх.
- В группе `get_system_prompt(is_group=True)` зовёт `db.get_all_chat_memory(chat_id)` — факты **всех участников** ЭТОГО чата (оба tier, без просроченных). Личное в группу НЕ течёт, другие группы — тоже (изоляция по `chat_id`).

### Команды
- `/memory` — показывает факты текущего пользователя (в группе — только его факты этого чата; в личке — объединённое). Потолок показа — `MEMORY_LONG_DISPLAY`/`MEMORY_MEDIUM_DISPLAY` (30+10=40), больше, чем уходит в system-prompt (12+8=20, см. ниже) — человек читает сам, разово, не модель на каждый промпт.
- `/memory_full` — то же самое, но БЕЗ потолка вообще (вся история). **Намеренно не добавлена в `USER_HELP`/`ADMIN_HELP`** — единственное сознательное исключение из правила "новая команда → обе константы" в разделе Definition of Done, чтобы не звали почём зря (может уйти как несколько десятков сообщений на давнего активного участника — v0.11.5-инцидент, XDNet, 740 фактов). Если решите документировать открыто — тогда добавляйте.
- `/forget` — чистит ВСЮ память юзера (и личное, и групповое во всех чатах).

### Потолок на чтении
`get_all_chat_memory` отдаёт не более `MEMORY_LONG_PER_USER` (12) и `MEMORY_MEDIUM_PER_USER` (8) фактов на человека, самые свежие (`ROW_NUMBER() OVER (PARTITION BY user_id, tier ORDER BY created_at DESC)`). Без потолка старые чаты раздували system-prompt до сотен тысяч токенов и Клодушка переставала отвечать. Не снимать потолок — если фактов не хватает, поднимать константы осознанно.

**`get_memory_for_private` тем же потолком обзавелась только в v0.11.3** — до этого читала
ВСЕ факты пользователя (личные + из всех групп, куда он течёт вверх) без ограничения.
Найдено 2026-08-31: у одного активного участника многих групп накопилось 1860 фактов,
~80k символов — `/memory` падала на `BadRequest: Text is too long` (лимит Telegram 4096
символов одним сообщением), а сама эта же функция кормит `get_system_prompt(is_group=False)`,
то есть личный диалог с этим пользователем на КАЖДОЕ сообщение тащил все 80k символов в
system-prompt. Тот же класс проблемы, что инцидент 2026-07-26, просто на масштабе одного
человека вместо всего чата — тот же общий инвариант ниже это и предписывал, просто эта
функция была написана раньше, чем он оформился как правило, и её пропустили. Теперь
использует тот же `ROW_NUMBER() OVER (PARTITION BY tier ...)` паттерн, что `get_all_chat_memory`,
партиция только по tier (не по chat_id — здесь это агрегат по одному пользователю сразу
по всем чатам). Старые факты в таблице `memory` при этом НЕ удаляются, просто перестают
читаться — как и в `get_all_chat_memory`. Разовая чистка/дедуп самой таблицы остаётся
открытой задачей (см. ниже).

**`db.get_memory` (не `get_memory_for_private`!) без потолка была ещё в одном месте —
починена следом, v0.11.5.** Это ОТДЕЛЬНАЯ функция: `/memory`, вызванная В ГРУППЕ,
читает не `get_memory_for_private`, а `db.get_memory(user_id, "group", chat_id)` —
факты только этого человека в ТЕКУЩЕМ чате. Потолок v0.11.3 её не касался. Найдено
2026-08-31 (после v0.11.4, live-тест в группе XDNet): у одного давнего активного
участника — 740 фактов в ОДНОМ чате, 34k символов; `/memory` не падала (спасибо
`reply_expandable`), но рассыпа́лась на десяток сообщений, местами разрывая строку
посреди слова между соседними сообщениями. Заодно нашлась причина такого раздутия —
извлечение памяти плодит почти-дубли вместо дедупа (`"Поделился фото"` /
`"Поделился фото в чате"` / `"Отправил фото в чат"` — 13/8/8 раз одно и то же).
Сама дедуп-гигиена таблицы `memory` остаётся открытой задачей (см. ниже) — здесь
почему потолок на ЧТЕНИИ обязателен, даже когда источник переполнен дублями.
`get_memory` теперь использует тот же `ROW_NUMBER() OVER (PARTITION BY tier ...)`,
партиция по tier внутри пары (user_id, context[, chat_id]).

**v0.11.6: оба потолка стали параметром, не жёстко зашитой константой.**
`get_memory(..., long_limit=None, medium_limit=None)` и `get_memory_for_private(...,
long_limit=None, medium_limit=None)` — `None` (дефолт) означает
`MEMORY_LONG_PER_USER`/`MEMORY_MEDIUM_PER_USER` (то, что кормит system-prompt через
`get_all_chat_memory`/`get_system_prompt`, эти вызовы не трогали). `cmd_memory`
передаёт `MEMORY_LONG_DISPLAY`/`MEMORY_MEDIUM_DISPLAY` (30/10) — человеку на глаз
можно показать больше, чем стоит скармливать в промпт на каждое сообщение.
`cmd_memory_full` передаёт заведомо огромные числа (`10**9`) — фактически без
потолка, вся история. Общий helper `_send_memory(update, long_limit, medium_limit,
header, label)` в bot.py, обе команды — тонкие обёртки над ним.

`/memory` (bot.py `cmd_memory`) заодно чинится сама по себе (независимо от потолков выше —
несколько слоёв защиты): длинный список теперь не падает в чат простынёй, а уходит через
`reply_expandable(reply_fn, body, header="")` — сворачивает текст Telegram-тегом
`<blockquote expandable>` (HTML parse mode, `html.escape` обязателен), в чате видна одна
строка со стрелочкой «развернуть». Лимит Telegram на сообщение (4096 символов) сам тег
не снимает — если `body` не влезает даже под тегом, режется на несколько сообщений, каждое
в своём collapsible-блоке (найдено 2026-08-31, "потестировал на себе, засрал чат"). Режет
**по границам строк**, не по количеству символов подряд — сырая нарезка рвала текст
посреди слова между соседними сообщениями (тот же живой тест, что нашёл баг выше);
единственная строка длиннее лимита — редкий случай, режется по символам только она.
Использован пока только в `/memory` — остальные «простынные» админ-команды (`/chats`,
`/users`, `/cost`, `/activity`) шлют себе в личку и не клоггают общий чат, поэтому не
трогала; переиспользовать `reply_expandable` там — тривиально, если понадобится.

**Общий инвариант:** любой источник данных, попадающий в system-prompt или в `messages`,
ОБЯЗАН иметь лимит по РАЗМЕРУ, а не только по количеству элементов. Добавляешь новый
источник — сразу с лимитом, рассчитанным на окно 200k (Haiku).

### Инцидент 2026-07-26 (для истории)
Группа падала с `400 invalid_request_error: prompt is too long: 257099 > 200000`.
Две независимые причины, наложившиеся друг на друга:
1. `get_all_chat_memory()` без потолка отдавала все живые факты всех 15 участников —
   590k символов ≈ 236k токенов при окне Haiku 200k.
2. Каденс извлечения стоял на `count_chat_messages(chat_id) % N == 0`. Счётчик залипал
   на 1000 (см. ниже), извлечение запускалось на КАЖДОМ сообщении и жгло токены прогоном
   транскрипта через модель. Парадокс: чем реже бота зовут в чат, тем вернее чат сгорает —
   реплики бота вытесняются из окна 1000 строк, и `COUNT(*) WHERE is_bot=0` упирается в 1000.
Починено в v0.8.0: потолок на чтении + `should_extract_chat_memory()`. Вес промпта
упал с 236k до ~4k токенов, дневной расход по биллингу вернулся к прежнему уровню.

### Разбор JSON из ответа модели: только `parse_json_lenient`
`text.find("{")` + `text.rfind("}")` — мина, а не разбор. Если ответ обрезан по
`max_tokens`, `rfind` находит ВНУТРЕННЮЮ скобку последнего целого элемента, срез выходит
вида `{"participants": [{...}, {...}` и `json.loads` падает с `Expecting ',' delimiter`.
Теряется не хвост, а ВСЁ окно памяти по всем участникам сразу, и молча: `except` глотал.

Всегда `api_errors.parse_json_lenient(text, "{" | "[", label=...)`: сначала строгий
разбор, при неудаче — досборка (скан глубины скобок с учётом строковых литералов,
последний недописанный элемент отбрасывается). `None` = разобрать не удалось вообще.
Применён во всех четырёх точках: `extract_memory`, `extract_all_participants_memory`,
фильтр фактов в `greet_new_member`, `whatsapp.extract_memory`. Не возвращать find/rfind.

Рядом — `api_errors.was_truncated(response)` (`stop_reason == "max_tokens"`). Проверять
ОБЯЗАТЕЛЬНО при разборе структурированного ответа: без этой строки факт обрезки не виден
в логе вообще, и ошибка выглядит загадочной.

#### Инцидент 2026-08-03
`extract_all_participants_memory` теряла ~11% извлечений (65 падений против 531 успеха
за 5 суток, ровно каждый день). `max_tokens=1024` не хватало на 5–12 участников с двумя
массивами фактов: позиции обрыва кучковались у потолка (median 2243 симв. ≈ 1024 токена
кириллицы). В личке ошибок было ноль — там плоский массив влезал, но код разбора стоял
такой же хрупкий. Починено: `max_tokens=4096`, «не больше 3 фактов каждого типа» в
промпте, `parse_json_lenient`, `was_truncated`, `chat_id` + `exc_info=True` в логе.
Проверено офлайн: на 215 точках обрыва старый разбор падал 187 раз, новый спасает факты
во всех 215.

### Важно
- `db.get_group_history()` (строки «Имя: текст») оставлена специально — её используют `daily_chat_review` и `cmd_review`. Не путать с `get_group_transcript()` и не удалять.
- Старый `extract_group_memory` удалён, заменён на `extract_all_participants_memory`. Не возвращать старый.
- `count_chat_messages()` **немонотонна**: `save_group_message` подрезает `group_messages` до 1000 строк на чат, поэтому `COUNT(*)` перестаёт расти и любая проверка `% N == 0` от него залипает навсегда. Именно так групповая память однажды перестала обновляться. Для каденса использовать `should_extract_chat_memory()`, а не счётчик. Сама `count_chat_messages` больше нигде не вызывается — оставлена как справочная.
- В `should_extract_chat_memory` дельту `MAX(id)` брать НЕЛЬЗЯ: `group_messages.id` — глобальный AUTOINCREMENT на все чаты, и болтовня в соседней группе продвигала бы счётчик тихому чату (извлечение = вызов Haiku на 50 реплик — запускалось бы почти на каждом сообщении). Считаются строки **этого** чата новее `last_extract_id` (таблица `chat_extract_state`).

## Открытые задачи (не «известные баги», а запланированное)
- **Гигиена памяти**: дедуп фактов (`UNIQUE(user_id, context, chat_id, fact)` +
  `INSERT OR IGNORE`; индекс не создастся, пока в таблице есть дубликаты) и разовая
  чистка просроченных (`DELETE FROM memory WHERE expires_at IS NOT NULL AND expires_at <= now`,
  ~380k символов балласта). На размер промпта не влияет — просроченные и так фильтруются,
  а с v0.11.3–0.11.5 все три функции чтения памяти (`get_memory`, `get_memory_for_private`,
  `get_all_chat_memory`) капаются по `MEMORY_LONG_PER_USER`/`MEMORY_MEDIUM_PER_USER`, так
  что даже необузданный дубликат-мусор в таблице (2026-08-31: "Поделился фото" 13 раз,
  740 фактов на человека в одном чате) больше не раздувает system-prompt. Дедуп теперь
  вопрос КАЧЕСТВА 20 отдаваемых фактов (чтобы это были 20 РАЗНЫХ фактов, а не 13 вариаций
  одного и того же, вытесняющих из-под потолка что-то более информативное), не корректности.
  **Инструмент для разовой ручной чистки — `dedup_memory.py`** (v0.11.6+, корень репо,
  НЕ часть бота, никем не импортируется): `--mode exact` убирает буквальные повторы без
  API, `--mode llm` просит модель объединить близкие по смыслу формулировки (стоит
  денег, один вызов на группу `user_id+context+chat_id+tier`, `max_tokens=8192` — на
  группах в сотни-тысячи фактов меньше не хватает, см. живой инцидент ниже). Фильтры
  `--user-id`/`--chat-id`/`--tier`, `--limit-groups N` (только llm — пробный прогон на
  части перед безлимитным), `-v`/`--verbose` (показывает сами факты — exact: кто чей
  дубль, llm: полный список «было»/«стало» на группу, не только счётчики — важно перед
  `--apply`, чтобы свериться, что модель ничего не потеряла/не выдумала). Дефолт —
  dry-run: читает со снимка во временном файле, sudo НЕ требует. `--apply` пишет в
  боевой файл напрямую — `data/` на сервере root:root, нужен `sudo` (для llm — `sudo -E`,
  прокинуть `ANTHROPIC_API_KEY`). `--model` принимает короткие имена
  (`haiku`/`sonnet`/`opus`/`fable`, реестр `MODEL_ALIASES` дублирует `MODELS` из bot.py)
  или полную API-строку. По завершении llm-режима печатает время, токены
  (in/cache_write/cache_read/out по отдельности) и оценку стоимости по локальной
  табличке `PRICING` (тоже дубль `MODELS`, сверять при смене цен там) — а если был
  `--limit-groups`, ещё и грубую экстраполяцию на весь фильтр. Живой масштаб на
  2026-08-31: 85k фактов в таблице, 264 группы с 2+ фактами; пробный прогон 5 групп
  Sonnet'ом — 312с (~62с/группу), экстраполяция на все 264 группы — грубо ~4.5 часа.

  **У этого ключа/пула включено автоматическое prompt caching** — не только для
  системных промптов, для ЛЮБОГО достаточно большого входа. Для дедупа вход ВСЕГДА
  уникален (разные факты в каждой группе), значит это ВСЕГДА запись в кэш, никогда
  чтение — `usage.input_tokens` при этом почти пустой (единицы токенов), а реальный
  вес в `cache_creation_input_tokens`. Без учёта этого оценка стоимости занижалась
  примерно в 100 раз (проверено: 400 фактов, 40690 символов -> `input_tokens=2`,
  `cache_creation_input_tokens=16186`). `CACHE_WRITE_MULTIPLIER`/`CACHE_READ_MULTIPLIER`
  (1.25x/0.1x, стандартные множители Anthropic для 5-минутного ephemeral-кэша) это
  учитывают. Стоит держать в уме и за пределами этого скрипта — если где-то ещё в
  проекте появится любой достаточно большой одноразовый payload, `/cost` может так же
  недосчитывать, если сам не смотрит на `cache_creation_input_tokens`.

# whatsapp.py

Отдельный сервис (FastAPI webhook, `docker-compose.yml` сервис `claudushka-wa`, порт
8080). Общий с bot.py модуль — только `api_errors.py` и `db.py`. Свой реестр моделей
отсутствует, см. `docs/claude/models-and-costs.md` (раздел про whatsapp.py).

## Статус: сервис на паузе (с 2026-09-19)
Решение Алексея: токен Meta протух (на стенде — 401, `code 190`), каналом никто не
пользуется. Держать открытым порт 8080 ради мёртвого сервиса незачем. `claudushka-wa`
(и `claudushka-wa-test` на стенде) получили `profiles: ["whatsapp"]` в соответствующих
`docker-compose*.yml` — обычный `docker compose up -d` их больше НЕ поднимает.

**Код и это правило НЕ тронуты** — `whatsapp.py` остаётся рабочим и актуальным (все
фиксы ТЗ-1/3/4/5, включая ниже по этому файлу, применялись и к нему тоже), просто
контейнер не запускается по умолчанию.

**Вернуть в строй**, когда появится новый токен Meta:
```bash
docker compose --profile whatsapp up -d
```
(на стенде — `docker compose -f docker-compose.test.yml --profile whatsapp up -d`).
Если хочется вернуть сервис в постоянный автозапуск (не только разовый ручной старт) —
убрать `profiles: ["whatsapp"]` из `docker-compose.yml` целиком, это единственное
условие паузы.

**Остановить и удалить уже запущенный на проде `claudushka-wa`** (если он ещё
поднят с прошлого раза — новый `docker compose up -d` без флага его не остановит
сам, `profiles:` только не даёт ПЕРЕСОЗДАТЬ/поднять заново, уже бегущий контейнер
продолжит работать, пока его явно не остановить):
```bash
docker stop claudushka-wa && docker rm claudushka-wa
```

## Безопасность вебхука (`POST /webhook/whatsapp`, фикс 2026-09-19, `d71d7c9`)
До этой правки `POST /webhook/whatsapp` принимал любой запрос без проверки подписи —
порт 8080 открыт наружу, кто угодно, зная URL, мог прислать JSON с произвольным `from` и
заставить бота потратить токены пула и ответить с нашего WA-аккаунта. Починено:

- **Проверка подписи `X-Hub-Signature-256`.** `_verify_wa_signature(raw_body, header)` —
  HMAC-SHA256 от СЫРОГО тела запроса (`await request.body()`, до `json.loads` — если
  распарсить и сериализовать заново, подпись не сойдётся, JSON-сериализация не
  побайтово идентична исходному телу) на ключе `WHATSAPP_APP_SECRET` (App Secret
  приложения в Meta for Developers, НЕ `WEBHOOK_VERIFY_TOKEN` — это разные секреты,
  второй только для GET-верификации при подписке). Сравнение через
  `hmac.compare_digest`. Нет заголовка / не начинается с `sha256=` / не совпало → 403,
  warning в лог без тела запроса.
- **Fail-closed.** `WHATSAPP_APP_SECRET` не задан → сервис стартует (не крашится),
  `logger.critical` при импорте модуля, ВСЕ POST отклоняются 403 до перезапуска с
  секретом в `.env`. Молча пропускать непроверенные запросы нельзя — это была бы дыра
  того же класса, что чинили.
- **Быстрый 200.** Обработка каждого сообщения идёт через `_spawn_background_task`
  (`_process_wa_message`), хендлер отвечает 200 сразу после проверки подписи, парсинга
  JSON и дедупа — не дожидаясь ответа Claude. Без этого Meta могла ретраить доставку по
  таймауту и пользователь получал бы дубль ответа.
- **Дедуп по `msg["id"]`.** `_is_duplicate_wa_message` — `OrderedDict[id, timestamp]`,
  TTL `WA_DEDUP_TTL_SECONDS` (600с) и потолок `WA_DEDUP_MAX_SIZE` (10000). In-memory,
  без персистентности — при рестарте забывается, это допустимо (повторно доставленный
  Meta дубль после рестарта обработается как новый, не страшно). OrderedDict, а не
  плоский dict — вставка хронологическая, TTL-чистка идёт с начала без полного скана.
- **Обход всех `entry`/`changes`.** Раньше бралось только `entry[0].changes[0]` — теперь
  двойной цикл по обоим уровням, Meta может прислать несколько апдейтов в одном вебхуке.
- `_spawn_background_task` — своя копия того же паттерна, что и в bot.py (модули друг
  друга не импортируют), защищает фоновые задачи (`extract_memory`) от сборки GC без
  сохранённой ссылки. Общий принцип «никаких блокирующих вызовов из event loop» —
  `docs/claude/api-errors.md`.

## Порядок сообщений одного номера (2026-09-19)
Каждое сообщение обрабатывается в фоне независимой задачей — если один номер пишет два
сообщения подряд, без синхронизации обе обработки читают историю
(`db.get_conversation_by_key`) раньше, чем любая из них её сохранит: второй ответ не
видит первого вопроса, ответы могут прийти в обратном порядке.

- **`_acquire_phone_lock(phone)` / `_release_phone_lock(phone)`** — модульные словари
  `_phone_locks: dict[str, asyncio.Lock]` и `_phone_lock_refcount: dict[str, int]`.
  Лок на номер сериализует обработку ОДНОГО номера; разные номера обрабатываются
  параллельно, лока друг у друга не ждут.
- **Рефкаунт, а не приватные атрибуты `Lock`.** Нужно было понять «лок больше никто не
  держит и не ждёт», чтобы удалять его из словаря и не растить память на каждый номер,
  который когда-либо писал боту — но `asyncio.Lock._waiters` не публичный API (не
  документирован, может исчезнуть/измениться между версиями Python). Вместо этого —
  явный счётчик: `_acquire_phone_lock` создаёт `Lock()` при первом обращении (или
  переиспользует существующий) и увеличивает счётчик; `_release_phone_lock` уменьшает
  его и при достижении нуля убирает и лок, и счётчик из словарей. Обе функции
  синхронные, без `await` внутри — между вызовом и изменением счётчика невозможна
  гонка с другой корутиной (event loop однопоточный, переключение возможно только
  на точке `await`).
- **Где именно берётся лок.** `_acquire_phone_lock`/`async with lock`/`_release_phone_lock`
  (в `finally`) — ВНУТРИ фоновой задачи, вокруг `await handle_wa_message(phone, text)`
  в `_process_wa_message`. Быстрый ответ 200 самому вебхуку это не трогает — лок
  влияет только на порядок фоновой обработки, не на момент ответа Meta.
  Ветки image/audio/video/document (фиксированный ответ «пока не умею») лока не берут
  — они не читают/не пишут историю, синхронизировать нечего.
- **Проверено** (не закоммичен, тестовый скрипт по правилам не хранится в репо):
  `httpx.AsyncClient` + `ASGITransport` в ОДНОМ event loop с тестом (не синхронный
  `TestClient` — тот гоняет каждый `client.post()` в отдельном цикле через
  background-портал, и фоновая задача, подвешенная на `await asyncio.sleep(...)`,
  обрывается вместе с циклом раньше, чем успевает завершиться, — так что тест на
  `TestClient` показал бы «работает», даже если бы лок был сломан). Мок `handle_wa_message`
  с искусственной задержкой: два сообщения одного номера — строго последовательно и в
  исходном порядке (макс. параллелизм 1); два сообщения разных номеров — параллельно
  (макс. параллелизм 2); после завершения обработки лок и счётчик номера убираются из
  словарей (нет бесконечного роста).

**Деплой.** `WHATSAPP_APP_SECRET` должен появиться в `.env` на сервере ДО деплоя этого
кода — иначе fail-closed сразу отключит WhatsApp. Порядок: добавить секрет в `.env` →
`git pull` → `docker compose up -d --force-recreate` (нужен именно `--force-recreate`,
а не `restart`, — поменялась переменная окружения `.env`, а не только `requirements.txt`;
`.env` контейнер читает один раз при создании, `restart` его не перечитывает — см.
`.claude/rules/docker-compose.md`).

**Не проверено живым Meta-вебхуком** (проверено только локально `TestClient`'ом с
фиктивными env, 2026-09-19): реальная доставка от Meta, формат её ретраев при таймауте.

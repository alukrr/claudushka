# Режим разработчика в платной личке (ТЗ `feat/dev-mode`, v1.11.0)

Перед правкой `dev_mode_active`, `handle_dev_message`, `_dev_answer`, `ws_*`, `dev_history`, `DEV_*` констант,
таблиц `dev_mode` / `dev_messages` — читай этот файл. Исходное ТЗ с решениями Алексея — `tz-dev-mode.md`,
чек-лист стенда — `staging-checklist-dev-mode.md`.

## Что это
Отдельный изолированный режим для тех, кто пишет с Клодушкой код. Весь код сидит за `dev_mode_active(user_id)`
(личка + платный тариф + флаг). Для остальных чатов и для этой же лички вне режима ничего не меняется: единственное
касание обычного пути — три строки в начале `handle_message` (после бана и стартового бонуса, до группового блока).

В режиме ВЫКЛЮЧЕНЫ: персона и `CORE_IDENTITY`, память (`extract_memory`, блок памяти), профиль, DRAW-маркер и рисование,
автопоиск (нативный и Tavily/GPT). `/search`, `/imagine`, `/clear` и остальные команды — обычные `CommandHandler`'ы,
в `handle_message` не попадают и работают как раньше (`/clear` чистит обычный тред лички, не тред режима).

## Команды
- `/dev` — включить режим и показать статус (только личка, только paid). `/dev off` — выключить (личка, тариф не важен —
  чтобы можно было выйти и после ухода в free). `/dev reset` — очистить `dev_messages` и якорь окна; файлы остаются.
- `/ws` — список (имя, строки, размер, «в контексте / не влез»); `/ws get <имя>` — документом; `/ws rm <имя>`;
  `/ws clear yes` (без `yes` — только предупреждение). Только в активном режиме.

## Хранение
- Флаг: `dev_mode(user_id PK, enabled, updated_ts)` — `db.get_dev_mode_flag/set_dev_mode_flag`. Ушёл в free при включённом
  флаге → `dev_mode_active` = False, флаг и данные не трогаем (как `chat_models`); вернулся в paid → режим снова активен.
  Порядок проверки в `dev_mode_active`: флаг (дешёвый запрос), потом тариф — функция зовётся на КАЖДОМ сообщении лички.
- Тред: `dev_messages(id, user_id, role, content, ts)` + индекс `(user_id, id)`. С `conversations` не смешивается.
- Файлы: `data/devspace/<user_id>/<имя>` (плоская папка; `./data` уже смонтирован у обоих сервисов — compose не менялся,
  `--force-recreate` не нужен, `restart`/`/update` достаточно). Источник правды — файловая система, таблицы метаданных нет.
  Запись атомарная (`.tmp-*` + `os.replace`), `ws_list` пропускает точечные файлы и не-файлы. Имя — `_safe_filename`.
- Принимается только СТРОГИЙ UTF-8 без нулевых байтов, любое расширение. Бинарное — отказ с причиной.

## Сборка запроса (`_dev_answer`)
```
system   = [DEV_PROMPT (cache_control как у персоны), WORKSPACE (cache_control 5m)]
messages = dev_history(user_id) + user-turn [(фото) + текст], с service_block (время, reply-контекст) и mark_cache_tail
```
- `DEV_PROMPT` — статичный (f-строка от констант процесса), без `CORE_IDENTITY`/`_core_rules`/памяти. Про `[[FILE]]`, workspace,
  честность, служебный блок, разметку Telegram. Нейтральный род (не «она»).
- WORKSPACE (`ws_block_text`): манифест ВСЕХ файлов (по имени) + `<file name="…">` содержимое влезших. Порядок содержимого —
  свежие первыми (mtime_ns, затем имя) пока хватает `DEV_CTX_FILES_CHARS`; не влезший файл ПРОПУСКАЕТСЯ, а более мелкие
  и старые за ним ещё пробуются (`ws_partition`); пропущенные в манифесте с пометкой «не загружен в контекст (лимит)».
  Детерминирован: при неизменном workspace блок байт-в-байт тот же → кэш попадает.
- **Сознательное отступление от инварианта «system статичен»**: workspace в system отдельным блоком (как память), меняется только
  при изменении файлов. Время, reply-контекст — по-прежнему только в `service_block`.
- История: `pick_history_window` шагами (scope `("d", user_id)`, не пересекается с личкой `("c", …)`) + потолок
  `DEV_HISTORY_CHARS`: старые реплики режутся целиком, окно начинается с user, якорь переезжает на обрезанное начало
  (окно не прыгает на каждой реплике).
- Вызов — только `call_claude`, `usage_label="dev"` (в `/cost` отдельная метка, при ответе фолбэка — `dev_fallback`),
  `model=get_chat_model(user_id)`, `**dialog_params`, `max_tokens=out_tokens(model, DEV_OUT_TOKENS)`.
  **`timeout=DEV_REQUEST_TIMEOUT` (900 с) передаётся явно**: без него SDK отказывается от нестримингового запроса
  с `max_tokens` > ~21k, а 16k + запас thinking (8k у Sonnet/Opus/Fable) = 24k. Проверить на стенде, что пул/SDK это принимают.
- `400 prompt is too long`: пересборка без содержимого файлов (манифест остаётся), пользователю — предупреждение;
  если файлов в контексте и так нет или повтор снова 400 — `reply_api_error` с подсказкой `/dev reset`.

## История (что пишется в `dev_messages`)
- user, текст — как есть. user, файл(ы) — `[Загружены в workspace: a.py (120 строк), …] <подпись>`. user, фото — `[Скриншот] <подпись>`
  (сама картинка модели уходит в этом запросе, не сохраняется).
- assistant — текст ответа; каждый `[[FILE]]`-блок вырезан, вместо него `(файл имя сохранён в workspace, N строк)` — БЕЗ содержимого
  (в отличие от обычной ветки, где `_file_sent_note` кладёт первые 3000 символов). Содержимое — только в workspace.
- Всегда ПАРОЙ user+assistant (чередование ролей). Подтверждение «📎 сохранён» тоже пишется парой.
- Ошибка API → ничего не пишется (как в обычной ветке).

## Файлы от модели
`extract_files(text, limit=DEV_FILES_PER_REPLY)` (тот же парсер, параметр вместо копии). Каждый файл: > `DEV_FILE_MAX_BYTES` — не
отправляется и не сохраняется; закрытый блок → `ws_save` + документ; **незакрытый блок (ответ упёрся в лимит длины) уходит
документом с предупреждением, но в workspace НЕ сохраняется** — иначе оборванный файл затёр бы хорошую версию (решение
реализации, в ТЗ не было). Не поместился в лимиты workspace — документ уходит, пользователю предупреждение со ссылкой на `/ws rm`.

## Обработчик (`handle_dev_message`)
Сначала `_check_message_limit` (дневной лимит непроверенных, как везде). Затем по типу:
- текст → `_dev_answer`; документ → `_dev_store_document` (скачать, `ws_save`) → без подписи «📎 a.py сохранён (N строк)» БЕЗ вызова
  модели (бесплатно, в `usage_log` ничего), с подписью — запрос; фото → vision-запрос (подпись по умолчанию — `DEV_PHOTO_DEFAULT`);
- голос/видео/кружок/GIF → короткий отказ с подсказкой `/dev off`; стикеры в бота вообще не регистрируются.
- Отредактированные сообщения (`edited_message`) в режиме тихо игнорируются (без ответа и без захода в обычный путь).
- Реакции 👀/✍ НЕ ставятся: в режиме нет поиска и рисования, а «печатает…» держит `call_claude`.
- **Альбом** (`media_group_id`, документы и фото): каждый файл сохраняется сразу по приходу; состояние в памяти процесса
  `_dev_albums[(user_id, media_group_id)]`; один запрос на альбом через `DEV_ALBUM_WAIT_SEC` после последнего элемента
  (таймер — фоновая задача `_dev_album_flush` через `_spawn_background_task`, каждый новый элемент отменяет прежний таймер);
  подписи склеиваются через перевод строки; ни одной подписи (и нет фото) — одно общее подтверждение без модели. Опоздавший файл
  (после старта обработки) начнёт новый альбом — второй ответ. Хендлер НЕ ждёт сам: PTB обрабатывает апдейты по очереди, спящий
  хендлер задержал бы остальные файлы альбома. Рестарт процесса теряет таймер — файлы остаются в workspace, ответа не будет.

## Лимиты (env, значения = стартовые, калибровать на стенде)
`DEV_FILE_MAX_BYTES` 300000 · `DEV_WS_MAX_FILES` 50 · `DEV_WS_MAX_BYTES` 5000000 · `DEV_CTX_FILES_CHARS` 150000 ·
`DEV_HISTORY_CHARS` 40000 · `DEV_OUT_TOKENS` 16000 · `DEV_FILES_PER_REPLY` 5 · `DEV_ALBUM_WAIT_SEC` 2.0 ·
`DEV_REQUEST_TIMEOUT` 900. Reply-контекст в служебном блоке — `DEV_REPLY_CONTEXT_CHARS` 3000. Изменение env — `--force-recreate`.

## Влияние на контекст и деньги
Обычные чаты: ноль. В режиме максимальный запрос ≈ `DEV_PROMPT` (~2k символов) + до 150k символов файлов + до 40k истории + вопрос;
в токенах для кода — заметно больше обычной реплики. Соотношение символы/токены и цену — замерить на стенде по логам `PROMPT … kind=dev`
и `usage_log` (метка `dev`). Повторные вопросы по тому же workspace в пределах TTL кэша читают файлы из кэша; после паузы дольше TTL —
полная цена записи. Gemini-фолбэк/Gemini-модель чата: `cache_control` вычищается, каждый запрос платит файлы целиком.

## Грабли и что не сделано
- `/forget` и `db.clear_memory` НЕ трогают `dev_messages` и `data/devspace/<user_id>` — открытый вопрос к Алексею (`open-tasks.md`).
- Старые версии файлов не храним (перезапись). Подпапки, ZIP, git, выполнение кода — не входят и (для выполнения) не будут никогда.
- Tool use нет: при фолбэке на Gemini `tools` не передаются, режим бы деградировал.
- `ws_load` читает ВСЕ файлы workspace на каждый запрос (до 5 МБ) — в потоке (`asyncio.to_thread`), для текущих лимитов терпимо.
- Ответ длиннее 4096 символов режется на куски по 4096 (Markdown → при ошибке разметки кусок уходит plain).

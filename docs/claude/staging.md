# Тестовый стенд (постоянный, ТЗ-4)

Перед правкой `docker-compose.test.yml`, `.env.test.example`, `scripts/test_wa_stand.py`
— читай этот файл. Стенд — постоянная часть инфраструктуры, не разовый скрипт: держать
в рабочем состоянии, использовать для каждого рискованного ТЗ (обновления зависимостей,
крупные рефакторинги), не только для ТЗ-4.

## Зачем

Прод — единственный экземпляр бота на реальных пользователей. Рискованные правки
(мажорные апдейты зависимостей, серьёзные изменения хендлеров) нужно сначала прогнать
на отдельном боте с той же кодовой базой, но без риска сломать чужие чаты. Стенд —
именно это: второй экземпляр `claudushka`/`claudushka-wa` на том же сервере, с
отдельным Telegram-ботом (токен от @BotFather, держит Алексей) и **пустой** БД.

## Из чего состоит

- `docker-compose.test.yml` — два сервиса, `claudushka-test` и `claudushka-wa-test`,
  зеркалят прод (`docker-compose.yml`), но:
  - `container_name` с суффиксом `-test`, чтобы не путать в `docker ps`/`docker logs`.
  - `env_file: .env.test` — свой набор переменных (ниже).
  - Данные — в `./data-test` (не `./data`!). **Пустая БД**, не копия прода: иначе
    тестовый бот попытается слать дневные обзоры (`daily_chat_review`) в чужие боевые
    чаты — `allowed_chats` в тестовой БД должна быть пустой, чат тестовому боту нужно
    добавлять заново, отдельно от прода.
  - `claudushka-test` **без** `/var/run/docker.sock` и **без** `.:/repo` — self-update
    (`/update`) на стенде не нужен и опасен (стенд обновляется вручную через
    `git pull` + пересборку, см. ниже). Поэтому и без `git`/`docker.io` в `command:`
    — они там были только ради `/update`.
  - `claudushka-wa-test` слушает `127.0.0.1:8081` (не `0.0.0.0`!) — наружу не светить,
    только с самого сервера (`curl` из скрипта ниже или вручную по SSH).
- `.env.test.example` — шаблон. Реальный `.env.test` — только на сервере, в `.gitignore`
  (как и `.env`), в репозиторий не попадает.
- `scripts/test_wa_stand.py` — прогон WhatsApp-цепочки на стенде (см. ниже).
- `data-test/` — данные стенда, в `.gitignore`, на сервере создаётся пустой директорией.

## `.env.test`: что в нём

Единственное ОБЯЗАТЕЛЬНОЕ отличие от боевого `.env` — `TELEGRAM_BOT_TOKEN`: токен
отдельного тестового бота. Алексей создаёт его сам у @BotFather (этап 0 ТЗ-4) и держит
у себя — **не передавать токен в репозиторий и не передавать его в чат с агентом**
(в отличие от `ANTHROPIC_API_KEY` и остальных ключей, тестовый Telegram-бот отвечает
реальным пользователям от имени этого токена, и если он утечёт куда-то за пределы
сервера — им сможет пользоваться кто угодно).

Все остальные переменные — **те же значения, что в боевом `.env`**: свой ключ Anthropic
под стенд заводить не нужно (это тот же пул, тот же баланс), свой WhatsApp Business
номер — тоже (номер один на весь аккаунт Meta). Практическое следствие: тесты на стенде
тратят реальный баланс пула, а WhatsApp-тест шлёт **реальное** сообщение через
**реальный** WhatsApp API на телефон Алексея — это осознанный компромисс ТЗ-4
(«проверяется вся цепочка, кроме самого Meta»), не дыра. Держать в уме при прогоне
чек-листа — счёт за токены общий с продом.

## Стенд живёт в отдельном `git worktree`, не в `~/claudushka`

**Не делать `git checkout <ветка>` внутри `~/claudushka`** (именно так стенд поднимали
до этой правки) — это боевая директория, там же `docker-compose.yml` прод-сервисов и
`.env` с реальными секретами. Переключение ветки прямо в ней означает, что окно между
`checkout` на тестовую ветку и обратным `checkout main` — это окно, где `~/claudushka`
физически содержит непроверенный код; случайный `/update` от Алексея в этот момент или
просто человеческая ошибка при выборе директории — и в прод улетает то, что должно
было остаться на стенде. Второй риск того же переключения на месте: `docker compose
-f docker-compose.test.yml`,
запущенный из `~/claudushka`, получает от Docker Compose имя проекта `claudushka` — то
же самое, что у боевого `docker-compose.yml` в той же директории (имя проекта по
умолчанию — basename каталога). Общие ресурсы с этим именем (сеть по умолчанию и т.п.)
у двух `docker-compose*.yml` пересекаются, и `down` тестового стека рискует задеть
боевой.

Решение — **`git worktree`**: второе рабочее дерево того же репозитория, отдельная
директория `~/claudushka-test`, своя текущая ветка, НЕ трогает состояние `~/claudushka`
вообще (тот как был на `main`, так и остаётся). Имя проекта Docker Compose при запуске
из `~/claudushka-test` становится `claudushka-test` — отдельное от боевого `claudushka`,
коллизии ресурсов не будет.

## Поднять стенд

Один раз — завести worktree (на сервере, из `~/claudushka`, саму `~/claudushka` не
трогает):

```bash
cd ~/claudushka
git fetch origin
git worktree add ~/claudushka-test origin/<ветка-с-правками>
```

Дальше всё живёт в `~/claudushka-test`, `~/claudushka` эту команду не изменяет никак:

```bash
cd ~/claudushka-test
mkdir -p data-test
cp .env.test.example .env.test   # один раз — дальше редактировать вручную
nano .env.test                   # вписать TELEGRAM_BOT_TOKEN тестового бота +
                                  # остальные значения, скопированные из .env
                                  # (включая ANTHROPIC_BASE_URL, см. ниже)
docker compose -f docker-compose.test.yml up -d
docker compose -f docker-compose.test.yml logs -f   # смотреть, что оба сервиса стартовали
```

Первый старт ставит зависимости из `requirements.txt` (`pip install` в `command:`,
как и в проде) — минуту-другую подождать, пока оба контейнера допишут в лог что-то
вроде «Клодушка started» / «Uvicorn running».

**`ANTHROPIC_BASE_URL` в `.env.test` обязателен**, хоть и не выделен в отдельный пункт
выше как «единственное обязательное отличие» (им остаётся `TELEGRAM_BOT_TOKEN`) — без
`ANTHROPIC_BASE_URL` запросы стенда уходят напрямую в `api.anthropic.com`, минуя пул
`router.apitoken.sale`: не будет ни скидки пула, ни общего с продом баланса, счёт
пойдёт по прямым ценам Anthropic на отдельный (или несуществующий) ключ. Значение —
то же, что в боевом `.env` (см. `.env.test.example`).

## Group Privacy в BotFather (нужно для тестирования групп)

Новый бот у @BotFather по умолчанию создаётся с **включённым Group Privacy** — в этом
режиме бот в группах видит только команды (`/что-то`), реплаи на свои сообщения и явные
упоминания (`@имя_бота ...`), но НЕ видит остальные сообщения участников. Для пункта 15
чек-листа (`docs/claude/staging-checklist.md`) этого достаточно, но если нужно
протестировать что-то, зависящее от пассивного чтения группового транскрипта без
упоминания бота (фоновое извлечение памяти, распознавание фото/голоса без адресации,
см. `docs/claude/group-chat.md` и `docs/claude/media.md`) — режим нужно выключить:

1. В чате с @BotFather → `/mybots` → выбрать тестового бота → **Bot Settings** →
   **Group Privacy** → **Turn off**.
2. Изменение применяется только к группам, в которые бота добавляют **после**
   выключения — если тестовая группа уже существует, бота нужно удалить из неё и
   добавить заново (или выдать ему права администратора группы — админам Group Privacy
   не мешает видеть сообщения независимо от режима).

## Не добавлять тестового бота в реальные/боевые чаты

Тестовый бот — это **ЧУЖОЙ** экземпляр Клодушки с чистой БД, но с той же логикой:
добавленный в реальный рабочий чат, он начнёт отвечать участникам НАРЯДУ с боевым
ботом (если оба не будут молчать по гейтингу) и, что важнее, сам чат попадёт в
тестовую `allowed_chats` — а значит в 22:00 по Берлину получит `daily_chat_review`
от ВТОРОГО бота, независимо от того, что уже прислал боевой (см. «Известные
ограничения» ниже). Тестировать группы — **только в отдельной тестовой Telegram-группе**,
созданной специально для этого (пункт 14 чек-листа).

## Переключить стенд на другую ветку

Внутри `~/claudushka-test` — обычный `git checkout`, это уже ИЗОЛИРОВАННОЕ дерево,
не боевое, переключать ветки в нём безопасно:

```bash
cd ~/claudushka-test
git fetch origin
git checkout origin/<другая-ветка>          # detached HEAD, этого достаточно для теста
docker compose -f docker-compose.test.yml up -d --force-recreate
```

## Обновить стенд (после новых коммитов в ТОЙ ЖЕ ветке)

Стенд НЕ имеет self-update и НЕ смонтирован на `/repo` — обновляется вручную, из
`~/claudushka-test` (не из `~/claudushka`):

```bash
cd ~/claudushka-test
git fetch origin
git checkout origin/<ветка>          # worktree создан от origin/<ветка> — это detached HEAD,
                                     # поэтому `git pull` даст «You are not currently on a branch»
docker compose -f docker-compose.test.yml up -d --force-recreate
```
(`git pull` заработает, только если worktree привязан к локальной ветке:
`git checkout -B <ветка> origin/<ветка>`.)

`--force-recreate` тут оправдан всегда (не только при смене `.env.test`) — стенд
предназначен для быстрой итерации, пересоздание контейнера дешевле, чем гадать,
достаточно restart или нет.

## Погасить стенд

```bash
cd ~/claudushka-test
docker compose -f docker-compose.test.yml down
```

Данные (`data-test/`) при этом НЕ удаляются (только контейнеры) — если нужна полностью
чистая БД для следующего прогона: `rm -rf data-test && mkdir data-test` ПОСЛЕ `down`
(не при поднятых контейнерах — файл БД будет занят процессом).

## Убрать стенд целиком (worktree)

Когда стенд больше не нужен (не после каждого прогона — worktree предназначен жить
между сессиями тестирования, как и сам стенд):

```bash
cd ~/claudushka-test && docker compose -f docker-compose.test.yml down
cd ~/claudushka && git worktree remove ~/claudushka-test
```

`git worktree remove` откажется, если в `~/claudushka-test` остались незакоммиченные
изменения — это защита, а не баг; для стенда их там быть не должно (правки идут через
обычный git-флоу в WSL, не редактированием файлов прямо на сервере).

## Как тестировать WhatsApp на стенде

Стенд слушает `127.0.0.1:8081`, наружу не видно — Meta туда достучаться не может
(и не должна, это не боевой webhook). Вместо реального Meta-вебхука прогоняем
`scripts/test_wa_stand.py`: он сам собирает JSON-payload в формате Meta, подписывает
его HMAC-SHA256 (`WHATSAPP_APP_SECRET` из `.env.test`, читает файл сам, секрет никуда
не печатает) и шлёт `curl`'ом на `127.0.0.1:8081/webhook/whatsapp` — то есть честно
проходит проверку подписи в `_verify_wa_signature`, а не обходит её.

WhatsApp (и на проде, и на стенде) **на паузе с 2026-09-19** — `claudushka-wa-test`
получил `profiles: ["whatsapp"]`, обычный `docker compose ... up -d` его не поднимает
(см. `.claude/rules/whatsapp.md`). Нужен явный запуск перед тестом:

```bash
cd ~/claudushka-test
docker compose -f docker-compose.test.yml --profile whatsapp up -d
python3 scripts/test_wa_stand.py <твой_номер_без_плюса> "текст сообщения"
# пример:
python3 scripts/test_wa_stand.py 491701234567 "привет со стенда"
```

Если всё поднято правильно — в течение нескольких секунд на указанный номер придёт
**настоящий** ответ в WhatsApp (боевой Meta Send API, см. предупреждение выше про общий
номер). Если ответа нет — `docker logs claudushka-wa-test` (сначала проверить, что
запрос вообще дошёл: `INFO: ... "POST /webhook/whatsapp HTTP/1.1" 200 OK` — если вместо
200 пришло 403, проверь `WHATSAPP_APP_SECRET` в `.env.test`).

Это проверяет всю цепочку (подпись → дедуп по `msg["id"]` → лок по номеру → история →
Claude → отправка ответа) — единственное, что НЕ проверяется — сама доставка от
настоящего Meta до нашего сервера (для этого нужен реальный вебхук от Meta на боевой
номер, стенд его не эмулирует).

## Бэкап и откат прод-БД перед рискованным деплоем

Стенд проверяет КОД, но не защищает от проблем при самом деплое на прод (правки схемы
БД, миграции в `init_db()`) — если деплой прошёл, а что-то всё же сломалось, нужен
быстрый путь назад. Делать это на `~/claudushka` (прод), не на стенде.

**Бэкап БД перед деплоем.** НЕ `cp data/claudushka.db data/claudushka.db.bak` —
контейнер `claudushka` держит файл открытым, `cp` во время записи может скопировать
файл в противоречивом состоянии (частично записанная страница SQLite). Используется
встроенный backup API sqlite3, безопасный на открытой БД:

```bash
docker exec claudushka python3 -c "
import sqlite3
s = sqlite3.connect('/app/data/claudushka.db')
d = sqlite3.connect('/app/data/claudushka.db.bak-$(date +%Y%m%d-%H%M)')
s.backup(d)
d.close()
"
```

**Зафиксировать коммит ДО пула** (чтобы было куда откатывать):

```bash
cd ~/claudushka
PRE=$(git rev-parse HEAD)
echo "$PRE" > /tmp/claudushka-pre-deploy.txt   # на всякий случай, если сессия оборвётся
git pull
docker restart claudushka   # или compose up -d --force-recreate, если менялся .env
```

**Откат при проблеме** — именно к зафиксированному `$PRE`, не к `main~1` и не
частичным `git checkout <файл>` на отдельные файлы (оба варианта не гарантируют
согласованное состояние, если пул принёс больше одного коммита или если понадобится
откатить и `requirements.txt`, и код одновременно):

```bash
cd ~/claudushka
git reset --hard "$(cat /tmp/claudushka-pre-deploy.txt)"   # или сам хеш, если файла нет
docker restart claudushka
```

Если проблема оказалась в схеме БД (а не в коде) — дополнительно вернуть файл БД из
бэкапа (контейнер должен быть остановлен на момент подмены файла):

```bash
docker stop claudushka
cp data/claudushka.db.bak-YYYYMMDD-HHMM data/claudushka.db
docker start claudushka
```

`git reset --hard` — необратимая операция для локальных незакоммиченных изменений в
`~/claudushka`; на проде их там в норме быть не должно (файлы правятся только через
`git pull`, не редактируются на месте — см. корневой `CLAUDE.md`, раздел «Правила»), но
стоит проверить `git status` перед `reset --hard`, если есть малейшее сомнение.

## Известные ограничения

- Стенд и прод используют один и тот же WhatsApp Business номер — параллельный
  ручной тест через реальный WhatsApp (не через скрипт) неотличим от прода на
  стороне получателя.
- `daily_chat_review` на стенде сработает по расписанию (22:00 Берлин) для любого чата,
  который окажется в `allowed_chats` тестовой БД — см. «Не добавлять тестового бота в
  реальные/боевые чаты» выше; если всё же понадобилось (не рекомендуется) — `/review_off`,
  `docs/claude/daily-review.md`.
- `/update` на стенде не работает (сознательно, см. выше) — обновление только вручную.

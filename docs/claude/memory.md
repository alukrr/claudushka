# Память

Перед правкой `memory`-таблицы, `extract_memory`, `extract_all_participants_memory`,
`get_memory`/`get_memory_for_private`/`get_all_chat_memory`, `/memory`, `/memory_full`,
`/forget` — читай этот файл. **Этот раздел раньше жил без собственного заголовка внутри
«Известные баги» — заголовок `## Память` восстановлен при переносе (2026-09-19,
разбивка CLAUDE.md, `855bcfe`).**

## Схема
Факты хранятся в таблице `memory` (`context` + `chat_id` + `tier` + `expires_at`):
- `context='private', chat_id=NULL` — сказано боту в личке.
- `context='group', chat_id=<id>` — узнано в конкретной группе.
- `tier='long'`, `expires_at=NULL` — долгосрочные факты (не протухают).
- `tier='medium'`, `expires_at=<unix+7d>` — среднесрочные, TTL 7 дней. Автоматически исключаются из выборок после истечения.
- **Просроченные строки удаляются** (`db.purge_expired_memory()`: `DELETE ... WHERE expires_at IS NOT NULL
  AND expires_at <= now`; long не трогается): раз в сутки в 04:30 Berlin (`memory_purge_job`, имя джоба
  `memory_purge`) и один раз на старте бота (фоном, `_spawn_background_task`). До v1.4.3 их не удалял никто —
  таблица копила мусор (живой случай 2026-10-18: ~1160 просроченных medium на человека в одном чате, dedup
  слал их модели). Чтения фильтруют `expires_at > now` и раньше, поэтому для бота ничего не меняется;
  `/memory_full` тоже читает через `get_memory` с этим фильтром — просроченного не показывает ни до, ни после.

## Профиль (v1.5.0)
Поверх фактов — маленький **проверенный** профиль участника (имя, город, профессия…), который идёт в system перед
фактами и важнее них; модель только предлагает, админ раз в неделю подтверждает. Всё — в `docs/claude/profile.md`.
`/forget` чистит и его (в пределах своей области, см. раздел «`/forget`»).

## Три уровня (группа)
1. **Краткосрочная** — `group_messages` (последние 50 реплик) → `build_group_messages()` → `messages` в API. Не персонализирована, весь чат. Подробнее — `docs/claude/group-chat.md`.
2. **Среднесрочная** (`tier='medium'`) — события и временные состояния этой недели (попала под дождь, поругалась с Валерой, купила клубнику). TTL 7 дней.
3. **Долгосрочная** (`tier='long'`) — устойчивые факты о людях: кто они, где живут, чем занимаются, интересы, возраст, взгляды. Без TTL.

## Извлечение
- **Личка** — `extract_memory()` по личному треду (`fix/private-memory-extract`, v2.13.1, ТЗ `docs/claude/tz-private-memory.md`). Модель — `DEFAULT_MODEL_ID` (Lite), как и все
  служебные вызовы (старое «Sonnet, hardcoded» отменено 2026-09-19, `docs/claude/models-and-costs.md`); расход — метка `extract_memory` на чат пользователя.
  - **Каденс — по базе, не по окну истории.** `_maybe_extract_private_memory(user_id)` зовётся после КАЖДОГО сохранения пары реплик в личке
    и сама решает: `n = db.count_conversation(user_id)`, запуск при `private_extract_due(n)` — `n >= MEMORY_EXTRACT_EVERY*2` и
    `n % (MEMORY_EXTRACT_EVERY*2) < 2` (последняя пара пересекла кратное 10; верно при любой чётности треда; после `/clear` счёт заново).
    Места вызова — все, где подряд идут два `db.save_message(user_id, …)`: основной диалог и ветка рисования («нарисуй …», успех и неудача) в `handle_message`,
    ответ на фото и файлы `_finish_media_answer`. Режим разработчика (`dev_messages`) и `whatsapp.py` не затронуты. Новое место, сохраняющее пару в личке, —
    обязано звать помощник (структурный тест `test_every_save_message_site_calls_helper` это проверяет).
  - **Почему не окно.** До v2.13.1 условие было `len(messages) % 10 == 0`, где `messages` — окно `private_history` (пары) + текущая реплика, то есть длина
    ВСЕГДА нечётная, и извлечение в личке не срабатывало ни разу (инцидент 2026-11-12, `docs/claude/incidents.md`). Тот же класс ошибки, что `count_chat_messages`
    (`.claude/rules/db.md`): каденс считают по базе, окно ходит шагами и немонотонно.
  - **Что видит модель:** последние `MEMORY_EXTRACT_EVERY*2` (10) строк треда из базы (`db.get_conversation_rows`, по `id`, не по `timestamp`: пара сохраняется в одну секунду),
    а не окно. **Лимит размера:** `clip_extract_messages` — реплика до `MEMORY_EXTRACT_MSG_CHARS` (1500) знаков, весь диалог до `MEMORY_EXTRACT_TOTAL_CHARS` (12000),
    не влезло — отбрасываются самые старые реплики. Параметр `messages` у `extract_memory` остаётся (общий вход для будущей первичной обработки старых тредов).
  - **Промпт:** факты — только из реплик пользователя (`role=user`), реплики `assistant` — лишь контекст (как в группе: реплики бота из извлечения убраны, инцидент 2026-09-28).
  - Запись: `db.add_memory_facts(..., "private", None)` → `context='private'`, `chat_id IS NULL`, всё в `long` (уровня `medium` в личке нет); предложения профиля — `chat_id=0`.
  - Запуск — `_spawn_background_task(asyncio.to_thread(...))`, `usage_ctx` копируется в поток. Ошибки — в лог (`Memory extraction error`), ответ пользователю не ломают.
  - Размер контекста: в личный system-промпт начинают попадать личные факты под прежним потолком (`MEMORY_LONG_PER_USER` 12 + `MEMORY_MEDIUM_PER_USER` 8, `get_memory_for_private`);
    новый вызов — до 12 000 знаков диалога на Lite раз в 10 строк треда (5 пар), платит чат пользователя.
- **Группа** — `extract_all_participants_memory(chat_id)`: один вызов Haiku на весь 50-реплик транскрипт, извлекает **оба уровня** сразу для **ВСЕХ видимых участников**. Атрибуция — ТОЛЬКО по `user_id` через метки участников (v2.7.2, `docs/claude/tz-memory-uid.md`): `build_memory_participants` строит по строкам окна (люди, `user_id` не NULL; строки без `user_id` в запрос не идут) метки `P1`, `P2`… в порядке первого появления; строка транскрипта извлечения — `[P1] Ник: текст`, список участников — `P1 — Ник (также писал как: Ник2)` и `P2 и P5 — РАЗНЫЕ люди с одинаковым ником «Ник»`; модель отвечает `{"participants": [{"id": "P1", "long_term", "medium_term", "profile_updates"}]}`, `resolve_memory_participant` берёт `uid` по метке (неизвестная метка — пропуск с warning; только `name` без `id` — только если этот ник в окне принадлежит ровно одному `user_id`). Поиск `user_id` по нику в БД (`get_user_id_by_name_in_chat`) удалён: он и был причиной инцидента 2026-09-28 (сменил ник на чужой — факты пишутся на него; два человека с одним ником — все факты последнему). Уже сохранённые факты задним числом не переписываются (ручная чистка — dedup TUI). Метки живут только в одном запросе (через 15 сообщений `P3` — другой человек), поэтому в тексты фактов и профиля они не попадают: правило в system-промпте («метки — только для поля id; другого участника упоминай по нику») и подстраховка кода `replace_memory_tags` (отдельные метки текущего окна, в т.ч. `[P2]`, заменяются на последний ник метки; метка не из окна не трогается; число замен — в логе «Group memory extracted … меток в текстах заменено: N»). Транскрипт ДИАЛОГА (`build_group_messages`) и обзор метки не получают. Каденс: `db.should_extract_chat_memory(chat_id, MEMORY_EXTRACT_EVERY_CHAT)` (каждые 15 сообщений в чате, детали каденса — `.claude/rules/db.md`). Вызывается **до** проверки `is_bot_mentioned` — работает даже когда бота не упоминают. Запускается в фоне через `asyncio.to_thread`, чтобы не блокировать ответ.
- Реплики Клодушки (`is_bot`) в транскрипт группового извлечения НЕ идут — факты о людях только из реплик людей (запрет одним промптом Haiku не держал). Промпт дополнительно запрещает записывать розыгрыши с ботом («заблокирован», «позвонил Алексею»), и ярлыки «держит такие-то взгляды» по одной перепалке в long (инцидент 2026-09-28, `docs/claude/incidents.md` — ~80 мусорных фактов про «бан до звонка Алексею»).
- **Временное местоположение не должно попадать в `long` (v1.4.4).** Живой случай 2026-10-18: человек из Казани
  уехал в отпуск в Москву, в `long` легло «Живёт в Москве на Нагатинской» рядом со старым «Живёт в Казани». Оба
  промпта теперь требуют: место жительства/работа/семейное положение/возраст — только когда человек прямо говорит
  о себе как о постоянном («я живу в…», «переехал в…», «устроился в…»); поездки, отпуск, командировки,
  «сейчас в…», гости — `medium_term` в группе («В отпуске в Москве»); не писать в `long` то, что противоречит
  другому устойчивому факту, без явного «переехал/сменил». **В личке `extract_memory` отдаёт плоский массив и
  кладёт всё в `long` (уровня `medium` там нет), поэтому временное там просто НЕ записывается** — перевод лички на
  два уровня потребует правки логики, в патч не входил. Модель извлечения самих сохранённых фактов не видит, так
  что это защита только на уровне формулировки; она не заменяет проверенный профиль.
- Старый `extract_group_memory` удалён, заменён на `extract_all_participants_memory`. Не возвращать старый.

## Асимметрия чтения (намеренная, не баг)
- В личке `_memory_text(is_group=False)` (блок 2 system, `build_system`) зовёт `db.get_memory_for_private(user_id)` — личные факты ПЛЮС все групповые факты про этого человека из всех чатов (с дедупом). Группа течёт вверх.
- В группе `_memory_text(is_group=True)` зовёт `db.get_all_chat_memory(chat_id)` — факты **всех участников** ЭТОГО чата (оба tier, без просроченных). Личное в группу НЕ течёт, другие группы — тоже (изоляция по `chat_id`).

## Команды
- `/memory` — показывает факты текущего пользователя (в группе — только его факты этого чата; в личке — объединённое). Потолок показа — `MEMORY_LONG_DISPLAY`/`MEMORY_MEDIUM_DISPLAY` (30+10=40), больше, чем уходит в system-prompt (12+8=20, см. ниже) — человек читает сам, разово, не модель на каждый промпт.
- `/memory_full` — то же самое, но БЕЗ потолка вообще (вся история). **Намеренно не добавлена в `USER_HELP`/`ADMIN_HELP`** — единственное сознательное исключение из правила "новая команда → обе константы" в Definition of Done, чтобы не звали почём зря (может уйти как несколько десятков сообщений на давнего активного участника — v0.11.5-инцидент, XDNet, 740 фактов). Если решите документировать открыто — тогда добавляйте.
- `/forget` — с подтверждением, только там, где вызван; `/forget all` — всё везде, только в личке. Подробно — раздел «`/forget`» ниже (v2.13.0).
  До v2.13.0 команда стирала ВСЁ и без вопросов (инцидент 2026-11-12, `docs/claude/incidents.md`).

## `/forget`: подтверждение, область, «сувениры» (v2.13.0)
ТЗ — `docs/claude/tz-forget-confirm.md`, чек-лист стенда — `docs/claude/staging-checklist-forget-confirm.md`.
- **Область = там, где вызвана.** Группа: факты человека этого чата (`context='group'`, этот `chat_id`) + его профиль и предложения профиля этого чата.
  Личка: личные факты (`context='private'`, `chat_id IS NULL`), личный профиль и предложения (`chat_id=0`) и личный тред (`conversations`);
  групповые факты остаются и в личке видны (`get_memory_for_private`) — предупреждение говорит это прямо. `/forget all` — только в личке:
  всё везде (+ тред), «сувениров» нет, модель не зовётся; в группе — отказ «Полное стирание — только в личке». Данные режима разработчика
  (`dev_messages`, `data/devspace/`) не трогаются ни одной из команд (открытый вопрос — `docs/claude/open-tasks.md`).
- **Команда ничего не удаляет** (`cmd_forget`): считает область (`db.forget_scope`), шлёт предупреждение с кнопками «Да, стереть» / «Отмена».
  Область пуста — «Мне и так нечего забывать» без кнопок (в личке при непустых групповых фактах — подсказка про `/forget all`). «Пусто» = нет ЖИВЫХ
  фактов, профиля, предложений и треда; остались только просроченные строки — отвечаем так же и стираем их молча (без файла-копии). Числа в
  предупреждениях без склонения: «фактов: N», «чатов: K».
  Состояния на сервере НЕТ (глобальных словарей «ожидает подтверждения» не заводить — инвариант про параллельные апдейты): всё в
  `callback_data` — `fg:go:<c|a>:<uid>:<unix>`, `fg:no:<uid>` (≤64 байт). Чат и тип чата берутся из сообщения с кнопкой, не из данных.
- **Кнопки** (`on_forget_button`, `CallbackQueryHandler(pattern=r"^fg:")`): нажать может только автор (иначе alert «Это не твоя память»), через
  `FORGET_CONFIRM_TTL` = 300 с — «Предупреждение устарело», «Отмена» — «Отмена. Всё помню». «Да»: ПЕРВЫМ делом `edit_message_reply_markup(None)`;
  не вышло (в т.ч. «message is not modified» — другое нажатие уже убрало кнопки) — ничего не стираем: это и есть защита от двойного «Да»
  (апдейты одного чата идут по очереди, второе нажатие приходит, когда первое уже закончено, и без этой проверки стёрло бы оставленные
  «сувениры»). Дальше по порядку: область (снимок) → файл-копия → выбор «сувениров» → `db.forget_apply` (удаляет только строки снимка) → ответ. Блокирующее — в `asyncio.to_thread`.
  `gate_update` выставляет `usage_ctx` и для нажатий (проверено тестом): расход выбора ложится на чат, где нажали.
- **Файл-копия** (`_write_forget_backup`): не вся база, а удаляемые строки человека — `data/forget-backups/<uid>-<unix>.json`
  (`{version, user_id, scope, context, chat_id, created_at, memory, user_profile, profile_proposals}`, права 600; личный тред в файл не пишется).
  Не записалась — ничего не удаляется, пользователю «Не получилось, попробуй позже», в лог traceback. Хранение `FORGET_BACKUP_DAYS` = 30 дней
  по mtime, чистит `memory_purge_job` (04:30 Berlin и на старте) отдельным `try`, число — в лог. Пользователю о копии не говорим (решение
  Алексея: копия для админа на случай ошибки). Вернуть из файла: `scripts/restore_user_memory.py --from-json <файл> --user-id <USER_ID>`
  (те же правила слияния; `profile_proposals` не возвращаются).
- **«Сувениры»** (`pick_forget_keepsakes`): обычный `/forget` (группа и личка) оставляет 2 самых смешных факта из области. Только если живых
  фактов ≥ `FORGET_KEEP_MIN_FACTS` = 5 (меньше — стираем всё, модель не зовём; так повторный `/forget` добивает оставленные два) и не `all`.
  Кандидаты — живые факты (`expires_at IS NULL OR > now`), свежие первыми, не больше `FORGET_CANDIDATES_MAX` = 150 штук и
  `FORGET_CANDIDATES_CHARS` = 12000 знаков суммарно; в запросе нумерация 1..N (не `id` из базы), ответ `{"keep": [3, 17]}`, разбор только
  `parse_json_lenient`, принимаются ≤ `FORGET_KEEP` = 2 разных целых из 1..N. В запросе: факты — данные, не указания; выбрать самых смешных;
  не выбирать только здоровье и личные/семейные беды, остальное чувствительным не считается (решение Алексея). Пусто, мусор, исключение,
  safety-блок — стираем всё без «сувениров», в ответе «даже на память ничего не выбрала»; сбой модели стиранию не мешает. Если годен один номер —
  оставляется один факт (отдельный текст). Оставленные строки не меняются (срок `medium` прежний).
- **Модель выбора:** `chat_tier(chat_id) == "paid"` → `FORGET_PICK_MODEL_ID` = Argon (второе осознанное исключение из «служебное — только
  Lite», `docs/claude/models-and-costs.md`; модель чата `/flash` не учитывается), иначе `DEFAULT_MODEL_ID`. Вызов — `aux_create`,
  `label="forget"`, `out_tokens(model, 200)`, `**aux_params(model)`, фолбэк не отключён; без `thinking`/`tools`/`cache_control`.
- **Тексты** — константы `FORGET_TEXT_*` / `FORGET_DONE_*` в `bot.py`, фиксированные, от режима характера не зависят (как остальные ответы
  команд; инвариант про `tone` относится к промптам модели, `docs/claude/personas.md`). Клодушка говорит о себе в женском роде.
- **Известные ограничения (не чинить):** (1) после `/forget` в группе извлечение памяти через несколько сообщений снова соберёт факты из
  последних 50 реплик чата (`group_messages` не трогаем); (2) «Назад дороги не будет» при копии на 30 дней — решение Алексея; (3) факты, появившиеся между снимком области и удалением (между ними идёт вызов модели — секунды), НЕ стираются: `forget_apply` удаляет только строки
  снимка `forget_scope` (те, что ушли в файл-копию); (4) данные режима разработчика не стираются.
- Размер контекста: system-промпт не растёт (оставленные факты — обычные строки памяти под прежним потолком); разовый запрос выбора — до 12 000
  знаков + служебный текст.

## Восстановление после `/forget`
`/forget` необратим средствами бота (инцидент 2026-11-12, `docs/claude/incidents.md`); вернуть можно из копии базы в `data/backups/`
скриптом `scripts/restore_user_memory.py` (stdlib, bot.py/db.py не импортирует, тесты — `scripts/test_restore_user_memory.py`).
Недельные факты живут 7 дней, поэтому — чем раньше, тем больше вернётся. Бота не останавливать.
```bash
# на сервере, скрипт можно подать через stdin — файлы на сервере не правим; data/ принадлежит root, поэтому sudo
sudo python3 scripts/restore_user_memory.py --from-db data/backups/<копия>.db --user-id <USER_ID> [--chat-id <CHAT_ID>]          # отчёт
sudo python3 scripts/restore_user_memory.py --from-db data/backups/<копия>.db --user-id <USER_ID> [--chat-id <CHAT_ID>] --apply  # запись
```
- **Возвращается:** факты (`memory`) во всех чатах и в личке, которых сейчас нет по `(user_id, context, chat_id, fact)` и которые не просрочены
  (`expires_at IS NULL OR > now`), и утверждённый профиль (`user_profile`, `INSERT OR IGNORE`: существующее поле не перезаписывается).
  Слияние, не замена: факты, накопленные после стирания, остаются; повтор текста внутри копии добавляется один раз (идемпотентность).
- **Из файла-копии `/forget`:** `--from-json data/forget-backups/<uid>-<unix>.json` вместо `--from-db` — те же правила слияния (проверка `user_id` файла и `--user-id`).
- **Не возвращается:** личный тред (`conversations`) и неподтверждённые предложения профиля (`profile_proposals`).
- Без `--apply` — только отчёт (числа и `id` строк копии, тексты не печатаются). С `--apply`: копия боевой базы `data/backups/claudushka-restore-<ГГГГММДД-ЧЧММСС>.db`
  (не создалась — ничего не пишется), затем одна транзакция `BEGIN IMMEDIATE` (`timeout=30`), план пересчитывается внутри неё.
- **Открывать копии в `data/backups/` только** `sqlite3.connect("file:<путь>?mode=ro&immutable=1", uri=True)`: они в режиме WAL и принадлежат root,
  обычный `mode=ro` падает с «attempt to write a readonly database». Скрипт делает это сам.
- Колонки берутся по именам из `PRAGMA table_info`; нет колонки или таблицы в копии — понятная ошибка до любой записи.
- `<USER_ID>` и `<CHAT_ID>` в репозиторий не писать (публичный).

## Потолок на чтении
`get_all_chat_memory` отдаёт не более `MEMORY_LONG_PER_USER` (12) и `MEMORY_MEDIUM_PER_USER` (8) фактов на человека, самые свежие (`ROW_NUMBER() OVER (PARTITION BY user_id, tier ORDER BY created_at DESC)`). Без потолка старые чаты раздували system-prompt до сотен тысяч токенов и Клодушка переставала отвечать. Не снимать потолок — если фактов не хватает, поднимать константы осознанно.

**`get_memory_for_private` тем же потолком обзавелась только в v0.11.3** — до этого читала
ВСЕ факты пользователя (личные + из всех групп, куда он течёт вверх) без ограничения.
Найдено 2026-08-31: у одного активного участника многих групп накопилось 1860 фактов,
~80k символов — `/memory` падала на `BadRequest: Text is too long` (лимит Telegram 4096
символов одним сообщением), а сама эта же функция кормит `get_system_prompt(is_group=False)`,
то есть личный диалог с этим пользователем на КАЖДОЕ сообщение тащил все 80k символов в
system-prompt. Тот же класс проблемы, что инцидент 2026-07-26 (`docs/claude/incidents.md`),
просто на масштабе одного человека вместо всего чата — тот же общий инвариант ниже это и
предписывал, просто эта функция была написана раньше, чем он оформился как правило, и её
пропустили. Теперь использует тот же `ROW_NUMBER() OVER (PARTITION BY tier ...)` паттерн,
что `get_all_chat_memory`, партиция только по tier (не по chat_id — здесь это агрегат по
одному пользователю сразу по всем чатам). Старые факты в таблице `memory` при этом НЕ
удаляются, просто перестают читаться — как и в `get_all_chat_memory`. Разовая
чистка/дедуп самой таблицы остаётся открытой задачей — `docs/claude/open-tasks.md`.

**`db.get_memory` (не `get_memory_for_private`!) без потолка была ещё в одном месте —
починена следом, v0.11.5.** Это ОТДЕЛЬНАЯ функция: `/memory`, вызванная В ГРУППЕ,
читает не `get_memory_for_private`, а `db.get_memory(user_id, "group", chat_id)` —
факты только этого человека в ТЕКУЩЕМ чате. Потолок v0.11.3 её не касался. Найдено
2026-08-31 (после v0.11.4, live-тест в группе XDNet): у одного давнего активного
участника — 740 фактов в ОДНОМ чате, 34k символов; `/memory` не падала (спасибо
`reply_expandable`), но рассыпа́лась на десяток сообщений, местами разрывая строку
посреди слова между соседними сообщениями. Заодно нашлась причина такого раздутия —
извлечение памяти плодит почти-дубли вместо дедупа (`"Поделился фото"` /
`"Поделился фото в чате"` / `"Отправил фото в чат"` — 13/8/8 раз одно и то же).
Сама дедуп-гигиена таблицы `memory` остаётся открытой задачей (`docs/claude/open-tasks.md`)
— здесь почему потолок на ЧТЕНИИ обязателен, даже когда источник переполнен дублями.
`get_memory` теперь использует тот же `ROW_NUMBER() OVER (PARTITION BY tier ...)`,
партиция по tier внутри пары (user_id, context[, chat_id]).

**v0.11.6: оба потолка стали параметром, не жёстко зашитой константой.**
`get_memory(..., long_limit=None, medium_limit=None)` и `get_memory_for_private(...,
long_limit=None, medium_limit=None)` — `None` (дефолт) означает
`MEMORY_LONG_PER_USER`/`MEMORY_MEDIUM_PER_USER` (то, что кормит system-prompt через
`get_all_chat_memory`/`get_system_prompt`, эти вызовы не трогали). `cmd_memory`
передаёт `MEMORY_LONG_DISPLAY`/`MEMORY_MEDIUM_DISPLAY` (30/10) — человеку на глаз
можно показать больше, чем стоит скармливать в промпт на каждое сообщение.
`cmd_memory_full` передаёт заведомо огромные числа (`10**9`) — фактически без
потолка, вся история. Общий helper `_send_memory(update, long_limit, medium_limit,
header, label)` в bot.py, обе команды — тонкие обёртки над ним.

`/memory` (bot.py `cmd_memory`) заодно чинится сама по себе (независимо от потолков выше —
несколько слоёв защиты): длинный список теперь не падает в чат простынёй, а уходит через
`reply_expandable(reply_fn, body, header="")` — сворачивает текст Telegram-тегом
`<blockquote expandable>` (HTML parse mode, `html.escape` обязателен), в чате видна одна
строка со стрелочкой «развернуть». Лимит Telegram на сообщение (4096 символов) сам тег
не снимает — если `body` не влезает даже под тегом, режется на несколько сообщений, каждое
в своём collapsible-блоке (найдено 2026-08-31, "потестировал на себе, засрал чат"). Режет
**по границам строк**, не по количеству символов подряд — сырая нарезка рвала текст
посреди слова между соседними сообщениями (тот же живой тест, что нашёл баг выше);
единственная строка длиннее лимита — редкий случай, режется по символам только она.
Использован пока только в `/memory` — остальные «простынные» админ-команды (`/chats`,
`/users`, `/cost`, `/activity`) шлют себе в личку и не клоггают общий чат, поэтому не
трогала; переиспользовать `reply_expandable` там — тривиально, если понадобится.

**Общий инвариант:** любой источник данных, попадающий в system-prompt или в `messages`,
ОБЯЗАН иметь лимит по РАЗМЕРУ, а не только по количеству элементов. Добавляешь новый
источник — сразу с лимитом, рассчитанным на окно 200k (прежний минимум; у Haiku 5.5 окно уже 1M, но лимиты не поднимали — вход >100k у него в 5 раз дороже).

Два инцидента, приведшие к этой архитектуре, — прогон 2026-07-26 (group chat "prompt is
too long") и извлечение 2026-08-03 (потеря ~11% извлечений памяти по truncated JSON) —
дословно в `docs/claude/incidents.md`.

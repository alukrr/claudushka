# Safety-блок провайдера: повтор без истории, скан и скрытие строки (v2.1.0)

ТЗ — `docs/claude/tz-safety-unblock.md`; чек-лист стенда — `docs/claude/staging-checklist-safety-unblock.md`; инциденты —
`docs/claude/incidents.md` (2026-10-30, 2026-10-31).

## Проблема

Пул отвечает `400 blocked by provider safety policy` (`api_errors.is_safety_block`), если в ЗАПРОСЕ есть текст, который режет
фильтр провайдера. Запрос диалога в группе несёт окно истории (`build_group_messages`, 50 реплик), поэтому ОДНА «плохая» строка
`group_messages` блокирует весь чат на любой вопрос, пока не уйдёт из окна. Виновником бывает любая строка: обзор «Вестник»
(2026-10-30), кусок реплики Клодушки, вставленный участниками (2026-10-31).

## Часть A — повтор без истории (`_dialog_call`)

Основной вызов диалога (`handle_message`) идёт через `_dialog_call`, а не напрямую через `call_claude`:

1. Полный запрос. Успех → счётчик блокировок группы `_safety_strikes[chat]` = 0.
2. `is_safety_block` → счётчик +1 (только группа), затем ОДИН повтор БЕЗ истории: группа — только последний user-turn
   (`base_messages[-1]`: реплики людей подряд, включая триггер и inline-reply), личка — только `user_text`; system тот же (с памятью),
   служебный блок и `mark_cache_tail` — через `compose`. Метка `usage_log` — `dialog`.
3. Повтор прошёл → ответ уходит как обычно, пользователь ничего не замечает. Счётчик успехом повтора НЕ сбрасывается.
4. Повтор тоже `is_safety_block` → исключение наверх, `reply_api_error` («Фильтр модели заблокировал запрос…»): виновата память,
   system или сама реплика-триггер. Память чистит админ руками (`/memory_full`, `/forget`).

Не затронуто: фото и файлы (`label=f"фото …"`, `f"файл …"`) — у них прежнее поведение.

Лог: `SAFETY BLOCK chat=… uid=… model=… | повтор без истории: ok|blocked`. Текст сообщений в лог НЕ пишется.

## Часть B — фоновый скан и скрытие (`safety_scan`)

- `group_messages.hidden INTEGER NOT NULL DEFAULT 0` (миграция в `init_db`). `hidden=1` — строка не уходит НИ В ОДИН промпт, но
  физически остаётся: обратимо. Фильтр `hidden = 0` стоит во всех трёх чтениях, которые идут в модель: `get_group_transcript`
  (диалог и извлечение памяти группы), `get_group_messages_range` (дневной обзор и `/review`), `get_group_history`.
  Новое чтение `group_messages` в промпт — обязано фильтровать `hidden = 0`. Чтения «не для модели» (атрибуция `sender_name → user_id`,
  каденс `chat_extract_state`, счётчики) скрытые строки видят.
- **Когда запускается.** Счётчик в памяти процесса: `SAFETY_SCAN_STRIKES` (2) блокировок ПОЛНОГО запроса подряд → фоновая
  задача через `_spawn_background_task`, если скан этого чата не идёт и с прошлого прошло ≥ `SAFETY_SCAN_COOLDOWN_MIN` (30) мин.
  После запуска счётчик = 0. Вручную — `/safety_scan` (мимо счётчика и паузы, но не параллельно).
- **Алгоритм** (`_safety_scan_inner`, `safety_find`). Пробы — НАСТОЯЩИЙ запрос диалога, собранный кодом бота (`build_system` +
  `build_group_messages` + `service_block` + `mark_cache_tail`), вызов — `_model_call` с `usage_label="safety_scan"`,
  `fallback=False`, `max_tokens=out_tokens(model, 32)`. Фильтр флакает → до `SAFETY_SCAN_ATTEMPTS` (2) попыток на пробу,
  «заблокировано» = хоть одна заблокирована.
  1. `probe(∅)` — воспроизвелось? Нет → конец (авто-скан молчит, ручной отвечает «не воспроизвёлся»).
  2. `probe(всё окно)` — окно пустое, остаются память/system. Блок есть → виновата не история, отчёт «смотреть руками».
  3. `safety_find` — поиск минимального набора через ИСКЛЮЧЕНИЕ половин (ловит комбинации и несколько копий в разных половинах).
  4. Набор расширяется точными дублями `content` (до 20), финальная проверка `probe(набор, shift=True)` — окно сдвигается на старые
     строки, как после реального скрытия; заблокировано → НЕ скрывать, отчёт с подозреваемыми id.
  5. `db.hide_group_messages` + `notify_admins`: id, автор, время Berlin, длина, число вызовов. **Текст строк не выводится нигде**
     (разбор инцидентов идёт в сессиях Claude Code — текст может оборвать сессию).
- **Окно проб.** Живой диалог берёт окно через `pick_history_window` (якорь шагами, `HISTORY_STEP`). Пробы идут мимо него
  (`exclude_ids`/`min_id` в `build_group_messages`): якорь живого диалога не трогается. Поиск — БЕЗ сдвига (`min_id` = начало
  живого окна, исключённые строки просто выпадают: ищем в том окне, которое реально ломает чат); финальная проверка — со сдвигом.
- **Бюджет.** `SAFETY_SCAN_MAX_CALLS` (40) вызовов API на скан (считается каждая попытка); исчерпан → отчёт «бюджет исчерпан»,
  подозреваемые не скрываются. Расход пишется на чат (`usage_ctx`), метка `safety_scan` в `/cost`.
- **Ничего не удаляется**, память/профиль/`conversations` скан не трогает, в чат ничего не пишется.

## Команды (admin-only)

- `/hidden [chat_id]` — скрытые строки чата (id, автор, время, длина; без текста). В личке `chat_id` обязателен.
- `/unhide [chat_id] <id>` — вернуть строку в промпты. В группе `chat_id` не нужен.
- `/safety_scan [chat_id]` — запустить скан вручную; итог — админам в личку.

## Env

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `SAFETY_SCAN_STRIKES` | 2 | блокировок полного запроса подряд до автоскана |
| `SAFETY_SCAN_COOLDOWN_MIN` | 30 | пауза между сканами одного чата |
| `SAFETY_SCAN_ATTEMPTS` | 2 | попыток на одну пробу |
| `SAFETY_SCAN_MAX_CALLS` | 40 | бюджет вызовов API на скан |
| `SAFETY_TEST_MARKER` | пусто | ТОЛЬКО стенд: строка в тексте `messages` запроса → вызов ведёт себя как safety-блок. В проде не задавать |

Изменение env — только `docker compose up -d --force-recreate` (не `restart`).

## Грабли

- Проверять только настоящий запрос бота. Упрощённый «последние N строк» в транскрипт давал противоречивые результаты: фильтр на
  пороге, а окно бота другое (инцидент 2026-10-31).
- В счётчике блокировок учитывается ПЕРВЫЙ (полный) запрос, а не повтор — иначе успешный повтор обнулял бы признак проблемы.
  Счётчик живёт в памяти процесса: рестарт обнуляет, это нормально (блокировки повторятся, скан запустится заново).
- При `PROMPT_CACHE=1` пробы несут `cache_control`; `call_claude` снимает его сам (`kwargs_for_model`) — прямой
  `client.messages.create` в пробах не использовать (сломается 400 на `cache_control` и не будет учёта расхода).
- Скрытая строка остаётся в `group_messages` и вытесняется обычной подрезкой `GROUP_MESSAGES_KEEP`.
- Контекст: промпт не растёт — скрытие его только уменьшает; повтор без истории короче основного запроса. Единственная добавка к
  расходу — вызовы скана (до 40 коротких запросов, `max_tokens` ≈ запас на рассуждения) и повтор диалога без истории.

## Не сделано

- Фото и файлы (`label=f"фото …"`, `f"файл …"`) без повтора без истории.
- Скан только для групп; блок в личке чинится повтором без истории и ничего не скрывает.
- Текст обзора «Вестник» по-прежнему кладётся в `group_messages` целиком (идея с короткой пометкой — `open-tasks.md`).

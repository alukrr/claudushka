## Часть А. Отдельный характер обзора

### Проблема
Обзор (ежедневный `daily_chat_review` и разовый `/review`) берёт подачу из режима характера чата:
`_review_system(chat_id)` → `persona_review_style(chat_id)` → `PERSONAS[get_chat_persona(chat_id)]`. Алексей хочет,
чтобы в чате было, например, общение `classic`, а обзор — `toxic`.

### Что сделать
1. **БД** (`db.py`, `init_db()`): новая таблица по образцу `chat_persona`
   ```sql
   CREATE TABLE IF NOT EXISTS chat_review_persona (chat_id INTEGER PRIMARY KEY, persona TEXT NOT NULL);
   ```
   Функции рядом с `get_chat_persona_db`/`set_chat_persona_db`: `get_review_persona_db(chat_id) -> str | None`,
   `set_review_persona_db(chat_id, persona)`, `clear_review_persona_db(chat_id)`. Нет строки = «как у чата».
   Миграций данных нет. В `.claude/rules/db.md` — строка в список таблиц со ссылкой на `docs/claude/personas.md`.
2. **bot.py**, рядом с `persona_review_style`:
   - `get_review_persona(chat_id) -> str`: строка есть и ключ в `PERSONAS` → он; ключ неизвестен → `logger.warning` и
     режим чата (БД не трогать, как в `get_chat_persona`); строки нет → `get_chat_persona(chat_id)`.
   - `persona_review_style(chat_id)` берёт `PERSONAS[get_review_persona(chat_id)]` (fallback на `tone`, как сейчас).
   - Подпись в `_review_system` «(режим характера чата)» → «(режим характера обзора)».
   - Обзор в free и так не шлётся — тарифной логики в `get_review_persona` нет.
3. **Команда `/review_persona [ключ|off] [chat_id]`** (по образцу разбора аргументов `/searchmode [mode] [chat_id]`,
   а прав — `_set_persona`):
   - без аргументов — показать: «Обзор для <чат>: <label> (отдельный режим | как у чата — <label>)» и список ключей
     `PERSONAS` с пометкой ▸ у действующего, плюс подсказка формата.
   - `ключ` (`classic|business|toxic|flirt|granny` — брать из `PERSONAS`, не хардкодить) → `set_review_persona_db`;
     `off` → `clear_review_persona_db` («обзор снова в характере чата»). Неизвестный ключ → подсказка со списком.
   - Только группы: в личке без `chat_id` → «Обзор бывает только в групповых чатах». `chat_id` вторым аргументом —
     только админ бота (иначе отказ, как в `_parse_target_chat`).
   - В группе менять могут админы чата и админы бота (`is_chat_admin`); смотреть (без аргументов) — все.
   - Free: не-админу бота — отказ «обзор — платная функция, баланс — /cost»; админ бота может записать
     («включится после пополнения») — как в `_set_persona`.
   - Регистрация в `main()` (CommandHandler) и в списке команд меню, если он там есть (см. как добавлены `personas`,
     `searchmode`).
4. **`/personas`** в группе: добавить строку «Обзор: <label> (отдельный | как у чата). /review_persona».

## Часть Б. Мелочи обзора из ту-ду

### Б1. В историю диалога — не полный текст обзора
**Сейчас** обе ветки (`daily_chat_review` и `cmd_review`) пишут в `group_messages`
`f"{_review_sent_note(len(entries))}\n{review}"` — обзор целиком (2–3 тыс. знаков). Он попадает в окно истории
диалога и в извлечение памяти. Инцидент 2026-10-30: токсичный обзор «Вестник» целиком в промпте → safety-фильтр
провайдера резал ВСЕ ответы в чате. С v2.1.0 есть самовосстановление (повтор без истории, скан и скрытие строки), но
корень — полный текст в истории — остался.
**Ограничение с другой стороны** — инцидент 2026-10-22: если модель совсем не видит обзор в истории, она на
претензии «признаётся», что всё выдумала. Поэтому не «только пометка», а **пометка + темы**:
1. Чистая функция `_review_history_text(n_human: int, review: str) -> str`:
   `_review_sent_note(n_human)` + перевод строки + «Темы обзора (полный текст в истории не хранится; он в самом
   сообщении в чате): » + заголовки через «; ».
   - Заголовок = первая непустая строка каждого абзаца (абзацы разделены пустой строкой), без ведущих эмодзи/
     пунктуации, обрезана до `REVIEW_HISTORY_TITLE_CHARS` = 80 символов (с «…»). Последний абзац (итоговая
     фраза-афоризм) не включать, если абзацев больше двух.
   - Весь результат — не длиннее `REVIEW_HISTORY_MAX_CHARS` = 800 символов (инвариант «лимит по размеру»).
   - Префикс `(обзор дня по` (`REVIEW_SENT_LABEL`) обязан остаться в начале — по нему `build_review_log`
     выкидывает прошлый обзор из лога следующего обзора. `_review_sent_note` и `REVIEW_SENT_LABEL` не менять (на
     `_review_sent_note('N')` ссылается system-prompt; изменение = переписанный кэш у всех чатов).
2. Оба места записи (`daily_chat_review`, `cmd_review`) — через `_review_history_text`. Отправка в Telegram —
   без изменений (люди видят полный обзор, как раньше).
3. Уже лежащие в БД старые обзоры не переписывать.
4. Для справки: reply на сообщение обзора по-прежнему даст модели цитату до 500 символов (`_bot_reply_quote`,
   v2.1.1) — так человек может спросить про конкретный кусок.

### Б2. N в пометке — только реплики людей
`_review_sent_note(len(entries))` считает и реплики бота. Передавать `human` (второе значение
`collect_review_entries`) — в обоих местах.

# ТЗ: режим разработчика в платной личке (ветка `feat/dev-mode`)

Статус: реализовано в ветке `feat/dev-mode` (2026-10-26), описание реализованного — `dev-mode.md`; на стенде не прогнано.
Отступления от ТЗ при реализации — в `dev-mode.md` (незакрытый `[[FILE]]` не пишется в workspace; пропуск не влезшего файла с попыткой следующих; реакции 👀/✍ не ставятся).

Зачем: часть пользователей (первый — Пётр) пишет с Клодушкой код. Болталка для этого
не годится: файл режется до 8000 символов, история файлы не помнит, каждый файл из
альбома обрабатывается отдельно, мешают персона и память. Делать из болталки
инструмент для кода Алексей не хочет: это распыляет приоритеты. Поэтому — отдельный
изолированный режим. Весь новый код сидит за одним флагом, для остальных чатов и для
этой же лички вне режима ничего не меняется.

## 0. Решения Алексея (2026-10-26)

1. Тред отдельный, свои таблицы. С обычной историей лички не смешивается.
2. Только личка. Групп режим не касается вообще.
3. Несколько файлов одной отправкой (альбом) склеиваются в один запрос — входит в v1.
4. Маркер `[[FILE: имя]]` остаётся. Персоны, рисование, память и профиль в режиме выключены.
   Видимый ответ — до 16k токенов.
5. Устройство хранения и истории Алексей оставил на усмотрение Claude. Решения ниже, раздел 2.

## 1. Включение и тариф

- Команда `/dev` — статус и включение. `/dev off` — выключить. `/dev reset` — очистить тред режима, файлы остаются.
  Название команды — предложение, Алексей может поменять.
- Работает только в личке (`chat_id == user_id`) и только если `chat_tier(user_id) == "paid"`.
  В группе и в free — короткое объяснение, флаг не ставится.
- Флаг хранится в БД: `dev_mode(user_id INTEGER PRIMARY KEY, enabled INTEGER NOT NULL, updated_ts INTEGER)`.
- Если чат ушёл в free при включённом флаге — режим считается выключенным (флаг и данные не трогать).
  При возврате в paid режим снова активен. Тот же принцип, что у `chat_models` в free.
- Единственная точка проверки: `dev_mode_active(user_id) -> bool` (личка + paid + флаг).

## 2. Workspace: файлы отдельно от истории

Главная идея. Файл — это СОСТОЯНИЕ, а не реплика. В истории хранится только пометка
«загружен/обновлён файл X», содержимое лежит в workspace в одном экземпляре (последняя версия).
Поэтому история не раздувается, и пять правок одного файла не дают пяти копий в контексте.

**Где лежит:** `data/devspace/<user_id>/<имя>` — плоская папка, без поддиректорий.
Решено НЕ заводить отдельный volume (идея Алексея): `./data` уже смонтирован в `/app/data`
у обоих сервисов. Значит, не нужны правка `docker-compose.yml` и `--force-recreate` при выкатке.
Если Алексей всё же хочет отдельный volume — это одна строка в compose плюс recreate, остальное ТЗ не меняется.
Источник правды — файловая система. Отдельной таблицы метаданных нет, листинг через `os.scandir`
(имя, размер, mtime, число строк).

**Что попадает в workspace:**
- Файл от пользователя (документ), если он декодируется как СТРОГИЙ UTF-8 (`errors="strict"`).
  В режиме принимается любое расширение, бинарное отклоняется с причиной. Список `text_exts`
  обычной ветки здесь не нужен.
- Файл от модели через `[[FILE: имя]]` — сохраняется в workspace и, как сейчас, отправляется документом.
- То же имя — перезапись (новая версия). Старые версии в v1 не храним.
- Санация имени — существующая `_safe_filename`.

**Лимиты** (env, стартовые значения — предположение, откалибровать на стенде):

| константа | старт | смысл |
|---|---|---|
| `DEV_FILE_MAX_BYTES` | 300_000 | один файл (как `FILE_MAX_BYTES`) |
| `DEV_WS_MAX_FILES` | 50 | файлов в workspace |
| `DEV_WS_MAX_BYTES` | 5_000_000 | всего на диске на пользователя |
| `DEV_CTX_FILES_CHARS` | 150_000 | сколько символов файлов уходит модели в одном запросе |
| `DEV_HISTORY_CHARS` | 40_000 | потолок окна истории режима |
| `DEV_OUT_TOKENS` | 16_000 | видимый ответ, в `out_tokens(model, ...)` |
| `DEV_FILES_PER_REPLY` | 5 | файлов в одном ответе модели (в обычной ветке 3) |
| `DEV_ALBUM_WAIT_SEC` | 2.0 | ожидание остальных файлов альбома |

При превышении `DEV_WS_MAX_*` новый файл не сохраняется, пользователь получает понятное
сообщение со ссылкой на `/ws rm`. Молча старое не удаляем.

**Команды workspace** (только в активном режиме):
- `/ws` — список: имя, размер, строки, «в контексте / не влез».
- `/ws get <имя>` — прислать файл документом.
- `/ws rm <имя>` — удалить один файл.
- `/ws clear yes` — удалить все файлы (без `yes` — только предупреждение).

## 3. Сборка запроса

```
system = [
  DEV_PROMPT            # статичный текст, cache_control (как блок персоны)
  WORKSPACE_BLOCK       # манифест + содержимое файлов, cache_control (как блок памяти)
]
messages = dev-история (окно)  +  последний user-turn с service_block()
```

- `DEV_PROMPT` — короткий и нейтральный, без `CORE_IDENTITY`, персоны, `_core_rules`, памяти, профиля.
  Содержит:
  - ты Claude, помогаешь писать код через Telegram;
  - как устроен workspace;
  - правило `[[FILE: имя]]`: всегда полный файл, то же имя = новая версия;
  - честность: не выдумывать функции и API, говорить о неуверенности;
  - что такое служебный блок в хвосте;
  - ограничения разметки Telegram.
  Текст байт-в-байт стабилен.
- `WORKSPACE_BLOCK`:
  - манифест ВСЕХ файлов (имя, строки, размер, время изменения);
  - полное содержимое файлов в порядке «самые свежие первыми», пока не исчерпан `DEV_CTX_FILES_CHARS`;
  - файлы, которые не влезли, — только в манифесте с пометкой «не загружен в контекст (лимит)»,
    модель может попросить пользователя убрать лишнее.
  Порядок детерминированный (mtime, затем имя), чтобы при неизменном workspace блок был байт-в-байт тот же и кэш попадал.
- **Сознательное отступление от инварианта «system статичен».** Workspace меняется чаще памяти, но так же
  чат-специфичен и меняется только при изменении файлов, не на каждой реплике. Кладём в system отдельным
  блоком по аналогии с памятью. Время, поиск, reply-контекст — по-прежнему только в `service_block`.
- Окно истории — `pick_history_window` шагами, как в личке, плюс жёсткий потолок `DEV_HISTORY_CHARS`
  (обрезаем старые реплики целиком, начало окна — с `user`). Лимит по размеру выполняет инвариант
  из CLAUDE.md и инцидента 2026-07-26.
- Модель — `get_chat_model(user_id)` с `**dialog_params(model)` и `out_tokens(model, DEV_OUT_TOKENS)`.
  Вызов — только через `call_claude` (фолбэк на Gemini работает как везде: `cache_control` обёртка
  не передаёт). `label=f"dev chat={user_id}"`, `usage_label="dev"`, чтобы режим был виден в `/cost`
  отдельной строкой. При реализации проверить, что `/cost` корректно показывает новый `usage_label`.
- Аварийная ветка `400 prompt is too long`: пересобрать без содержимого файлов (только манифест)
  и сказать пользователю, что workspace не влез.

## 4. История режима

Таблица `dev_messages(id INTEGER PRIMARY KEY AUTOINCREMENT, user_id INTEGER NOT NULL, role TEXT NOT NULL, content TEXT NOT NULL, ts INTEGER NOT NULL)`
плюс индекс по `(user_id, id)`.

Что пишется:
- **user, текст** — как есть.
- **user, файл(ы)** — `[Загружены в workspace: a.py (120 строк), b.py (40 строк)] <подпись>`.
- **assistant** — текст ответа. Каждый `[[FILE]]`-блок вырезан и заменён на
  `(файл имя сохранён в workspace, N строк)`. Содержимое в историю не пишется, оно в workspace.
- **user, фото** — `[Скриншот] <подпись>`. Фото уходит модели в этом запросе, но не сохраняется.

`/dev reset` удаляет строки `dev_messages` пользователя. Обычную историю лички (`conversations`)
режим не читает и не пишет.

## 5. Обработчик

В начале `handle_message`, до любой обычной логики лички: `if not is_group and dev_mode_active(user_id): return await handle_dev_message(...)`.
Отдельная функция, обычный путь не трогается.

- **Текст** — запрос по разделу 3.
- **Документ без подписи** — сохранить в workspace, ответить `📎 a.py сохранён (120 строк)`, модель НЕ вызывать (бесплатно).
- **Документ с подписью** — сохранить и ответить моделью на подпись.
- **Альбом (`media_group_id`):**
  - каждый файл сохраняется сразу по приходу;
  - запрос к модели — один на альбом, через `DEV_ALBUM_WAIT_SEC` после последнего файла группы
    (таймер перезапускается на каждом новом файле, состояние в памяти процесса по `media_group_id`);
  - подписи всех файлов альбома склеиваются в один вопрос;
  - нет ни одной подписи — одно общее подтверждение со списком файлов, без вызова модели.
  - Проверить на стенде: в каких апдейтах альбома документов Telegram передаёт подпись.
  - Ожидание — только через `_spawn_background_task`, не голый `create_task`.
- **Фото** — vision-запрос в контексте режима (скриншот ошибки).
- **Голос, видео, GIF, стикеры** — v1: короткий ответ «в режиме разработчика — текст, файлы и фото, `/dev off` для обычного чата».
- **Выключено в режиме:** `extract_memory`, предложения профиля, DRAW-маркер, автопоиск.
  `/search` как команда работает как раньше, в v1 не адаптирован.
- Реакции 👀/✍ — как в обычной ветке.
- Ответ длиннее 4096 символов — режется как сейчас. Файлы отправляются через существующую логику `extract_files`
  с лимитом `DEV_FILES_PER_REPLY` (параметр, а не новая копия функции).

## 6. Учёт и доступ

- Все вызовы — через обёртки, в `usage_log` с `usage_label="dev"`. Новых путей мимо `_record_usage` нет.
- Opus/Fable-подтверждение и прочие правила `get_chat_model` — без изменений.
- Бан, unverify — работают как везде (`gate_update` раньше роутинга).
- Удаление данных: `db.clear_memory` / `/forget` для этого пользователя — НЕ трогают dev-данные. Это открытый вопрос
  к Алексею: должна ли полная очистка пользователя удалять и `dev_messages`, и `data/devspace/<user_id>`.

## 8. Стенд — обязателен

Новые таблицы и новый обработчик — по правилам проекта только через стенд. Минимум проверить:
1. free-личка: `/dev` отказывает, флаг не пишется.
2. paid-личка: `/dev`, файл без подписи → 📎 и в `usage_log` нет записи.
3. Альбом из 3 файлов с подписью на одном → один ответ модели, все три в workspace.
4. Альбом без подписей → одно подтверждение.
5. «Добавь функцию в a.py» → модель отдаёт полный файл, он перезаписан в workspace, в `dev_messages` пометка без содержимого.
6. Workspace больше `DEV_CTX_FILES_CHARS` → `/ws` показывает «не влез», запрос не падает.
7. Логи PROMPT: размер system и истории в пределах лимитов; повторный вопрос без изменения файлов → cache read.
8. `/dev off` → обычная болталка, персона на месте, dev-история в контекст не попала.
9. `/dev reset`, `/ws rm`, `/ws clear yes`.
10. Фолбэк на Gemini (принудительно) — ответ приходит, файлы сохраняются.
11. Перевод чата в free при включённом режиме → обычная болталка, данные целы.

## 9. Влияние на контекст и деньги

- На обычные чаты — нулевое: их сборка запроса не меняется.
- В режиме максимальный запрос — примерно `DEV_PROMPT` (~2k символов) + до 150k символов файлов + до 40k истории + вопрос.
  В токенах для кода это заметно больше, чем у обычной реплики болталки. Точное соотношение
  символы/токены и цену — замерить на стенде по логам `PROMPT` и `usage_log`, на глаз не оценивать.
- Повторные вопросы по тому же workspace в пределах TTL кэша должны читать файлы из кэша.
  После паузы дольше TTL — полная цена записи. Платит сам пользователь со своего баланса.

## 10. Не входит в v1

- Tool use (модель сама читает и пишет файлы через инструменты). Причины: цикл вызовов усложняет код,
  а при фолбэке на Gemini `tools` не передаются (инвариант model-fallback), то есть режим бы деградировал.
  При текущих размерах (файлы на десятки тысяч символов) «всё в контексте» достаточно.
- Подпапки, история версий и diff, ZIP-архивы, git.
- Выполнение кода — НЕ делать никогда (безопасность сервера).
- Группы, голос, видео.
- Адаптация `/search` и нативного поиска под режим.

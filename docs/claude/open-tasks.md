# Открытые задачи (не «известные баги», а запланированное)

- **Гигиена памяти**: дедуп фактов (`UNIQUE(user_id, context, chat_id, fact)` +
  `INSERT OR IGNORE`; индекс не создастся, пока в таблице есть дубликаты) и разовая
  чистка просроченных (`DELETE FROM memory WHERE expires_at IS NOT NULL AND expires_at <= now`,
  ~380k символов балласта). На размер промпта не влияет — просроченные и так фильтруются,
  а с v0.11.3–0.11.5 все три функции чтения памяти (`get_memory`, `get_memory_for_private`,
  `get_all_chat_memory`) капаются по `MEMORY_LONG_PER_USER`/`MEMORY_MEDIUM_PER_USER`, так
  что даже необузданный дубликат-мусор в таблице (2026-08-31: "Поделился фото" 13 раз,
  740 фактов на человека в одном чате) больше не раздувает system-prompt. Дедуп теперь
  вопрос КАЧЕСТВА 20 отдаваемых фактов (чтобы это были 20 РАЗНЫХ фактов, а не 13 вариаций
  одного и того же, вытесняющих из-под потолка что-то более информативное), не корректности.
  Подробнее про память — `docs/claude/memory.md`.
  **Инструмент для разовой ручной чистки — `dedup_memory.py`** (v0.11.6+, корень репо,
  НЕ часть бота, никем не импортируется): `--mode exact` убирает буквальные повторы без
  API, `--mode llm` просит модель объединить близкие по смыслу формулировки (стоит
  денег, один вызов на группу `user_id+context+chat_id+tier`, `max_tokens=8192` — на
  группах в сотни-тысячи фактов меньше не хватает, см. живой инцидент ниже). Фильтры
  `--user-id`/`--chat-id`/`--tier`, `--limit-groups N` (только llm — пробный прогон на
  части перед безлимитным), `-v`/`--verbose` (показывает сами факты — exact: кто чей
  дубль, llm: полный список «было»/«стало» на группу, не только счётчики — важно перед
  `--apply`, чтобы свериться, что модель ничего не потеряла/не выдумала). Дефолт —
  dry-run: читает со снимка во временном файле, sudo НЕ требует. `--apply` пишет в
  боевой файл напрямую — `data/` на сервере root:root, нужен `sudo` (для llm — `sudo -E`,
  прокинуть `ANTHROPIC_API_KEY`). `--model` принимает короткие имена
  (`haiku`/`sonnet`/`opus`/`fable`, а также `argon` = gemini-4-argon, `flash` = gemini-3.8-flash и `lite` = gemini-3.1-flash-lite (те же имена, что команды бота) —
  Gemini через пул, ВЫБОР ВРУЧНУЮ, не автофолбэк: дедуп меняет память, смена модели посреди прогона дала бы смесь;
  у Gemini `max_tokens` + запас 4000 на рассуждения, без thinking/output_config/cache_control, оценка цены
  приблизительная — `THINKING_EST`; реестр `MODEL_ALIASES` дублирует `MODELS` из bot.py,
  см. `docs/claude/models-and-costs.md`) или полную API-строку. По завершении llm-режима
  печатает время, токены (in/cache_write/cache_read/out по отдельности) и оценку
  стоимости по локальной табличке `PRICING` (тоже дубль `MODELS`, сверять при смене цен
  там) — а если был `--limit-groups`, ещё и грубую экстраполяцию на весь фильтр. Живой
  масштаб на 2026-08-31: 85k фактов в таблице, 264 группы с 2+ фактами; пробный прогон 5
  групп Sonnet'ом — 312с (~62с/группу), экстраполяция на все 264 группы — грубо ~4.5 часа.

  **У этого ключа/пула включено автоматическое prompt caching** — не только для
  системных промптов, для ЛЮБОГО достаточно большого входа. Для дедупа вход ВСЕГДА
  уникален (разные факты в каждой группе), значит это ВСЕГДА запись в кэш, никогда
  чтение — `usage.input_tokens` при этом почти пустой (единицы токенов), а реальный
  вес в `cache_creation_input_tokens`. Без учёта этого оценка стоимости занижалась
  примерно в 100 раз (проверено: 400 фактов, 40690 символов -> `input_tokens=2`,
  `cache_creation_input_tokens=16186`). Множители кэша (в `PRICING` скрипта — per-model, запись 5m/1h
  раздельно, синхронно с bot.py) это учитывают. Стоит держать в уме и за пределами этого скрипта — если где-то ещё в
  проекте появится любой достаточно большой одноразовый payload, `/cost` может так же
  недосчитывать, если сам не смотрит на `cache_creation_input_tokens` (см.
  `docs/claude/models-and-costs.md`).

  **Проще всего гонять `--mode llm` через `docker exec claudushka python3 /repo/...`**
  (`/repo` — примонтированный туда же корень репо) — внутри контейнера уже есть пакет
  `anthropic` (на голом хосте его нет, `pip install anthropic==1.7.0` либо так) и
  `ANTHROPIC_API_KEY` в окружении (не надо `source .env`), и процесс и так root
  (не надо `sudo`/`sudo -E`). `--help` в самом скрипте — там же все примеры.

  **TUI и безопасное применение (ветка `feat/dedup-tui`).** `dedup_memory.py` без `--mode`
  (или `--tui`) открывает curses-интерфейс `dedup_tui.py` (только stdlib, палитра на 8 цветах,
  мин. 80×24; `docker exec -it claudushka python3 /repo/dedup_memory.py`, без TTY — выход с
  кодом 2). Ядро (`run_llm`/`apply_results`/оценки) не печатает и не делает `sys.exit` —
  его же использует CLI. Что важно помнить:
  - **Обрезанный ответ (`stop_reason=max_tokens`) = статус `truncated`, группа не применяется
    никогда** (раньше удалялась вся группа и вставлялся огрызок — тихая потеря данных).
  - **Оценка без API**: `CHARS_PER_TOKEN=2.5` (одна точка замера), `OUT_RATIO=1.0` (верхняя
    граница), вход тарифицируется как запись кэша 5m. Время — только из калибровки
    `data/dedup_calibration.json` (обновляется после каждого реального прогона, per-model).
  - **Пробный прогон стоит денег** (вызывает API), в БД не пишет.
  - **Применение** = `apply_reviewed`: бэкап `data/backups/claudushka-dedup-<ts>.db`
    (`sqlite3.backup`, не создался — не пишем) -> для каждой группы своя транзакция с проверкой,
    что все `row_ids` снимка на месте (иначе группа пропущена); факты, добавленные после снимка,
    не трогаются. CLI `--apply` идёт тем же путём (бэкап до первого платного вызова).
  - Журнал каждого прогона (в т.ч. непримененного) — `data/dedup_runs/<ts>-<model>.json`;
    логи `api_errors` в TUI уходят в `data/dedup_tui.log` (stderr ломает экран curses).
  - **Калибровка накопительная** (суммы в `data/dedup_calibration.json`, коэффициенты — взвешенное
    среднее; старый формат без сумм при первом обновлении заменяется). Сброс — F7, `x`, либо
    удалить ключ модели из файла. Выбор, скрытый tier/context-фильтром, виден в шапке
    «(скрыто фильтром: N гр.)» и в диалогах прогона/применения.
  - **Запуск на проде — функция `dedup`** (`docs/claude/prod-aliases.sh`, подключить в `~/.bashrc`
    на сервере): без аргументов TUI, с аргументами — CLI; сама выбирает `-it`/`-i` по TTY.
  - **Построчная правка (v1.4.2).** В просмотре группы (`Enter` на результате) клавиша `e` — режим
    правки колонки «стало»: курсор ↑↓, `Tab` — колонка, `Enter`/`e` — строчный редактор (ввод через
    `get_wch`, кириллица; пустая строка = удалить), `a`/`Ins` — добавить, `d`/`Del` — удалить, `→` на
    колонке «было» — скопировать факт в «стало», `u` — отмена (стек на группу), `R` — сброс к ответу
    модели, `Esc` — выйти из правки (правки остаются в результате). `b` — скрыть/показать «было»
    (по умолчанию одна колонка, если окно уже 100; выбор пользователя не перебивается ресайзом и
    лежит в `data/dedup_tui.json`). Метка `✎` — правил человек (если глиф ломает ширину, заменить
    `EDIT_MARK` в `dedup_tui.py` на `*`). Пустое «стало» = группа неприменима (удалить все факты
    группы — только `--mode delete`). Дубли в «стало» подсвечиваются, не запрещаются.
  - **Ручная правка без модели**: `e` на строке группы в главном списке → `GroupResult` со статусом
    `manual` (`row_ids` всей группы из снимка, токены/деньги нулевые), применяется тем же
    `apply_results` (проверка `row_ids`, бэкап, `APPLY`). Без изменений — в применение не попадает.
    Если у группы уже был результат прогона — замена с подтверждением; новый прогон НЕ затирает
    результат с правками человека (ответ модели остаётся в журнале). Правка идёт внутри одной
    группы `(user, context, chat, tier)`, перенос long ↔ medium не поддерживается.
  - **Журнал правок**: при применении пишется `data/dedup_runs/<ts>-<model|manual>-reviewed.json`, при
    выходе без применения — `...-unapplied.json`: на группу `facts_before`, `facts_model` (ответ
    модели), `facts_after` (итог), `edited`, `status` (`manual` — без модели). В калибровку правки и
    `manual` не идут.
  - **Просроченные факты (v1.4.3, инцидент 2026-10-18 в `incidents.md`).** Бот сам удаляет просроченные
    `medium` (`memory_purge`, `docs/claude/memory.md`). dedup по умолчанию видит ТОЛЬКО живые строки
    (`--include-expired` — снять фильтр; TUI всегда живые); `--mode purge-expired` (dry-run считает, `--apply` —
    бэкап + удаление) и `x` в TUI удаляют просроченное сразу. При применении слитой medium-группы
    `expires_at` = МИНИМУМ живых сроков группы на момент записи (слитый факт не живёт дольше самого
    «старого» живого источника — какой слитый факт из каких строк, мы не знаем), если всё просрочено — группа
    пропускается («всё просрочено»). Выбор минимума, а не «отдельно хранить происхождение каждого факта» — дешевле
    и безопасно в худшую сторону (факт может протухнуть раньше, чем надо, но не воскреснет).
  - **Большие группы идут по частям.** Не влезает в один ответ (`estimate_group().risk`) → куски с оценочным
    выходом ≤ 60% `MAX_OUT_TOKENS` (`plan_chunks`), затем слияние (может потребовать ещё проход, до 3 уровней, иначе
    `truncated`). Один `GroupResult`: суммы токенов/стоимости/секунд, `chunks` (число кусков), `calls` (всего
    вызовов); любой обрезанный/упавший вызов → вся группа не применяется. Метка в TUI `÷N`, `ok 1160→85 (4 части +
    слияние)`. Такие группы НЕ идут в калибровку. ВНИМАНИЕ: без калибровки `OUT_RATIO=1.0` («ничего не слилось»)
    заставляет резать и группы, которые влезли бы одним вызовом (до ~200 фактов на кусок), и слияние тоже
    считается «не влезающим» → лишние проходы и деньги. Сделай пробный прогон малых групп (калибровка), потом
    большие.
    **Обрезка внутри кусков (2026-10-20, живой случай: 1304 уникальных long-факта, «ОБРЕЗАНО даже по частям»).**
    Оценка выхода занижена у фактов без повторов, поэтому реально обрезаться может и кусок. Теперь обрезанный вызов
    делится пополам и идёт заново (`call_split`, до 4 уровней подряд); провал СЛИЯНИЯ (обрезка/пусто), исчерпание
    `MAX_CHUNK_LEVELS` и «куски почти не сжались» (≥90% входа) больше не дают `truncated`: итогом остаются результаты
    кусков (каждый честно дедуплицирован, без межкусочной дедупликации). `truncated` — только если не удался кусок
    уровня 0, который уже нельзя делить (1 факт).
  - **Не платить дважды.** `previously_truncated`: последний прогон группы по журналу `data/dedup_runs/` —
    `truncated`, те же `row_ids` и то же число кусков (журналы до v1.4.3 без `chunks` — «без нарезки»; группа,
    которая теперь пойдёт по частям, НЕ блокируется) → в TUI статус «обрез.ранее» и диалог перед прогоном (Enter —
    пропустить, `f` — гнать, Esc — отмена), в CLI пропуск строкой, `--force-retry` — гнать.
  - Спорное решение: клавиши `n` (снять всё) и «следующее совпадение» разведены — совпадения
    листаются `N`/`P` или F3 при активном поиске. Не проверено живьём: терминал `xterm-256color`,
    реальный API-прогон (см. отчёт ветки).
  Живой прогон вскрыл и починил на месте: наивный `"".join(b.text for b in
  resp.content if hasattr(b, "text"))` падал на `NoneType` (thinking-блок пятого
  поколения без текста) — теперь `api_errors.response_text`/`parse_json_lenient`, те
  же хелперы, что у bot.py/whatsapp.py, не переизобретены заново (см.
  `docs/claude/api-errors.md`).
- **`chat_models` постоянна**: `/haiku` `/sonnet` `/opus` `/fable` пишут выбор навсегда,
  отката по таймеру нет. Решение об автооткате не принято; текущая модель видна в `/models`.
- **GPT через прокси**: другой API, нужен отдельный клиент и поле `provider` в реестре
  `MODELS`. Решение не принято.
- **whatsapp.py вне реестра**: свой хардкод `claude-sonnet-4-6`. Синхронизировать —
  только вынося `MODELS` в общий модуль (как сделали с `api_errors.py`).

- **`/update` оставляет root-овые файлы в репозитории на сервере** (2026-10-28). `cmd_update` → `_git("pull")` выполняется
  внутри контейнера от root (`.:/repo` в `docker-compose.yml`), поэтому каждый НОВЫЙ каталог/файл, пришедший через
  `/update`, на хосте принадлежит root. Следующий `git pull` от `alukr` на сервере падает: `unable to create file
  docs/claude/bench/...: Permission denied` (каталог `docs/claude/bench` создан в 19:33 UTC через `/update`), а прерванный
  checkout оставляет изменённые файлы → `-dirty`. Разовая починка: `sudo chown -R alukr:alukr docs .git`,
  `git checkout -- <файлы>`, `git pull`. Варианты исправления (выбирает Алексей): (1) после успешного pull в
  `cmd_update` вернуть владельца — `chown -R` на uid/gid владельца `/repo` (взять из `os.stat("/repo")`), без `data/`;
  (2) запускать git в контейнере от uid хоста (`user:` в compose — затронет весь сервис, `data/` и `pip install`
  в `command:`; рискованнее). Root-овые `__pycache__/*.pyc` в корне (дедуп через `docker exec`) git не мешают.

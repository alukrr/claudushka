# Дневной обзор чата (`daily_chat_review`, `/review`)

Перед правкой `daily_chat_review`, `cmd_review`, `/review_on`, `/review_off`,
`run_daily` — читай этот файл.

## Обзор за сутки с блоками тем (v1.10.0, ТЗ `docs/claude/tz-daily-review-topics.md`)
Разделы ниже («Три проблемы…», «Пометка… (v1.7.1)») — история прежней версии (последние 100 сообщений дня, 1000–1200
знаков); актуальное поведение — здесь. Чек-лист стенда — `docs/claude/staging-checklist-review-topics.md`.

**Окно.** `_review_window()` — с `DAILY_REVIEW_HOUR` (21:00) ВЧЕРА до запуска, по `BERLIN_TZ`, через дату (в ночь
перехода CET/CEST окно честно 23 или 25 часов). `db.get_group_messages_range(chat_id, since, until)` — все сообщения окна по
возрастанию, без LIMIT по числу. `collect_review_entries` → `build_review_log`:
- прошлый обзор (`is_bot` и текст начинается с `(` + `REVIEW_SENT_LABEL`) выкидывается — иначе Opus пересказывает
  вчерашнее (префикс `REVIEW_SENT_LABEL` менять нельзя — на нём фильтр; так же отфильтруются и старые `/review`);
- реплика человека режется до `REVIEW_USER_MSG_CHARS` (500), бота — до `REVIEW_BOT_MSG_CHARS` (200), с «…»;
- строка лога — `HH:MM Имя: текст` (Берлин), переводы строк в тексте заменяются пробелом;
- порог «мало сообщений» — `REVIEW_MIN_HUMAN_MSGS` (5) по НЕ-бот сообщениям.

**Хранение.** `db.GROUP_MESSAGES_KEEP` = 3000 строк на чат (было 1000): иначе в активном чате утро удалялось до обзора.

**Ветка A** — лог ≤ `REVIEW_SINGLE_MAX_CHARS` (60 000, env): весь лог одним сообщением в Opus («сначала про себя выдели темы»).
`REVIEW_SINGLE_MAX_CHARS=0` — всегда ветка B (переключатель без правки кода).

**Ветка B** — `split_review_sessions` (чистая функция): новая сессия при паузе ≥ `REVIEW_SESSION_GAP_MIN` (45 мин, по epoch —
переход CET/CEST не мешает), сессия длиннее `REVIEW_CHUNK_MAX_CHARS` (20 000) режется по границе сообщения. Каждая часть →
`aux_create(label="daily_review_chunk", model=DEFAULT_MODEL_ID, **aux_params())` (Haiku, до `REVIEW_CHUNK_PARALLEL`=4
параллельно), ответ — JSON `{"topics": [{title, from, to, participants, gist, moments, quotes}]}` через `parse_json_lenient`.
Упавшая/пустая часть пропускается (warning), обзор живёт; упали ВСЕ → обзор не шлётся. Итоговый вызов Opus получает JSON тем
(`_cap_topics`, лимит `REVIEW_TOPICS_MAX_CHARS` = 30 000: сначала режутся цитаты, потом моменты, потом хвост) + последние
`REVIEW_RAW_TAIL_MSGS` (40) сообщений сырьём под лимитом `REVIEW_RAW_TAIL_MAX_CHARS` (8000); соседние похожие темы
разных частей модель объединяет сама (сказано в промпте).

**Формат итога** (`_review_system`, общий для A, B и `/review`): вступление 1–3 предложения → 3–6 блоков тем (заголовок, когда,
кто, 2–4 предложения с подачей режима `persona_review_style`) → афоризм под ЭТОТ день (не заготовка про AI). Plain text,
эмодзи в начале блока допустимы. Ориентир 2000–3000 знаков, `max_tokens = out_tokens(model, 2200)`, `was_truncated` →
`trim_to_last_sentence`. Telegram 4096: `split_telegram_text(review, footer)` делит по границе абзаца, футер `/review_off` — в
последнем сообщении; в `group_messages` уходит один целый текст без футера.

**Пометка в транскрипте.** `_review_sent_note(N)` — «обзор дня по N сообщениям с прошлого обзора (21:00); …» (час —
`DAILY_REVIEW_HOUR`). Одна формулировка для ежедневного обзора и `/review`; N — число записей лога (после фильтра прошлого обзора).

**`/review`** (admin-only) — тот же сбор и ветки A/B (то же окно «с прошлого 21:00 до сейчас»), финал на модели ЧАТА через
`call_claude` + `dialog_params`, `max_tokens = out_tokens(model, 2200)`; без футера. Можно проверить на стенде, не ожидая 21:00.
Haiku-части идут в `usage_log` под `usage_ctx` чата (`label=daily_review_chunk`).

**Деньги и контекст.** Размер входа Opus: A — до 60 000 знаков (≈ 20–25k токенов на русском, Opus 5.5 в `MODELS`); B —
≤ 30 000 + 8 000 знаков (≈ 12–15k токенов). Haiku-частей на активный день (≈ 100–150k знаков лога) — обычно 5–10, каждая
≤ 20 000 знаков (≈ 7k токенов) — порог ступени >100k недостижим. **Замер стенда 2026-10-24** (синтетический лог, Opus 5.5, `scripts`-прогон через `prepare_review_input` + `aux_create`):
| Сценарий | Лог | Ветка | Haiku | Opus вход/выход | Время | Стоимость |
|---|---|---|---|---|---|---|
| 128 сообщений | 6.9k знаков | A | — | 7k знаков / 1689 ток. | 20 с | $0.055 |
| те же, `REVIEW_SINGLE_MAX_CHARS=0` | 6.9k | B (5 частей) | 5 вызовов, $0.003 | 11k знаков / 1422 | 8 + 17 с | $0.062 |
| 1920 сообщений | 103k | B (7 частей) | 7 вызовов, $0.011 | 18k знаков / 1538 | 11 + 19 с | $0.089 |
Обзор 2.5–2.7k знаков, один Telegram-месседж; фильтр прошлого обзора сработал (маркер не просочился). Порог
`REVIEW_SINGLE_MAX_CHARS=60000` не подбирали под реальный чат — на живых данных проверить, как A ведёт себя на 40–60k.

**С ТЗ v0.10 (`docs/claude/billing.md`) ежедневный обзор — платная фича.** Шлётся только paid-группам
(`chat_tier == 'paid'`), не забаненным, с `daily_review_enabled=1` (`db.get_review_chats()` — все
группы `chat_id < 0`, не только `approved`; платность проверяет код). Free-чатам не шлётся, флаг
`daily_review_enabled` при этом НЕ трогается. Модель — ВСЕГДА Opus (`DAILY_REVIEW_MODEL_ID` = `MODELS["opus"]["id"]`, с 2026-09-23 — Opus 5.5) независимо
от модели чата — осознанное исключение из «служебное — Haiku». Промпт креативнее («фельетон»,
~1000–1200 знаков вместо 600), `max_tokens` 500 → 1000, `trim_to_last_sentence` сохранён.
Строку «Отключить ежедневный обзор: /review_off (админ чата)» добавляет КОД отдельным абзацем, не
модель; в `group_messages` обзор сохраняется БЕЗ неё. `usage_ctx` выставляется явно на каждый чат цикла
(`label='daily_review'`, `billed=1`), сбрасывается в `finally`. Историческая часть ниже (600 знаков,
500 токенов) — про прежнюю версию; `/review` (разовый, admin-only) остаётся на старом промпте и
модели чата.

Три проблемы найдены и починены одной правкой (2026-09-06):
1. **Обзоры были слишком длинные** (промпт просил 4-6 абзацев) — сокращено до 2-3
   абзацев, явный потолок «не больше 600 знаков суммарно» в самом промпте, `max_tokens`
   снижен 1024 → 500. Модели не всегда точно попадают в символьный лимит, но абзацы
   и токен-потолок вместе держат текст компактным.
2. **Обрезался на середине слова** при упоре в `max_tokens` — раньше это не
   проверялось вообще. Теперь `api_errors.was_truncated(response)` логируется, и
   `api_errors.trim_to_last_sentence(text)` режет висящий хвост до последнего целого
   предложения (`.`/`!`/`?`/`…`). Если целого предложения нет вообще — возвращает текст
   как есть (лучше урезанный ответ, чем пустой). Это НЕ то же самое, что
   `_repair_truncated_json` — тот чинит структурированный JSON, этот — свободный текст.
3. **Клодушка не видела собственные обзоры** и была уверена, что не писала их: обзор
   уходил в чат через `send_message`/`reply_text`, но никогда не сохранялся в
   `group_messages` — в следующей реплике модель не находила его в транскрипте
   (`build_group_messages()`) и решала, что текст ей приписали. Теперь оба пути
   (`daily_chat_review` и `cmd_review`) зовут `db.save_group_message(chat_id,
   context_bot_id, "Клодушка", review, is_bot=True)` сразу после отправки — тот же
   паттерн, что у обычных ответов бота в группе (см. рисование и текстовые ветки
   `handle_message`).

Концовка обзора (2026-09-06): раньше промпт требовал фиксированную фразу «я AI, вижу
картину целиком, а они — нет» — на практике превращалась в шаблонную подпись под
каждым обзором. Заменено на «одна короткая фраза-афоризм/шутка под события ИМЕННО
ЭТОГО дня, не заготовленная фраза про AI» — модель придумывает новую концовку каждый
раз, привязанную к конкретной динамике чата, а не повторяет один и тот же оборот.

## Вкл/выкл ежедневного авто-обзора per-chat (`/review_on`, `/review_off`)
`allowed_chats.daily_review_enabled` (INTEGER, дефолт 1 — обратная совместимость, ничьё
поведение не меняется молча) — `daily_chat_review()` пропускает чат, если флаг снят
(теперь фильтр в SQL — `db.get_review_chats()`; раньше `if not chat["daily_review_enabled"]:
continue` в цикле по `db.get_allowed_chats()`, который удалён). Хранится в `allowed_chats`, а не в отдельной таблице (в
отличие от `/ratelimit` → `chat_rate_limits`, `docs/claude/group-chat.md`): это свойство
ОДНОГО чата целиком, не пары (chat_id, user_id), отдельная таблица была бы избыточной.

Команды доступны и глобальным админам бота, и реальным админам/creator'ам ЭТОГО
Telegram-чата — переиспользован `is_chat_admin()` (`docs/claude/group-chat.md`),
тот же паттерн, что у `/ratelimit`. Работают только в группах. `db.set_chat_review_enabled`
возвращает `False`, если строка чата не нашлась (`UPDATE ... WHERE chat_id=?` с нулевым
`rowcount`) — на практике не должно случаться: `handle_new_chat` создаёт строку
`allowed_chats` (`status='pending'`) в момент, когда бота добавляют в чат, задолго до
того, как кто-то успеет позвать `/review_on`. Тот же паттерн проверки `rowcount`
пригодился в `set_chat_status` — см. `.claude/rules/db.md` и инцидент 2026-09-16/17 в
`docs/claude/incidents.md`.

**Не путать `/review_on`/`/review_off` с `/review`**: `/review` — разовый обзор ПРЯМО
СЕЙЧАС, остаётся admin-only (`is_admin`, глобальные админы бота), не трогали. Новые
команды управляют только ЕЖЕДНЕВНОЙ фоновой рассылкой (`run_daily` в `main()`).

## Часовой пояс (`BERLIN_TZ`)
Дневной обзор запускается через `app.job_queue.run_daily(daily_chat_review, time=dt_time(hour=DAILY_REVIEW_HOUR, minute=0, tzinfo=BERLIN_TZ), ...)` в `main()`. `DAILY_REVIEW_HOUR = 21` (до 2026-10-25 было 22: после перехода на CET это полночь по МСК, а часть участников живёт по МСК; 21:00 Berlin = 23:00 МСК зимой / 22:00 МСК летом). Окно обзора с v1.10.0 — с 21:00 вчера до запуска (см. раздел вверху), сообщения после 21:00 попадают в следующий обзор. `BERLIN_TZ = ZoneInfo("Europe/Berlin")` —
единственный источник правды для часового пояса во всём проекте (используется и здесь,
и в `service_block` для текущей даты/времени — служебный блок последнего user-turn, `docs/claude/prompt-cache.md`). До фикса 2026-09-19 (`b72e96e`) было
жёсткое `timezone(timedelta(hours=2))` — не учитывало переход CET/CEST, обзор съехал бы
на час после 25.10.2026. `ZoneInfo` в `tzinfo` параметра `datetime.time` для
`JobQueue.run_daily` — штатный способ, PTB сам пересчитывает следующий запуск с учётом
DST (перепроверено живым тестом на PTB 22.8 при обновлении зависимостей, 2026-09-19 —
`job_queue.jobs()[0].job.trigger.timezone` возвращает `Europe/Berlin`, работает так же,
как на 21.10).
Добавлять новое место с датой/временем — брать `BERLIN_TZ` из bot.py, НЕ писать
`timezone(timedelta(...))` по новой.

Зависимость `tzdata` в `requirements.txt` — гарантия работы `ZoneInfo` независимо от
того, есть ли системная база часовых поясов в образе `python:3.12-slim` (живая проверка
07.09.2026 через `docker run --rm python:3.12-slim python3 -c "import zoneinfo;
zoneinfo.ZoneInfo('Europe/Berlin')"` на сервере показала, что системная tzdata в образе
УЖЕ есть — но пакет добавлен как защита от смены базового образа в будущем, а не потому,
что без него сломано сейчас).

## Режим характера (v1.7.0)
Промпты `daily_chat_review` и `/review` берут подачу из режима чата: `persona_review_style(chat_id)` (`review_style` из
`PERSONAS`, нет → `tone`). Структура, длина и лимиты обзора не менялись; зашитое «AI, который умнее всех» теперь
`review_style` режима `classic`. Подробности — `docs/claude/personas.md`.

## Пометка при записи обзора в транскрипт (v1.7.1)
Обзор строится по сообщениям всего дня (до 100), а диалог видит только окно `GROUP_TRANSCRIPT_LIMIT`. Чтобы модель на
reply не объявляла обзор выдумкой, в `group_messages` он пишется как `_review_sent_note(N)\n<текст>`: «(обзор дня по N
сообщениям с начала суток; большинство из них могут быть вне твоего окна истории)» (`/review` — «по последним N
сообщениям»). В чат уходит чистый текст обзора. Пометка объяснена в `_core_rules` (служебная запись, не копировать).
Побочно: пометка попадает и в `get_group_history` (следующий обзор/`/review` увидит её в логе чата) — безвредно.
Инцидент 2026-10-22 — `docs/claude/incidents.md`.

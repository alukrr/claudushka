# ТЗ: дневной обзор за весь день, с блоками тем (ветка `feat/review-topics`)

Перед правкой прочитай `docs/claude/daily-review.md` (история промпта, пометка обзора в транскрипте,
инцидент 2026-10-22) и `.claude/rules/db.md`. Ветку делать от `main` ПОСЛЕ мержа `fix/review-21`
(`DAILY_REVIEW_HOUR = 21`).

## Проблема
`daily_chat_review` берёт `db.get_group_history(chat_id, 100, since_ts=_day_start_ts())` —
`ORDER BY timestamp DESC LIMIT 100`, то есть ПОСЛЕДНИЕ 100 сообщений дня. В активном чате обзор
начинается ~с 20:00, утро и день теряются. Длинные ответы самой Клодушки тоже съедают эти 100 мест.
Сообщения после времени запуска (21:00) не попадают ни в один обзор.

## Решения Алексея (2026-10-24)
1. Механизм — гибрид A+B: день влезает в бюджет → один вызов Opus по всему логу (A); не влезает →
   нарезка на сессии, выжимка каждой Haiku в JSON, итог пишет Opus по выжимкам (B).
2. Окно — с прошлого обзора: с `DAILY_REVIEW_HOUR` вчера до запуска сегодня (по `BERLIN_TZ`).
3. Формат: вступление и финальный афоризм остаются, между ними — блоки тем. Длиннее, чем сейчас, — ок.
4. Время рассылки одно на всех (`DAILY_REVIEW_HOUR`), новых таблиц НЕ делаем.

## 1. Окно и сбор лога
- `since` = `datetime.combine(today - 1 day, dt_time(DAILY_REVIEW_HOUR), tzinfo=BERLIN_TZ)`, `until` = сейчас.
  Через дату, НЕ `now - timedelta(hours=24)` — в ночь перехода CET/CEST окно честно 23 или 25 часов.
  Вынести в функцию рядом с `_day_start` (`_review_window()` или подобное).
- Новая функция в db.py, напр. `get_group_messages_range(chat_id, since_ts, until_ts)` → список dict
  `{id, ts, sender, text, is_bot}` по ВОЗРАСТАНИЮ времени, без LIMIT по числу (лимит — по размеру, ниже).
  `get_group_history` не менять (её зовёт `/review` и другие).
- **Исключить из лога прошлый обзор**: он сохранён в 21:00:xx вчера и попадает в окно. Фильтр —
  `is_bot` и текст начинается с `f"({REVIEW_SENT_LABEL}"`. Без этого Opus будет пересказывать вчерашний обзор.
- Реплики бота: оставлять, но резать сильнее, чем людей (напр. `REVIEW_BOT_MSG_CHARS = 200`); людей —
  `REVIEW_USER_MSG_CHARS = 500`. Обрезка — с пометкой «…».
- Формат строки лога: `HH:MM Имя: текст` (время по `BERLIN_TZ`) — нужно модели для «когда» в блоках тем.
- Порог «мало сообщений» (сейчас `< 5`) — считать по НЕ-бот сообщениям.

## 2. Хранение: подрезка `group_messages`
`db.save_group_message` держит последние **1000** строк на чат (`DELETE ... LIMIT 1000`). Если за сутки
в чате больше 1000 сообщений, утро удаляется ещё до обзора — никакой A/B не поможет. Вынести число в
константу (`GROUP_MESSAGES_KEEP`) и поднять до 3000. Схема не меняется. Проверить, что больше никто не
полагается на 1000 (`count_chat_messages` — справочная, см. `.claude/rules/db.md`). Задокументировать в
`.claude/rules/db.md` и `docs/claude/group-chat.md`. Для недельного обзора (на потом) этого будет мало —
отметить в `open-tasks.md`, не решать сейчас.

## 3. Ветка A — один вызов
Если суммарный размер лога ≤ `REVIEW_SINGLE_MAX_CHARS` (стартовое значение 60 000, подобрать на стенде) —
весь лог одним сообщением в Opus. Промпт: сначала (про себя) выдели темы дня, потом пиши в формате п. 5.
`REVIEW_SINGLE_MAX_CHARS = 0` → всегда ветка B (переключатель «чистый B» без правки кода).

## 4. Ветка B — сессии и выжимки
- Нарезка: новая сессия при паузе ≥ `REVIEW_SESSION_GAP_MIN` (45) минут; сессия длиннее
  `REVIEW_CHUNK_MAX_CHARS` (20 000) режется на части по границе сообщения. Чистая функция без I/O —
  покрыть юнит-тестом (пустой лог, одна длинная сессия, паузы ровно на границе, переход CET/CEST).
- Каждая часть → `aux_create(label="daily_review_chunk", model=DEFAULT_MODEL_ID, **aux_params(), ...)`
  (инвариант: служебные — Haiku с `aux_params`). Ответ — JSON через `api_errors.parse_json_lenient(..., "{")`:
  `{"topics": [{"title", "from", "to", "participants": [...], "gist", "moments": [...], "quotes": [...]}]}`.
  Цитаты — дословно из лога, коротко (до ~120 знаков), 0–2 на тему: от них зависит юмор финала.
- Упавшая/пустая выжимка части не роняет обзор: часть пропускается, в лог warning. Упали ВСЕ → обзор
  не шлём (как сейчас при пустом ответе).
- Итоговый вызов Opus: JSON тем всех частей (лимит по размеру, напр. 30 000 знаков) + последние ~40
  сообщений лога сырьём (тоже под лимитом) — для живости. Сообщения с подряд идущими похожими темами
  разных частей модель объединяет сама — сказать об этом в промпте.

## 5. Формат и промпт итога (общий для A и B)
- Подача — `persona_review_style(chat_id)`, как сейчас.
- Структура: вступление 1–3 предложения (сюжет дня) → 3–6 блоков тем → афоризм под ЭТОТ день (не
  заготовка про AI — правило из `daily-review.md` сохраняется).
- Блок темы: короткий заголовок + когда (утро/день/вечер или время) + кто + 2–4 предложения с подачей
  режима. Только plain text (Telegram шлётся без parse_mode); эмодзи-маркер в начале блока — допустимо.
- Мелочь, не тянущую на тему, — не перечислять, «не старайся упомянуть всех» сохраняется.
- Объём — ориентир 2000–3000 знаков. `max_tokens` = `out_tokens(DAILY_REVIEW_MODEL_ID, 2200)` (подобрать).
  `was_truncated` → `trim_to_last_sentence` — как сейчас.
- **Лимит Telegram 4096** на `review + "\n\n" + DAILY_REVIEW_FOOTER`: если длиннее — делить по границе
  абзаца на 2 сообщения (футер — в последнем), не резать посреди фразы. В `group_messages` — один
  текст целиком, без футера.

## 6. Пометка в транскрипте
`_review_sent_note`: сейчас «по N сообщениям с начала суток». Заменить формулировку для ежедневного
обзора на «по N сообщениям с прошлого обзора (21:00)» (час — из `DAILY_REVIEW_HOUR`). Префикс
`REVIEW_SENT_LABEL` НЕ менять — по нему фильтр из п. 1. Проверить, как пометка объяснена в `_core_rules`
(инцидент 2026-10-22), и при необходимости поправить там же.

## 7. `/review` (разовый, admin-only)
Предложение: тот же сбор лога (п. 1–4, то же окно «с прошлого 21:00 до сейчас»), финал — как сейчас на
модели чата через `call_claude` с `dialog_params`. Так фичу можно проверить на стенде без ожидания 21:00.
Если это выходит за рамки — оставить `/review` как есть и явно сказать в отчёте.

## 8. Деньги и контекст
- `usage_ctx` выставляется на чат до ВСЕХ вызовов (и Haiku-частей, и Opus), сбрасывается в `finally` — как сейчас.
- В отчёте оценить: размер входа Opus в A и B, число Haiku-вызовов на активный день, ориентировочную
  стоимость обзора (цены из `MODELS`). Haiku: вход > 100k стоит в 5 раз дороже — части по 20k знаков туда не
  дотягивают, но проверить.
- Все новые источники в промпте — с лимитом по размеру (инвариант CLAUDE.md).

# ТЗ: параллельная обработка апдейтов с порядком внутри чата (`feat/concurrent-updates`)

Постановка Алексея 2026-11-02 («давай параллельную обработку, в несколько потоков»). Проблема — `docs/claude/open-tasks.md`,
раздел «Последовательная обработка апдейтов»: PTB обрабатывает апдейты строго по одному, поэтому любой долгий `await` в
хендлере (генерация картинки, медленный ответ пула, ожидание ретрая) задерживает ответы ВСЕМ чатам. Живой случай —
стенд 2026-11-02: `Retry-After: 866` на 14 минут повесил все команды (частично закрыто потолком `SDK_RETRY_WAIT_CAP`, v2.5.1).

Технически это не потоки ОС, а параллельные задачи asyncio на одном event loop (так устроены PTB и бот); блокирующие вызовы и
сейчас уходят в пул потоков (`asyncio.to_thread`) — его размер тоже правим (п.4).

ТЗ для отдельной сессии: **сначала `CLAUDE.md` целиком**, затем `docs/claude/api-errors.md` (блокирующие вызовы, фоновые задачи,
ретраи), `docs/claude/billing.md` (`usage_ctx`, `gate_update`), `docs/claude/group-chat.md`, `docs/claude/prompt-cache.md`
(окно истории `pick_history_window`), `.claude/rules/db.md`.

## Целевое поведение
- Апдейты РАЗНЫХ чатов обрабатываются параллельно.
- Апдейты ОДНОГО чата — строго по очереди, в порядке прихода (как сейчас): иначе ломаются чередование реплик в `group_messages` /
  `conversations`, окно истории, автоигнор, лимиты, порядок ответов.
- Общее число одновременно обрабатываемых апдейтов ограничено (`MAX_CONCURRENT_UPDATES`, по умолчанию 16).

## Что сделать
1. **Свой процессор апдейтов** (в `bot.py`, не новый файл): `class PerChatUpdateProcessor(telegram.ext.BaseUpdateProcessor)`.
   Сначала прочитать исходник установленной PTB 22.8 (`telegram/ext/_baseupdateprocessor.py`, `Application.process_update`/
   `__process_update_wrapper`, как `Application` вызывает процессор и создаёт ли отдельную задачу на апдейт) и сослаться на это в
   докстринге — не по памяти.
   - Ключ очереди: `update.effective_chat.id`, если есть; иначе `update.effective_user.id`; иначе без очереди.
   - **Сначала блокировка чата, потом общий лимит.** Если взять слот общего лимита и потом ждать блокировку своего чата, флуд в одном
     чате займёт все слоты и остановит остальные. Если базовый `process_update` берёт семафор сам до `do_process_update` — переопределить
     `process_update` (свой `asyncio.Semaphore`), не полагаясь на приватные поля базового класса.
   - Блокировки per-chat — `asyncio.Lock` в словаре со счётчиком ожидающих; запись удаляется, когда чат освободился (память не растёт).
   - Исключение в одном апдейте не держит блокировку чата (`async with`), следующий апдейт этого чата обрабатывается.
   - Подключение: `Application.builder()...concurrent_updates(PerChatUpdateProcessor(MAX_CONCURRENT_UPDATES))`.
     `MAX_CONCURRENT_UPDATES` — env, по умолчанию 16; `1` = как сейчас (аварийный откат без кода).
2. **`usage_ctx` и другие contextvars.** Сейчас `gate_update` ставит `usage_ctx` в начале каждого апдейта и в докстринге сказано
   «PTB обрабатывает апдейты последовательно в одном task'е». Проверить по исходнику PTB, что при процессоре каждый апдейт идёт в
   ОТДЕЛЬНОЙ задаче (тогда contextvar изолирован) — и тестом: два апдейта разных чатов параллельно, у каждого свой `usage_ctx` в
   `usage_log`. Если задача общая — остановиться и сказать: тогда нужен другой подход. Докстринг поправить.
3. **Аудит глобального состояния в `bot.py`.** Пройти ВСЕ модульные изменяемые объекты (на момент ТЗ, не полный список):
   `_street_notified`, `_unknown_model_warned`, `_reaction_chain`, `_reacted`, `_fallback_until`, `_bonus_checked`,
   `_free_msg_counter`, `_recent_addresses`, `_activity_last_check`, `_known_groups`, `_safety_strikes`, `_safety_last_uid`,
   `_safety_scan_running`, `_safety_scan_last`, `_dev_albums`, `_ma_cache`, якоря `pick_history_window`, плюс `global`-переменные. По
   каждому в отчёте: ключ (чат / пользователь / модель / глобальный), защищён ли очередью чата, есть ли гонка между РАЗНЫМИ чатами
   и чем она грозит. Чинить только реальные проблемы (например, проверка-и-запись, растянутая через `await`, по общему для разных
   чатов ключу); косметические гонки (лишнее уведомление админу раз в жизни) — описать, не чинить.
   Известное допущение: дневной лимит непроверенного участника, пишущего одновременно в двух группах, может пропустить +1 ответ — норм.
4. **Пул потоков.** `asyncio.to_thread` использует пул loop'а по умолчанию: `min(32, cpu + 4)` потоков — на сервере это мало, а
   синхронные вызовы модели (`sync_create`, извлечение памяти, поиск) теперь пойдут параллельно. В `post_init`:
   `loop.set_default_executor(ThreadPoolExecutor(max_workers=THREAD_POOL_WORKERS, thread_name_prefix="claudushka"))`,
   `THREAD_POOL_WORKERS` — env, по умолчанию 32. Проверить, что всё блокирующее (SQLite, `client.messages.create`, ffmpeg) и так идёт
   через `to_thread`/обёртки — новых блокирующих вызовов в event loop не появилось (инвариант проекта).
5. **SQLite.** WAL уже включён (`db.get_conn`). Добавить `sqlite3.connect(..., timeout=30)` (сейчас дефолт 5 с): параллельные записи из
   пула потоков ждут друг друга, а не падают «database is locked». Длинных транзакций не вводить.
6. **Логи.** В строке `PROMPT …` уже есть chat/uid — убедиться, что по логам можно развести перемешанные апдейты разных чатов; если
   где-то в логах нет chat_id там, где он нужен для разбора, — добавить.

## Тесты
`scripts/test_concurrent_updates.py`:
- два апдейта ОДНОГО чата с искусственной задержкой в первом → второй стартует только после первого (порядок сохранён);
- два апдейта РАЗНЫХ чатов → идут параллельно (общее время ≈ одной задержки);
- лимит: при `MAX_CONCURRENT_UPDATES=2` третий чат ждёт;
- флуд одного чата (10 апдейтов) не занимает слоты: апдейт другого чата обрабатывается сразу;
- исключение в апдейте не блокирует следующий апдейт этого чата; словарь блокировок пустеет после обработки;
- апдейт без чата и пользователя обрабатывается;
- `usage_ctx`: два параллельных апдейта разных чатов пишут в `usage_log` каждый свой `chat_id` (через `gate_update` и подменённую модель);
- `MAX_CONCURRENT_UPDATES=1` → строго последовательно.
- все `scripts/test_*.py` без сети — зелёные; характеризационные тесты реестра — без правок.

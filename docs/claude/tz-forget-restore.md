# ТЗ: восстановить память участника после случайного `/forget` (`chore/restore-user-memory`)

Постановка Алексея 2026-11-12: участник одной из групп стёр свою память командой `/forget` (она удаляет всё и без вопросов,
`bot.py` `cmd_forget` → `db.clear_memory`). Нужно вернуть её из последней копии базы. **Делается первой, до ТЗ
`docs/claude/tz-forget-confirm.md` и до любого деплоя.** Недельные факты (`tier='medium'`) живут 7 дней — чем позже, тем меньше вернётся.

ТЗ для отдельной сессии: **сначала `CLAUDE.md` целиком**, затем `docs/claude/memory.md`, `docs/claude/profile.md`, `.claude/rules/db.md`,
раздел «Бэкап» в `docs/claude/staging.md`.

**Репозиторий публичный: ник, `user_id`, `chat_id` и название чата в файлы и коммиты не писать.** Настоящие значения `<USER_ID>` и
`<CHAT_ID>` даёт Алексей в сессии.

## Что уже выяснено (проверено на сервере 2026-11-12, только чтение)
- Копия-источник: `~/claudushka/data/backups/claudushka-dedup-20261111-233243.db` (снята 2026-11-11 23:32). В ней у участника
  158 фактов (87 `long`, остальные `medium`), все — в одной группе, личных нет; профиль — 3 поля; предложений профиля — 4.
- Стирание случилось между 2026-11-11 23:32 и 2026-11-12 08:17: в боевой базе на 13:42 у него 5 новых фактов (первый — 08:17), профиль пуст.
- Копии в `data/backups/` в режиме WAL и принадлежат root: открывать только так —
  `sqlite3.connect("file:<путь>?mode=ro&immutable=1", uri=True)`. Обычный `mode=ro` падает с «attempt to write a readonly database».
- `data/` на сервере — root:root, запись в боевую базу с хоста — через `sudo` (как у `dedup`, `docs/claude/open-tasks.md`).

## Решения Алексея
1. Возвращаем **всё, что стёр `/forget`**: факты во всех чатах и в личке и подтверждённый профиль (`user_profile`).
   Личный тред (`conversations`) и неподтверждённые предложения (`profile_proposals`) **не** возвращаем.
2. **Слияние, не замена:** факты, накопленные после стирания, остаются. Из копии добавляются только те, которых сейчас нет.
3. Бота не останавливать. Скрипт остаётся в репозитории на следующие случаи.

## Что сделать
1. **`scripts/restore_user_memory.py`** — только stdlib, bot.py и db.py не импортирует, сеть не нужна.
   - Аргументы: `--from-db <копия>`, `--db <боевая, по умолчанию data/claudushka.db>`, `--user-id`, необязательный `--chat-id`
     (ограничить одним чатом), `--apply`.
   - **Без `--apply` — только отчёт**, боевую базу открывает на чтение: сколько фактов в копии, сколько из них просрочено и будет
     пропущено, сколько уже есть в боевой, сколько будет добавлено (по `tier` и по чатам), какие поля профиля будут добавлены.
     Тексты фактов не печатать — только числа и `id` строк копии (вывод попадает в чат сессии).
   - **Факты:** строки `memory` копии с этим `user_id`, у которых `expires_at IS NULL OR expires_at > now`. Строка добавляется, если в
     боевой нет строки с тем же `(user_id, context, chat_id, fact)` — `chat_id` сравнивать через `IS` (в личке он `NULL`). Переносить
     `fact, context, chat_id, tier, created_at, expires_at` как есть; `id` — новый.
   - **Профиль:** строки `user_profile` копии с этим `user_id` — `INSERT OR IGNORE` по первичному ключу со всеми колонками как есть
     (`source`, `updated_at`, `updated_by`). Поле, которое уже есть в боевой, не перезаписывать. Это дословный возврат строк, уже
     утверждённых админом, поэтому идёт мимо `db.apply_profile_ops` — осознанное исключение из инварианта профиля; записать его в
     `docs/claude/profile.md`. Если по коду `apply_profile_ops` видно, что дословная копия что-то ломает, — остановиться и спросить Алексея.
   - **С `--apply`:** сначала копия боевой базы через `sqlite3.backup` в `data/backups/claudushka-restore-<ГГГГММДД-ЧЧММСС>.db`
     (не создалась — ничего не писать, как `backup_db` в `dedup_memory.py`); затем одна транзакция `BEGIN IMMEDIATE`,
     `timeout=30` (бот работает и пишет в ту же базу). В конце — те же числа, что в отчёте, и путь к копии.
   - Повторный запуск с `--apply` ничего не добавляет (проверить тестом).
   - Колонки читать по именам из `PRAGMA table_info`; если в копии нет колонки или таблицы, которая есть в боевой, — понятная ошибка
     до любой записи, а не падение посередине.
2. **Тесты** `scripts/test_restore_user_memory.py` (временные базы, без сети): пустая боевая; боевая с новыми фактами и с дублем текста;
   просроченный `medium` пропущен; личный факт (`chat_id` NULL) не дублируется; профиль не перезаписывает существующее поле;
   `--chat-id`; чужие пользователи не тронуты; повторный запуск; копия не создалась → записи нет; пробный прогон не меняет файл.
3. **Прогон.** Заход на сервер — только с «да» Алексея в этой сессии; перед `--apply` — спросить ещё раз.
   - Шаг 0, только чтение: убедиться, что копия на месте и числа в ней совпадают с разделом «Что уже выяснено».
   - Копия боевой базы в `/tmp` (`sqlite3.backup`) → `--apply` на ней → числа сошлись с пробным прогоном.
   - Пробный прогон на боевой, отчёт показать Алексею. После его «да» — `sudo python3 scripts/restore_user_memory.py … --apply`.
   - Проверка: `SELECT tier, COUNT(*) FROM memory WHERE user_id=<USER_ID> GROUP BY tier` и число строк `user_profile`. Перезапуск
     бота не нужен: память читается из базы на каждый ответ.
4. **Документация:** `docs/claude/memory.md` — раздел «Восстановление после `/forget`» (команда, что возвращается и что нет, как
   открывать копии); `docs/claude/profile.md` — исключение из п.1; `docs/claude/incidents.md` — запись 2026-11-12 без ника и id
   (что случилось, откуда вернули, сколько строк, урок — ТЗ подтверждения); `CLAUDE.md` — строка «Память» в индексе.

- Не мержить без Алексея, тег не ставить.

## Стенд и версия
Стенд не нужен: бот не меняется, логика проверяется тестами и прогоном на копии боевой базы. Версия не меняется (скрипт не часть
бота); коммиты `chore:` и `docs:`.

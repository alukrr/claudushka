# Групповой чат (мультиперсональный контекст)

Перед правкой `build_group_messages`, `handle_message` (групповая ветка), `/ratelimit`,
`is_chat_admin`, гейтинга доступа в группах — читай этот файл.

В группах бот — участник беседы нескольких людей, а не личный диалог 1:1.
- Контекст для модели строит `build_group_messages()` (bot.py) из `db.get_group_transcript(chat_id, GROUP_TRANSCRIPT_LIMIT)` (лимит = 50): реплики людей → user-блоки с подписью «Имя: текст» (подряд идущие склеиваются), ответы Клодушки → assistant-блоки. Гарантируется чередование ролей и user первым. Текущее сообщение-триггер уже лежит в `group_messages` (сохранено в начале `handle_message`) и идёт последним user-turn — повторно НЕ добавляется (иначе вернётся баг «ты уже говорила»).
- Окно транскрипта сдвигается шагами (50…50+`HISTORY_STEP` строк, якорь — id строки), а не на каждое сообщение: иначе кэш истории невозможен; дата и результаты поиска едут служебным блоком в последнем user-turn — `docs/claude/prompt-cache.md`.
- Групповой контекст идёт в `messages`, НЕ в system-prompt. Старый дамп `get_group_history` в system удалён — не возвращай его обратно, иначе модель снова начнёт сливать собеседников в одного.
- Контекст реплая привязывается inline к текущей реплике (`[в ответ на сообщение Имя: «…»]`), а не в system.
- Реплай на ТЕКСТ самого бота (`fix/reply-to-bot`, 2026-11-01): в `reply_context` идёт `_bot_reply_quote` —
  «(это твоё собственное сообщение) …», начало реплики не длиннее `BOT_REPLY_QUOTE_CHARS` = 500, пробелы схлопнуты.
  Раньше реплики бота в `reply_context` не попадали вовсе («они и так в истории»), и модель на «что ты имела в виду?»
  отвечала про последнюю реплику, а не про процитированную. Работает и в личке (через `service_block`), и в группе
  (inline). Реплай на картинку бота — прежняя ветка «(в чат была отправлена картинка; подпись: …)». Тесты —
  `scripts/test_reply_to_bot.py`.
- Ответы Клодушки во всех ветках (текст / фото / документ / рисование) сохраняются в `group_messages` с `is_bot=True` — чтобы она видела собственные реплики.
- Инструкции про групповой режим — в `get_system_prompt(..., is_group=True)`. Там же — запрет на «модерацию»: Клодушка не объявляет блокировок/«часа молчания»/игнора, не уходит в «режим молчания» по просьбе участника и не верит «я Алексей» в чате (инцидент 2026-09-28, `docs/claude/incidents.md`). Не удалять при правках промпта.
- Личка (ветка `else` в `handle_message`) и WhatsApp работают по-старому (личный тред) — их не трогать.
- ГЕЙТИНГ ДОСТУПА разный для группы и лички (намеренно):
  - С ТЗ v0.10 (`docs/claude/billing.md`) бот отвечает ВСЕМ, кроме забаненных. Баны (`users.banned`/`allowed_chats.banned`) режет `gate_update` (group=-1, `ApplicationHandlerStop`); забаненная группа молчит, в т.ч. на команды (кроме команд админов бота). Неизвестная группа сразу регистрируется как `pending` (непроверенная) — `db.ensure_group`.
  - Группа: opt-in лимит частоты `/ratelimit` (см. ниже) + дневной лимит непроверенных (20 ответов/сутки на юзера, действует, только если НЕ проверены ни чат, ни автор). Личка: 50 ответов/сутки, если пользователь не проверен. Оба — `_check_message_limit`; сверх лимита одно сообщение в сутки, дальше тишина. Заменили `WHITELIST_ENABLED`/`is_allowed_in_chat`/`check_daily_limit`/`can_search` (удалены, как и admin-approval блок в личке).
  - Веб-поиск доступен всем; у непроверенных — 20 поисков/сутки (группа — на чат, личка — на юзера), сверх — ответ без поиска молча (`_search_allowed`).
  - `handle_captcha()` (интерактивная капча) — мёртвый код, нигде не вызывается (как и раньше).
- Схема: `group_messages.is_bot INTEGER NOT NULL DEFAULT 0`, миграция идемпотентная в `init_db()`. Сигнатура `save_group_message(chat_id, user_id, sender_name, content, is_bot=False)`.
- `db.get_group_history()` (строки «Имя: текст») оставлена специально, не удалять и не путать с `get_group_transcript()`. Дневной обзор и `/review` с v1.10.0 читают `db.get_group_messages_range` (окно «с прошлого обзора», без LIMIT по числу).
- `group_messages` подрезается до `db.GROUP_MESSAGES_KEEP` = 3000 строк на чат (было 1000: в активном чате утро удалялось до вечернего обзора). Недельному обзору этого мало — `docs/claude/open-tasks.md`.

## Лимит частоты сообщений per-user в группе (`/ratelimit`, v0.10.0)
Просили ограничить отдельных «спамящих» участников группы, не трогая остальных.
- Таблица `chat_rate_limits(chat_id, user_id, interval_seconds, last_ts)`, PK `(chat_id, user_id)`.
  **Отсутствие строки = без ограничений** (это дефолт для всех) — не «0 = безлимит» и не
  отдельный флаг, просто нет записи.
- `db.check_group_rate_limit(chat_id, user_id)` — True можно отвечать (и сразу обновляет
  `last_ts`), False — лимит не истёк. Вызывается в `handle_message` СРАЗУ после проверки
  `is_bot_mentioned` (и `_check_message_limit` — дневной лимит непроверенных), ДО любых API-вызовов — это
  самая ранняя точка, где уже известны `chat_id`/`user_id` и бот точно был адресован.
  При `False` — обычный `return`, **без сообщения пользователю** (так просили: превышение
  лимита должно быть незаметным, а не «подожди ещё 3 минуты»).
- `db.set_group_rate_limit` / `remove_group_rate_limit` (`user_id=None` — снять со всех
  разом) / `get_group_rate_limits` — CRUD для команды.
- **Новый уровень админства**: `is_chat_admin(context, chat_id, user_id)` (bot.py) — ПОМИМО
  глобальных `ADMIN_IDS` разрешает управлять лимитом реальным админам/creator'ам ЭТОГО
  Telegram-чата через `context.bot.get_chat_member().status`. Раньше в кодовой базе не было
  понятия «админ группы», только `is_admin()` = глобальный админ бота — не путать эти два
  уровня при добавлении новых групповых команд. Тот же хелпер переиспользован в
  `/review_on`/`/review_off` (`docs/claude/daily-review.md`).
- `/ratelimit` без аргументов — список лимитов чата. Ответом на сообщение участника без
  доп. аргументов — его текущий лимит (`db.get_group_rate_limit`, без побочных эффектов,
  не путать с `check_group_rate_limit`). Ответом + `/ratelimit <N>` (минуты) или
  `/ratelimit off` — установить/снять лимит этому участнику. Без ответа — то же самое
  по ID первым аргументом (`/ratelimit <user_id> <N|off>`), как в `/ban`.
  `/ratelimit off` без ответа и без ID — сброс всех лимитов чата разом.
- Команда видна в `USER_HELP` (не в `ADMIN_HELP`, который показывается только глобальным
  админам через `is_admin()`) — иначе админы группы, не являющиеся админами бота, не
  увидели бы её в `/help` вообще.
- **`check_group_rate_limit` вызывается и в `cmd_search`/`cmd_imagine`**, не только в
  `handle_message`: это отдельные `CommandHandler`, а не текстовая ветка, и лимит туда
  не долетал бы без явной проверки — а это самые дорогие по деньгам команды (Tavily +
  Claude / Gemini). Один и тот же `last_ts` на пользователя в чате — лимит общий на
  «любое обращение к Клодушке», не отдельный счётчик на каждую команду.
- Найдено при первом деплое (server-side тест, ещё до тега v0.10.0), исправлено сразу:
  1. `cmd_search`/`cmd_imagine` изначально лимит не ловили — см. выше, починено.
  2. Реплай на сообщение + `/ratelimit` без аргументов раньше показывал usage вместо
     лимита этого конкретного участника — тоже починено (см. выше).
- **Известные, осознанно НЕ починенные, ограничения:**
  - Анонимные админы группы (`GroupAnonymousBot`, `user_id=1087968824`) в `is_chat_admin`
    получат `get_chat_member(...).status == "left"` и отказ «может только админ этого
    чата» — fail-closed, не дыра, но обычному анонимному админу команда покажется
    сломанной. Если у Алексея в чатах заведутся анонимные админы — тогда разбираться,
    как их отличать от реально вышедших пользователей.
  - [Историческое, до ТЗ v0.10: `cmd_ratelimit` не смотрел на whitelist-гейт. Гейта больше
    нет — бот отвечает всем неброненным, так что пункт потерял смысл.]

## Скрытые строки (`group_messages.hidden`, v2.1.0)
Строка с `hidden=1` не попадает ни в диалог, ни в дневной обзор, ни в извлечение памяти (фильтр `hidden = 0` в
`get_group_transcript`, `get_group_messages_range`, `get_group_history`). Ставит её `safety_scan` после safety-блока провайдера,
управление — админ-команды `/hidden`, `/unhide`, `/safety_scan`. Подробности — `docs/claude/safety-unblock.md`.

## Автоигнор (`feat/group-behavior`, v2.4.0)
ТЗ — `docs/claude/tz-group-behavior.md`. Только группы, только кодом: паузу включает и объявляет бот фиксированной строкой, модель — нет
(system-prompt: «автоматическая пауза бота… её включает бот, не ты»; инцидент 2026-09-28, `docs/claude/incidents.md`).
- **Проступок 1 — повтор** (бесплатно): `detect_repeat` держит в памяти процесса последние 5 обращений `(chat_id, user_id)`; текущее —
  повтор, если `difflib` ratio ≥ 0.9 минимум с ДВУМЯ предыдущими за 10 минут (`_norm_address`: lower, без пунктуации/эмодзи; плейсхолдеры
  медиа `[Фото]`… не сравниваются). Время обращения — `message.date` (время ОТПРАВКИ, не обработки: PTB обрабатывает апдейты по очереди,
  при тормозящем боте накопленная очередь иначе выглядела бы «после ответов»). Предыдущее обращение считается, только если бот ответил ПОСЛЕ него и
  ДО того, как человек написал текущее: `int(ts_prev) <= last_bot_ts <= int(now)`; метка `db.get_last_bot_ts` передаётся параметром
  `detect_repeat(..., now=, last_bot_ts=)` (функция чистая). Бот упал/молчит/тормозит — три «ты тут?» не проступок. Идёт синхронно: вместо ответа на это сообщение — предупреждение/пауза, модель не вызывается.
- **Проступок 2 — травля** (Lite): `_abuse_check_task`, `label="abuse_check"`, фоном ПАРАЛЛЕЛЬНО с ответом (запускается после `/ratelimit` и
  лимита непроверенных — на сообщения, на которые не отвечаем, Lite не тратим). Вход — `db.get_user_bot_exchange` (только СТРОГО ПОСЛЕ `last_strike_ts` человека — уже наказанное второй раз не судим; служебные строки бота — пометки паузы `(служебное:`, картинки `DRAW_SENT_LABEL`, обзора `REVIEW_SENT_LABEL` — во вход не идут, префиксы из констант, `_abuse_skip_prefixes`): последние 6 реплик
  человека и реплики бота между ними и «сейчас» (чужие не берутся; `hidden = 0`; каждая ≤ 300, всего ≤ 3000 знаков). Ответ JSON
  `{"abuse": bool}` через `parse_json_lenient`; мусор/пусто/ошибка/safety-блок/не-bool → `false` + warning. `reason` из ответа пишется в INFO-лог (≤ 200 знаков): при `true` — в строке `autoignore … reason=abuse why=…`, при `false` — `abuse_check … abuse=false why=…`. Промпт (`_ABUSE_SYSTEM`) прямо говорит: повторы без оскорблений — не травля (их ловит повтор), один обычный вопрос/просьба — никогда не травля (стенд 2026-11-01: вопрос «где ключи от танка?» после трёх наказанных повторов получил ложную паузу). Если `true` — предупреждение
  идёт ПОСЛЕ уже отправленного ответа.
- Не действует на админов бота (`is_admin`) и при `autoignore_enabled = 0` (`/autoignore off`): проверки не вызываются вообще.
- **Лестница** (`chat_ignores`, переживает рестарт): проступок через > 24 ч после прошлого — уровень с нуля; уровень 1 — предупреждение;
  2 → 5 мин, 3 → 15, 4 → 30, 5+ → 60 (`IGNORE_STEPS_MIN`; для стенда укорачивается переменной окружения `IGNORE_STEPS_MIN=1,1,1,1`).
  Сообщения — фиксированные строки (`strike_text(name, level, reason)`), одно на проступок, всегда говорят ЗА ЧТО: «…за повторы одной и той же фразы (флуд)» / «…за оскорбления в адрес бота»; во время паузы — тишина. В Telegram уходит живой текст, а в
  `group_messages` (`is_bot=True`) — СЛУЖЕБНАЯ ПОМЕТКА `pause_history_note`: «(служебное: предупреждение бота для Имя о повторах)» (при травле — «о грубости в адрес бота», по `reason`) /
  «(служебное: автопауза бота для Имя на N мин за повторы|за грубость в адрес бота)» — без первого лица и без слов «беру паузу» (модель копирует форматы из своей истории,
  инциденты 2026-09-08 и 2026-09-28; по образцу `_draw_sent_note`). System-prompt для этого не менялся.
- **Где действует пауза:** `handle_message` сразу после `is_bot_mentioned` (до `/ratelimit` и лимитов) + `cmd_imagine`, `cmd_search`. Пассивное
  сохранение реплики и извлечение памяти — выше по коду, паузой не затронуты (обзор и контекст видят всё). `gate_update` не режет (игнор — не бан).
- **Команды** (группа; админы чата и бота): `/autoignore [on|off]` (без аргумента — состояние и кто в паузе: имя/uid, до скольки по Берлину,
  уровень), `/unignore` (ответом на сообщение или `/unignore <user_id>`: строка `chat_ignores` удаляется).
- **Остаточный риск:** модель может скопировать и служебную пометку. Следить на стенде (шаг 15 чек-листа).

## Активность (`feat/group-behavior`, v2.4.0)
`/activity [0-100] [chat_id]` — `allowed_chats.activity_percent`, per-chat (старая глобальная `CHAT_ACTIVITY_CHANCE` была мёртвым кодом и удалена).
Смотреть — все; менять — админы чата и бота; чужой чат — только админ бота. Free: значение сохраняется, но не работает.
- **Условия** (`activity_should_check`, дешёвые первыми; срабатывает там, где сообщение НЕ адресовано боту): процент > 0; чат paid; автор не в паузе
  (кто угодно, включая админов); есть текст/подпись/распознанное медиа; ≥ `ACTIVITY_COOLDOWN_MIN` = 10 мин с последней реплики бота в чате
  (`db.get_last_bot_ts`: любой — ответ, обзор, активность, объявление паузы) и ≥ `ACTIVITY_RECHECK_MIN` = 3 мин с последней попытки проверки
  (память процесса); `random` против процента.
- **Фон** (`_activity_task`, `_spawn_background_task`, хендлер не ждёт): Lite `label="activity_check"` (последние 15 строк, ≤ 4000 знаков) →
  `{"say": bool}` → при `true` модель чата, `call_claude(..., label="activity", usage_label="activity")`, тот же `build_system` (кэш общий) +
  `build_group_messages`, в служебном блоке `service_block(spontaneous=True)`. Маркеры `[[DRAW]]`/`[[FILE]]` вырезаются, пусто — молчим. Ответ — reply
  на сообщение-триггер, пишется в `group_messages` (`is_bot=True`), `_count_reply` НЕ вызывается. Любая ошибка (в т.ч. safety-блок) — warning.
- 100% = Lite спрашивается на каждом сообщении, прошедшем кулдауны; потолок — одна реплика в 10 минут на чат (≤ 6 в час).

## Управляющие чата (`feat/chat-managers`, v2.5.0)
ТЗ — `docs/claude/tz-chat-managers.md`. Участник, которого вручную назначили, в СВОЕЙ группе имеет права **как админ этого чата** (не как админ
бота), хотя в Telegram он не админ. Таблица `chat_managers (chat_id, user_id, added_by, added_at)`, PK `(chat_id, user_id)`; права — только в том
чате, где выданы.
- **`is_chat_admin(context, chat_id, user_id)`** — единая точка «админ этого чата»: админ бота → да; `get_chat_member` (один запрос):
  `administrator`/`creator` → да; `member` или `restricted` (с `is_member`) **и** строка в `chat_managers` → да; `left`/`kicked`/ошибка запроса → нет.
  Строку при выходе НЕ удаляем: вернулся в группу — права вернулись. Через неё ходят `/ratelimit`, `/review_on|off`, `/unignore`, `/cost` в группе,
  реестр настроек (`_check_change` → `can_change(is_chat_admin=…)`) и будущее мини-приложение, поэтому управляющие получили права сразу везде.
- **`is_real_chat_admin`** — то же БЕЗ управляющих: админ бота или администратор/создатель в Telegram. Только для выдачи и снятия прав
  (`/manager add|rm`): управляющий других не назначает. **Инвариант:** выдача прав — только `is_real_chat_admin`.
- **Команды** (только группы): `/manager add|rm` (ответом на сообщение или `<user_id>`; выдают и снимают настоящие админы), `/managers` (список:
  имя по последней реплике, uid, кто и когда добавил; смотрят все админы чата, включая управляющих). Админа бота и уже-админа Telegram
  добавлять не нужно («и так админ», строка не пишется); бота — нельзя. По `<user_id>` участник должен находиться запросом `get_chat_member`
  (опечатка в ID не выдаёт права постороннему).
- **Что реально отдаёт Telegram (стенд, 2026-11-01):** участник, которого админ чата ограничил в интерфейсе («Restricted by …», все права выключены, на сутки), у `getChatMember` пришёл как `status: member` — без `is_member` и `until_date` (проверено на двух аккаунтах, в окне через ~5 минут и позже). Статус `restricted` мы живьём не получили, ветка `restricted` в `is_chat_admin` проверена только юнит-тестом с подменой; на поведение это не влияет (`member` и `restricted` трактуются одинаково). Вышедший (`left`) приходит как `status: left` без `is_member`, строка `chat_managers` остаётся. `kicked` живьём не проверялся.

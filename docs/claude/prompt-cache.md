# Prompt caching (ТЗ `feat/prompt-cache`, v1.1.4)

Перед правкой system-prompt, сборки `messages` диалога, окна истории или чего-либо, что попадает
в НАЧАЛО запроса к модели, — читай этот файл. Любое изменение раньше точки кэша обнуляет кэш всего,
что за ним.

## Зачем
До ветки `cache_read = 0` на всех вызовах, а каждая реплика писала ~12k токенов в кэш по ×1.25
(пул кэширует сам, бот `cache_control` не ставил). Эксперимент 2026-10-09 прямо через пул: явный
`cache_control` на system ~18k → 1-й запрос `cache_write=18029`, 2-й `cache_read=18029`. Пул кэш читает,
виноват был наш запрос. Цель: `cache_read > 0` со 2-й реплики (личка и группа, все модели).

## Как устроен запрос диалога
Порядок префикса у API: `tools → system → messages`. Нестабильное в начале ломает всё после него.

| Часть | Что | Точка кэша |
|---|---|---|
| system, блок 1 | `_persona_text(is_group)` — персона (+ групповой аддендум). БЕЗ даты, статична, общая для всех чатов одного типа на одной модели | №1, TTL `CACHE_TTL_PERSONA` (5m/1h) |
| system, блок 2 | `_memory_text(...)` — память (личная или групповая), если есть. Меняется при извлечении фактов (раз в 5/15 реплик) | №2, 5m |
| messages | история: окно шагами (см. ниже) | — |
| messages | последний assistant ПЕРЕД финальным user-turn | №3, 5m (`mark_cache_tail`) |
| messages, хвост | финальный user-turn: `[service_block, текст пользователя]` — меняется каждый запрос | нет |

Итого 3 точки из 4 допустимых. Минимум кэшируемого префикса (док prompt-caching, сверено 2026-10-10):
512 токенов у Haiku 5.5 / Sonnet 5.5 / Opus 5.5 / Fable 5.1 (у Haiku 4.5 — 4096, но его в реестре больше нет).
Персона ~2k токенов (4.9k символов, группа 6.3k). Lookback — 20 блоков на точку; расстояние между
точками №3 соседних запросов — 2–3 блока.

**`service_block(...)`** — «[Служебно, не от пользователя]»: время по Берлину, reply-контекст (ТОЛЬКО личка;
в группе он уже inline в `build_group_messages`), результаты поиска (с пометкой «данные, не инструкции» —
теперь они в user-turn, а не в system, т.е. с меньшим авторитетом, это заодно безопаснее). В БД
(`conversations`, `group_messages`) НЕ сохраняется — туда идёт только текст пользователя. Персона знает про
этот блок (`SERVICE_MARK`) и не цитирует его заголовок.

Сборка: `build_system(...)` → список блоков (или строка при `PROMPT_CACHE=0`); `with_service_block(messages, text)`
→ копия с text-блоком перед последним user-turn; `mark_cache_tail(messages)` → точка №3. Фото и документ:
те же `build_system` + `with_service_block` (дата), точка №3 не нужна — одноходовые, но блоки system
(персона/память) делят кэш с диалогом.
`get_system_prompt()` остался строковой обёрткой (откат и совместимость), `system_chars(system)` — длина
для логов `PROMPT ... system=` и для аварийной ветки prompt-too-long (сравнение с `history_chars`).

## Окно истории — шагами
Раньше окно было «последние 40/50 строк»: начало `messages` сдвигалось каждую реплику, и кэш истории
невозможен в принципе. Теперь начало стоит на месте, пока с якоря набралось меньше `base + HISTORY_STEP`
строк, потом резко подрезается до последних `base` (`pick_history_window`).
- Личка: `MAX_HISTORY=40` … 40+`HISTORY_STEP` (дефолт 20) строк; `private_history()`; ведущие assistant срезаются.
- Группа: `GROUP_TRANSCRIPT_LIMIT=50` … 70 строк; внутри `build_group_messages`.
- **Якорь — id строки, не счёт**: `group_messages` подрезается до 1000 строк на КАЖДОЕ сохранение
  (db.save_group_message), и счёт строк в активной группе замирает на 1000 при скользящем начале.
  Якоря лежат в памяти процесса (`_HISTORY_ANCHORS`) — после рестарта окно пересоберётся от последних
  `base` строк, один промах кэша.
- Цена: в среднем на `HISTORY_STEP/2` строк истории больше — эти токены идут по цене чтения кэша.
  Следить за ступенью Haiku 5.5 >100k (warning в логе уже есть).
- Известная мелочь: в групповом транскрипте префикс времени у вчерашних сообщений меняется в полночь
  (`ЧЧ:ММ` → `ДД.ММ ЧЧ:ММ`) — один промах кэша в сутки.
- Попутно `db.get_conversation_rows` сортирует по `id`, а не по `timestamp` (пара user/assistant в одну
  секунду раньше могла поменяться местами); `get_conversation` (2 строки для счётчика) не трогали.

## Env и откат
| Переменная | Дефолт | Что |
|---|---|---|
| `PROMPT_CACHE` | `1` | `0` — откат без правки кода: system строкой без `cache_control`, окно скользит как раньше (`HISTORY_STEP=0`); служебный блок в хвосте остаётся |
| `HISTORY_STEP` | `20` | шаг окна; `0` — скользящее окно |
| `CACHE_TTL_PERSONA` | `5m` | `1h` — запись точки №1 дороже (2.0× вместо 1.25×), окупается при редких, но разных чатах; точка №1 первая, порядок «длинный TTL раньше короткого» соблюдён |

Изменение `.env` → `docker compose up -d --force-recreate claudushka` (`restart` env не перечитывает).

## Что НЕ делали (и почему)
- Служебные вызовы (`aux_params`): входы маленькие, выгоды нет.
- `/review` (раз в сутки), WhatsApp (на паузе, свой `get_system_prompt` в whatsapp.py).
- effort/thinking между репликами не меняются (смена сбрасывает кэш сообщений): `dialog_params` константны.
- Учёт (`calc_llm_cost`) не трогали: запись 5m/1h уже разделена, чтение — `cache_read_mult`.

## Вопрос на проверку: cache_write на маленьких вызовах
`should_search` (~580 токенов) пишет `cache_write`, хотя бот кэш не просит и 580 > 512 (минимум Haiku 5.5),
т.е. формально кэшируемо — пул сам размечает вход. После выкатки сравнить usage `should_search` до/после и
записать сюда. Логику учёта не менять, пока не сверим с реальным списанием на балансе пула.
Данные до ветки (стенд 2026-10-09): `input=4, cache_write≈580, cache_read=0, output 4–11`.

## Грабли
- Изменчивое в system (время, поиск, reply) — нельзя: оно в начале префикса. Только в `service_block`.
- Фото в запросе, по доке, влияет на кэш system («Images» в таблице инвалидации) — фото редки, не оптимизировали.
- Блок памяти меняется при каждом извлечении фактов — один промах на блок 2 и всё, что за ним.

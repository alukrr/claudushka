# ТЗ: профиль, вторая очередь — автодедуп сверяет факты с профилем, извлечение не дублирует профиль (issue #4)

Ветка `feat/profile-stage2`. Перед работой прочитай `docs/claude/profile.md` (в т.ч. «Профиль v2»), `docs/claude/memory.md`
(«Автоматическая дедупликация», извлечение, метки `P1…`) и `docs/claude/open-tasks.md` → «Гигиена памяти». Схема БД не меняется,
но меняются промпты извлечения и дедупа, а дедуп УДАЛЯЕТ факты — нужен стенд и прогон на копии прод-БД. Чек-лист —
`docs/claude/staging-checklist-profile-stage2.md`, пишешь сама.

## Почему
Профиль (`user_profile`) — проверенные админом поля, факты (`memory`) — то, что модель извлекла сама. Сейчас они живут отдельно:
- в фактах остаются устаревшие и противоречащие профилю вещи («живёт в Москве» при профиле «Город: Гамбург», «не женат» при
  «Семья: муж; …»), модель видит обе версии и путается;
- извлечение пишет в факты то же, что уже есть в профиле (имя, город, профессия) — дубль занимает место в блоке памяти
  (в самом большом чате ~74 тыс. знаков фактов против ~600 знаков профилей).
Это исходная цель профиля (`docs/claude/profile.md` → «Не входит»).

## Часть 1. Дедуп видит профиль

### Данные
- В `dedup_memory.py` — функция `load_profiles(conn) -> dict[(user_id, context, chat_id), str]`: подтверждённый профиль в
  виде «Поле: значение; …» (как `_profile_text`, теми же подписями полей; в личке `chat_id = 0`, НЕ NULL). Ожидающие
  предложения (`profile_proposals` pending) НЕ брать — только подтверждённое.
- Профиль к группе фактов — по ключу группы (`GroupKey`: `user_id`, `context`, `chat_id`). Нет профиля — группа идёт как
  сейчас, ничего не меняется.
- Лимит: профиль уже ≤ `PROFILE_TOTAL_MAX` (1200); в запрос — не больше этого, с обрезкой целыми полями (инвариант размера).

### Запрос
- Профиль кладётся в user-сообщение, НЕ в `SYSTEM_PROMPT` (system общий для всех групп). Формат с профилем:
  `{"profile": "Город: Гамбург; Семья: муж; …", "facts": [...]}`; без профиля — как сейчас, голый JSON-список (калибровка
  `load_calibration`/`estimate_group` для групп без профиля не меняется; оценку для групп с профилем увеличить на длину профиля).
- Отдельный системный промпт для варианта с профилем — `SYSTEM_PROMPT_PROFILE` (дополняет `SYSTEM_PROMPT`):
  «profile — проверенные данные о человеке, они ВЕРНЫ. Факт, который ПРЯМО противоречит профилю, удали. Факт, который
  только повторяет профиль (то же имя, город, профессия, тот же член семьи), удали — он уже есть в профиле. Факт, который
  уточняет или дополняет профиль, оставь. При сомнении — оставь. Верни {"facts": [...], "dropped_by_profile": [...]} —
  во втором списке дословно те исходные факты, которые удалены из-за профиля».
- Большие группы по частям (`plan_chunks`): профиль — в каждый кусок и в вызов слияния.

### Применение и страховка
- `dropped_by_profile` — только для отчёта: в `GroupResult` новое поле (список), берём лишь строки, которые ДОСЛОВНО есть
  среди исходных фактов группы; остальное игнорировать.
- Страховки автодедупа (`DEDUP_AUTO_MIN_KEEP`, `DEDUP_AUTO_MIN_KEEP_ABS`, бюджет) — как есть. Дополнительно: если
  `dropped_by_profile` > 30% фактов группы — группу НЕ применять, в отчёт «подозрительно много удалений по профилю»
  (константа `DEDUP_PROFILE_MAX_DROP = 0.3`).
- Отчёт автодедупа (`/dedup_auto`, понедельник) — строка «по профилю удалено N фактов» по группе и общий итог; сами
  удалённые факты — в файл-отчёт прогона (`save_run`), не в Telegram (могут быть личными).
- dedup TUI: на экране результата группы — пометка у фактов из `dropped_by_profile` («✗ профиль»), чтобы Алексей видел
  причину при ручном прогоне.
- Режим `estimate` (сейчас включён на проде) ничего не удаляет — новое поведение начнёт работать, только когда Алексей включит
  `apply`.

## Часть 2. Извлечение не дублирует профиль
- Текущий профиль в запрос извлечения уже идёт (`_profile_prompt_text`, для `profile_updates`). Добавить правило к ФАКТАМ в
  промпты извлечения (группа — `extract_all_participants_memory`, личка — `_extract_private_raw`): «Не записывай в facts то,
  что уже есть в профиле человека или что ты сейчас кладёшь в profile_updates (имя, пол, год рождения, город, профессия,
  хобби, семья, как общаться). Новое, чего нет в профиле, — записывай как обычно».
- Кодом НЕ фильтровать (сравнение строк ненадёжно) — только промпт. На стенде замерить эффект.
- Найди grep'ом все места, где собирается промпт извлечения фактов (в т.ч. `/memory_backfill`), и перечисли в отчёте.

## Не входит
- Автоматическое изменение профиля по фактам (профиль меняет только админ через `db.apply_profile_ops`).
- Чистка уже накопленных дублей профиля в фактах отдельным прогоном — её сделает часть 1 при обычном автодедупе.
- Первичное заполнение профилей из фактов; правка профиля самим человеком.

## Тесты (локально, без сети)
- `load_profiles`: группа и личка (`chat_id=0`), пустой профиль → нет ключа, pending не попадает.
- Сборка запроса: с профилем — объект с `profile`/`facts` и `SYSTEM_PROMPT_PROFILE`; без — прежний список и `SYSTEM_PROMPT`
  (байт в байт как раньше).
- Разбор ответа: `dropped_by_profile` с недословной строкой — отброшена; отсутствует — пустой список; > 30% — группа не
  применяется, причина в отчёте.
- Куски: профиль есть в каждом куске и в слиянии (замоканный клиент).
- Промпты извлечения содержат новое правило (группа и личка).

## Стенд (чек-лист)
- Копия прод-БД: `dedup` (TUI) по 3–5 группам людей с профилем — до/после, какие факты ушли «по профилю», нет ли лишнего.
- `/dedup_auto run` в `estimate` и в `apply` на копии: отчёт, страховка 30%.
- Извлечение: тестовая группа, человек с профилем «Город: X» пишет «я из X» — факт не появляется, предложения профиля нет
  (уже есть); пишет новое — факт появляется.

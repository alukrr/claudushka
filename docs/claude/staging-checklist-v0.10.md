### 0.2. Как делать SELECT: через что и откуда
В контейнере нет утилиты `sqlite3`, зато есть Python с модулем `sqlite3`. Поэтому запросы идут так:
**на сервере** → `docker exec` в контейнер `claudushka-test` → Python читает файл БД `/app/data/claudushka.db`
(на диске сервера это `~/claudushka-test/data-test/claudushka.db`, папка примонтирована в контейнер).

Чтобы не набирать это каждый раз, один раз **на сервере** вставьте в терминал две функции (они живут, пока открыт
этот сеанс SSH; при новом подключении вставить заново):

```bash
# q "SELECT ..."  — читать
q() { docker exec claudushka-test python3 -c "
import sqlite3, sys
c = sqlite3.connect('/app/data/claudushka.db'); c.row_factory = sqlite3.Row
for r in c.execute(sys.argv[1]): print(dict(r))
" "$1"; }

# qw "UPDATE ..." — писать (INSERT/UPDATE/DELETE), с коммитом
qw() { docker exec claudushka-test python3 -c "
import sqlite3, sys
c = sqlite3.connect('/app/data/claudushka.db')
n = c.execute(sys.argv[1]).rowcount; c.commit(); print('изменено строк:', n)
" "$1"; }

# логи бота: последние N строк или с фильтром
logs() { docker logs claudushka-test 2>&1 | tail -${1:-60}; }
```

Проверка, что всё работает: `q "SELECT COUNT(*) AS n FROM usage_log"` → выведет `{'n': 0}` или число.
Если ошибка «no such table» — бот ещё не стартовал полностью (`logs 30`). «No such container» — стенд не поднят.

Три вещи, которые понадобятся во многих сценариях:

| Что | Как узнать |
|---|---|
| `GID` — id тестовой группы (число с минусом) | в группе написать `/id` — бот ответит `Chat ID: -100…` |
| `UID` — id вашего второго (не админ) аккаунта | ему в личке с ботом написать `/id` — `User ID: …` |
| Сегодняшняя дата по Берлину (нужна для `daily_usage`) | на сервере: `TZ=Europe/Berlin date +%F` |

Дальше в командах `GID` и `UID` — подставляйте свои числа. Перед началом удобно один раз заменить их в терминале:
`GID=-100123...; UID=987...` и писать `$GID` / `$UID` (в `q "..."` внутри двойных кавычек bash подставит значения сам).

## B1. Вызовы привязаны к чату (самое важное)

Если тут у служебных вызовов `chat_id = NULL` — остановиться и прислать мне логи, дальше не идти (правило ТЗ п.2:
не обходить костылём).

| Шаг | Где | Что делаю | Ожидание |
|---|---|---|---|
| 1 | TG-админ | В тестовой группе написать боту, чтобы он ответил: `Клодушка, какая сегодня погода в Берлине?` (слово «погода» включает веб-поиск) | Бот отвечает в группе |
| 2 | TG-админ | Написать в группе ещё ~15 обычных сообщений (можно без обращения к боту) — так срабатывает фоновое извлечение памяти (раз в 15 реплик) | Ответов нет, это нормально |
| 3 | TG-админ | Написать: `Клодушка, нарисуй кота` | Приходит картинка |
| 4 | Сервер | `q "SELECT id, chat_id, chat_type, user_id, kind, label, billed, cost_usd FROM usage_log ORDER BY id DESC LIMIT 15"` | Строки с `label` = `dialog`, `should_search`, `search`, `draw_translate`, `image`, `extract_chat_memory` — у всех `chat_id` = ваш `GID`, `chat_type` = `group` |
| 5 | Сервер | `q "SELECT COUNT(*) AS без_чата FROM usage_log WHERE chat_id IS NULL AND label IN ('dialog','should_search','extract_chat_memory','draw_translate')"` | `0`. Строки без чата (`svc`, `aux`) допустимы только у вызовов вне апдейта, таких у нас практически нет |
| 6 | Сервер | `q "SELECT billed, COUNT(*) AS n FROM usage_log GROUP BY billed"` | Пока группа без баланса — все `billed = 0` (free) |

## B3. Уход в ноль: writeoff и сообщение

Цель — чтобы траты превысили баланс, и в базе появился `writeoff`. Для этого нужен маленький баланс.

| Шаг | Где | Что делаю | Ожидание |
|---|---|---|---|
| 1 | TG-админ | Свежий чат для теста: создать вторую тестовую группу (или использовать личку второго аккаунта: тогда `ID` = его `UID`). Дальше `X` — этот ID | — |
| 2 | TG-админ | `/topup X 0.005 force` (ровно столько, чтобы один-два ответа Sonnet «съели» баланс; `force` — чтобы ID был принят, если он ещё не в базе) | `Баланс: $0.01`, режим платный |
| 3 | TG-юзер/группа | В чате X написать боту 1–3 сообщения, пока не придёт `Баланс закончился, я перешла в бесплатный режим…` | Это сообщение приходит **один раз** |
| 4 | Сервер | `q "SELECT kind, amount, note FROM chat_credits WHERE chat_id=X ORDER BY id"` | Есть строка `writeoff` с `note='auto'`, сумма ≈ насколько ответ превысил остаток |
| 5 | Сервер | `q "SELECT ts, label, billed, cost_usd FROM usage_log WHERE chat_id=X ORDER BY id DESC LIMIT 5"` | Последний платный ответ `billed=1`, следующие — `billed=0` |
| 6 | TG-админ | `/cost X` | Баланс `$0.00`, режим `бесплатный` |
| 7 | TG-юзер/группа | Ещё одно сообщение боту | Отвечает Haiku (в логе `PROMPT … model=claude-haiku-4-5`), повторного «Баланс закончился» нет |

Проверить точный ноль без writeoff: `/topup X 1`, затем `/topup X -1` → в ответе `Баланс: $0.00`, режим бесплатный,
в чат пришло то же «Баланс закончился…». Строки writeoff при этом нет (баланс не уходил в минус).

## B5. Дневной лимит картинок в free

Личка free (10/сутки) и группа (5 на участника).

| Шаг | Где | Что делаю | Ожидание |
|---|---|---|---|
| 1 | TG-юзер | В free-личке: `нарисуй кота` | Приходит картинка, подпись `Модель: GPT Image 2` |
| 2 | Сервер | Проверка счётчика: `q "SELECT COUNT(*) AS n FROM usage_log WHERE kind='image' AND billed=0 AND chat_id=X AND ts >= strftime('%s','now','start of day')"` | `1` (границей суток в SQL служит UTC-полночь, это грубая проверка; сам бот считает по Берлину) |
| 3 | Сервер | **Чтобы не рисовать 10 раз:** добавить 9 недостающих строк: `for i in 1 2 3 4 5 6 7 8 9; do qw "INSERT INTO usage_log (ts,chat_id,chat_type,user_id,kind,model,label,cost_usd,billed) VALUES (strftime('%s','now'),X,'private',X,'image','gpt','image',0.02,0)"; done` (подставьте `X`; для личных чатов `chat_id` = `user_id`) | — |
| 4 | TG-юзер | `нарисуй собаку` | Ответ: `Лимит картинок на сегодня исчерпан (10/10). Сброс в 00:00 по Берлину, через N ч M мин…`, картинки нет |
| 5 | TG-юзер | `/imagine космос` | То же сообщение о лимите |
| 6 | Группа | В тестовой группе (free) от юзера 5 раз `нарисуй …` (или добавить 5 строк INSERT с `chat_type='group'` и `user_id=UID`), шестая — отказ; тот же запрос от другого участника — проходит | Лимит считается на участника, а не на группу |
| 7 | — | Спонтанный `[[DRAW]]` (бот сам решает нарисовать) вызвать вручную нельзя. Проверка косвенная: при исчерпанном лимите и вопросе вроде «покажи, как выглядит закат» бот отвечает текстом, в чате нет строки `[[DRAW…` | Маркера в тексте нет, картинки нет |
| 8 | TG-админ | Админ в тех же условиях лимита не имеет (личный чат админа всегда paid) | — |

## B6. Лимиты непроверенных в личке

Проверяем на **TG-юзер**, аккаунт которого не проверен. Убедитесь: `q "SELECT telegram_id, role FROM users WHERE telegram_id=$UID"` → `role='street'`. Если он `premium`, сделайте `/unverify <UID>`.

| Шаг | Где | Что делаю | Ожидание |
|---|---|---|---|
| 1 | TG-юзер | Написать боту в личку пару сообщений | Бот отвечает |
| 2 | Сервер | `q "SELECT * FROM daily_usage WHERE chat_id=$UID"` | Строка: `day` = сегодня по Берлину, `msgs` = число ответов бота (не ваших сообщений: если бот не ответил, счётчик не растёт) |
| 3 | Сервер | **Чтобы не писать 50 раз:** выставить счётчик на 49: `qw "UPDATE daily_usage SET msgs=49 WHERE chat_id=$UID AND user_id=$UID AND day='$(TZ=Europe/Berlin date +%F)'"` | `изменено строк: 1` |
| 4 | TG-юзер | Одно сообщение (пятидесятое) | Бот отвечает |
| 5 | TG-юзер | Ещё одно | Бот отвечает **один раз** текстом: `Дневной лимит для непроверенных исчерпан, сброс в 00:00. Снять лимиты навсегда: пополнить баланс от $5 или написать @alukr.` |
| 6 | TG-юзер | Ещё 2–3 сообщения | Тишина, бот не отвечает |
| 7 | Сервер | `q "SELECT msgs, limit_notified FROM daily_usage WHERE chat_id=$UID"` | `msgs=50`, `limit_notified=1` |
| 8 | Сервер | Поиск: вставить 20 записей поиска: `for i in $(seq 20); do qw "INSERT INTO usage_log (ts,chat_id,chat_type,user_id,kind,model,label,cost_usd,billed) VALUES (strftime('%s','now'),$UID,'private',$UID,'search','tavily','search',0.008,0)"; done`; сбросить счётчик сообщений: `qw "UPDATE daily_usage SET msgs=0, limit_notified=0 WHERE chat_id=$UID"` | — |
| 9 | TG-юзер | `Клодушка, какой курс евро сегодня?` | Бот отвечает без поиска (тихо, никакого предупреждения). В логе нет `web_search` для этого сообщения |
| 10 | TG-юзер | `/search курс евро` (явная команда) | Ответ: `Дневной лимит поиска для непроверенных исчерпан (20)…` |
| 11 | TG-админ | `/verify <UID>` и сообщение от юзера | Лимитов больше нет (в том числе в `/cost` у него пропала строка «сообщений сегодня») |

## B11. Ежедневный обзор на Opus

Обзор запускает не команда, а расписание: раз в сутки в **22:00 по Берлину**. Вручную его не вызвать (`/review` — это
другая, разовая функция со старым промптом). Значит:

| Шаг | Где | Что делаю | Ожидание |
|---|---|---|---|
| 1 | TG-админ | Убедиться, что группа платная и включён флаг: `/cost` в группе → `Режим: платный`; `q "SELECT chat_id, daily_review_enabled, banned FROM allowed_chats WHERE chat_id=$GID"` → `1, 0` | — |
| 2 | Группа | В тот же день до 22:00 написать в группе не меньше 5 сообщений (обзор берёт только сообщения за сегодня по Берлину) | — |
| 3 | Сервер | Проверка, что сообщения на месте: `q "SELECT COUNT(*) AS n FROM group_messages WHERE chat_id=$GID AND timestamp >= strftime('%s','now','start of day','-2 hours')"` | ≥ 5 |
| 4 | — | Стенд должен быть поднят в 22:00 по Берлину (в 20:00 UTC летом). **Внимание:** любой другой чат в тестовой БД, где есть баланс, тоже получит обзор — на пустой БД такой один | — |
| 5 | Группа | После 22:00 | Приходит обзор ~1000–1200 знаков, последней строкой отдельно: `Отключить ежедневный обзор: /review_off (админ чата)` |
| 6 | Сервер | `q "SELECT model, label, billed, cost_usd, chat_id FROM usage_log WHERE label='daily_review'"` | `model='claude-opus-5'`, `billed=1`, `chat_id=GID` |
| 7 | Сервер | Обзор в транскрипте без хвоста про `/review_off`: `q "SELECT content FROM group_messages WHERE chat_id=$GID AND is_bot=1 ORDER BY id DESC LIMIT 1"` | Текст обзора без последней служебной строки |
| 8 | Группа | **Отрицательный тест:** в free-группе (после B3) или в молчавшей несколько дней (нет сегодняшних сообщений) обзор не приходит | Обзора нет, в `usage_log` нет `daily_review` для этого чата |

Не хотите ждать вечера: пропустите B11 на стенде и проверьте на проде после деплоя (в первую же ночь), но тогда заранее
предупредите админов чатов, что с этого момента обзор идёт на Opus.

# ТЗ: самовосстановление чата после safety-блока провайдера (`feat/safety-unblock`)

Статус: реализовано в ветке `feat/safety-unblock` (описание — `safety-unblock.md`; отличие от ТЗ: поиск идёт без сдвига
окна, сдвиг — только в финальной проверке). Целевая версия: **v2.1.0** (новая колонка в `group_messages` + новые админ-команды → minor, стенд
обязателен — `docs/claude/staging.md`). Тег — один, на всё ТЗ, ставит Алексей.

## Зачем

Пул отвечает `400 blocked by provider safety policy`, если в ЗАПРОСЕ есть текст, который режет фильтр провайдера
(`api_errors.is_safety_block`). Запрос диалога в группе несёт окно истории (`build_group_messages`, 50 реплик), поэтому одна
«плохая» строка в `group_messages` блокирует ВЕСЬ чат на любой вопрос, пока не уйдёт из окна (десятки сообщений) или пока
Алексей не удалит её руками на сервере. Было дважды за два дня:

- 2026-10-30 — обзор «Вестник» (`docs/claude/incidents.md`);
- 2026-10-31 — кусок реплики Клодушки, вставленный участниками 5 раз; сама реплика целиком фильтр проходила
  (`docs/claude/incidents.md`). Вывод: виновником может быть ЛЮБАЯ строка, не только обзор.

Ручной разбор (бисекция replay'ем настоящего запроса) оба раза сработал однозначно. Задача — чтобы бот делал это сам и
не удалял ничего.

## Часть A — повтор без истории (сразу, на первой же блокировке)

Место: основной диалог в `handle_message` (bot.py, блок `except anthropic.BadRequestError` после `call_claude(... label=f"диалог
chat=...")`; сейчас там обрабатывается только `is_prompt_too_long`, остальное `raise` → `reply_api_error`).

1. Если `api_errors.is_safety_block(e)` — ОДИН повтор:
   - группа: `messages` = только последний user-turn из уже собранных (`base_messages[-1]` — склейка реплик людей с
     триггером), через тот же `compose(...)` (служебный блок, `mark_cache_tail`); `system` — тот же (с памятью);
   - личка: `messages` = только текущий `user_text` через `compose`.
   - Вызов — `call_claude(..., label=f"диалог chat={chat_id} (без истории, safety)", usage_label="dialog", model=_model,
     **dialog_params(_model), max_tokens=out_tokens(_model, 4096), ...)`. Фолбэк не трогать (400 его и так не включает).
2. Повтор прошёл — отвечаем как обычно (сохранение в `group_messages`/историю, `_count_reply` — тем же путём, что основной
   ответ; не дублировать код, вынести общий хвост, если нужно). Пользователю ничего дополнительно не пишем.
3. Повтор тоже `is_safety_block` — `reply_api_error` как сейчас (текст «Фильтр модели заблокировал запрос…» уже есть).
   Значит, виновата память, system или сама реплика-триггер — это ловит Часть B (триггер) или Алексей руками (память).
4. Логи: `logger.warning("SAFETY BLOCK chat=... uid=... model=... | повтор без истории: ok|blocked")`. Текст сообщений в
   лог НЕ писать.
5. `reply_context` в группе уже вшит в последний user-turn — оставить как есть (если виноват процитированный текст, повтор
   тоже заблокируется — это нормально, см. п. 3).

Фото/файл (`label=f"фото ..."`, `f"файл ..."`) — не трогать в этом ТЗ, отметить в отчёте как не сделанное.

## Часть B — фоновый поиск виновной строки и её скрытие (только группа)

### B1. Схема

- `group_messages.hidden INTEGER NOT NULL DEFAULT 0` — миграция `ALTER TABLE` в общий список миграций db.py (как
  `is_bot`), идемпотентно. `hidden=1` — строка не уходит ни в один промпт, но физически остаётся (обратимо).
- Фильтр `hidden = 0` добавить во ВСЕ чтения `group_messages`, которые идут в модель: `get_group_transcript` (диалог и
  `extract_all_participants_memory`), `get_group_messages_range` (дневной обзор/`/review` — Argon за весь день упрётся в ту же
  строку), `get_group_history`. Проверить grep'ом, что других чтений нет. Очистка по `GROUP_MESSAGES_KEEP` — как раньше
  (скрытые тоже считаются и вытесняются).
- Новые функции db.py: `hide_group_messages(chat_id, ids) -> int`, `unhide_group_message(chat_id, id) -> bool`,
  `list_hidden_group_messages(chat_id, limit=20) -> list[dict]` (id, sender_name, is_bot, timestamp, length — без текста),
  `group_message_ids_with_same_content(chat_id, ids) -> list[int]` (точные дубли по `content`, только `hidden=0`).
- Обновить `.claude/rules/db.md`.

### B2. Когда запускается

- Счётчик в памяти процесса `_safety_strikes: dict[chat_id, int]`: +1 на каждый `is_safety_block` ПЕРВОГО (полного) запроса
  диалога в группе (Часть A, до повтора); сброс в 0 на успешный полный запрос. Успех повтора без истории счётчик НЕ сбрасывает.
- На `>= SAFETY_SCAN_STRIKES` (env, по умолчанию 2) — запустить скан через `_spawn_background_task` (не голый
  `create_task`), если для этого чата скан сейчас не идёт (`_safety_scan_running: set`) и с прошлого скана прошло не меньше
  `SAFETY_SCAN_COOLDOWN_MIN` (env, по умолчанию 30). После запуска счётчик в 0.
- `usage_ctx` в фоновой задаче выставить явно на этот чат (как в джобах) — расход скана пишется на чат.

### B3. Алгоритм скана — `async def safety_scan(chat_id, user_id)`

Ключевое (грабли 2026-10-31): проверять только НАСТОЯЩИЙ запрос, собранный кодом бота, и «удаление» имитировать
исключением строк из чтения — окно при этом сдвигается на более старые строки, как после реального скрытия. Упрощённый
транскрипт «последние N строк» давал противоречивые результаты.

1. `probe(excluded: set[int]) -> bool` (True = заблокировано): собрать `system = build_system(user_id, True, chat_id)` и
   `messages` через `build_group_messages(chat_id, "", GROUP_TRANSCRIPT_LIMIT, exclude_ids=excluded)` + `with_service_block`
   (пустой `service_block`) + `mark_cache_tail` — то есть ровно как в диалоге. Для этого добавить в `build_group_messages` и
   `db.get_group_transcript` необязательный параметр `exclude_ids` (SQL `id NOT IN (...)`, лимит прежний — окно само
   сдвигается). `pick_history_window` для проб вызывать так, чтобы не портить его состояние для живого диалога (проверить,
   хранит ли он состояние по ключу; если да — отдельный ключ, например `("gscan", chat_id)`).
   Вызов — `call_claude(context, chat_id, label=f"safety_scan chat={chat_id}", usage_label="safety_scan", fallback=False,
   model=get_chat_model(chat_id), **dialog_params(...), max_tokens=out_tokens(model, 256), system=..., messages=...)`.
   Ретраи 529/429 — как обычно в обёртке. Фильтр на пороге и срабатывает не каждый раз → каждая проба до
   `SAFETY_SCAN_ATTEMPTS` (2) попыток: заблокировано, если заблокирована ХОТЬ ОДНА. Успешный ответ модели не используется.
2. Подтверждение: `probe(set())` — если не заблокировано, конец («не воспроизвелось», уведомление не шлём, только лог).
3. Кандидаты `C` = id строк текущего окна (как их выдаёт `pick_history_window`), включая триггер.
4. `probe(C)` (всё окно исключено, в окно приехали старые строки): если всё ещё заблокировано — виноваты память/system или
   старые строки; конец, уведомление админам «скан не нашёл виновную строку в окне — вероятно, память; смотреть руками».
5. Поиск минимального набора через ИСКЛЮЧЕНИЕ (не «половина отдельно» — так комбинации не ловятся):
   ```
   find(cands, base):            # base — уже исключённые; известно: probe(base ∪ cands) == False
       if len(cands) == 1: return cands
       A, B = половины cands
       if not probe(base ∪ A): return find(A, base)
       if not probe(base ∪ B): return find(B, base)
       # виноваты строки в обеих половинах
       fa = find(A, base ∪ B)
       return fa ∪ find(B, base ∪ fa)
   ```
   Бюджет — `SAFETY_SCAN_MAX_CALLS` (env, по умолчанию 40 вызовов API, считать каждую попытку). Исчерпан — конец без
   скрытия, уведомление «бюджет исчерпан, найдено частично: …».
6. Найденный набор `F` расширить точными дублями (`group_message_ids_with_same_content`) — 2026-10-31 это были 4 одинаковые
   вставки. Финальная проверка `probe(F)` == False; если заблокировано — не скрывать, уведомить.
7. Скрыть: `db.hide_group_messages(chat_id, F)`. Уведомить админов (`notify_admins`): название чата, chat_id, сколько строк
   скрыто, по каждой — id, автор (имя/бот), время Berlin, длина; сколько вызовов потрачено; подсказка `/unhide <id>`.
   **Текст строк в уведомлении и логах не выводить** (Алексей разбирает инциденты в сессиях Claude Code — сам текст может
   оборвать сессию).
8. В чат ничего не писать.

Ограничение на размер: пробы — того же размера, что обычный запрос диалога, новых источников в промпт нет.
Стоимость: 2026-10-31 весь ручной разбор — ~120 вызовов, из них на нормальную бисекцию ушло ~20; бюджет 40 с запасом.
На free-чате модель — Lite (`get_chat_model`), это нормально: проверяем тот запрос, который реально падает.

## Чего НЕ делать

- Не трогать память (`memory`), профиль, `conversations` — если виновата память, это ручная работа Алексея.
- Не добавлять текст строк в логи/уведомления/`/hidden`.
- Не вызывать `client.messages.create` напрямую — только `call_claude` (учёт расхода, ретраи); `fallback=False` у проб.
- Не менять Часть A в фото/файлах, личке (кроме п. A1 «личка»), WhatsApp.

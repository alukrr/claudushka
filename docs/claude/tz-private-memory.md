# ТЗ: личная память — починить извлечение и обработать старые треды (`fix/private-memory-extract`, затем `feat/memory-backfill`)

Постановка Алексея 2026-11-12: в dedup TUI не видно личек. Причина не в инструменте: **личных фактов в базе нет ни одного** —
извлечение памяти в личке ни разу не сработало.

ТЗ для отдельной сессии: **сначала `CLAUDE.md` целиком**, затем `docs/claude/memory.md`, `docs/claude/profile.md`,
`docs/claude/billing.md`, `docs/claude/models-and-costs.md`, `docs/claude/api-errors.md`, `.claude/rules/db.md`.
Две части — две ветки и две сессии. Часть 2 начинать только после того, как часть 1 на проде и Алексей сказал «да».

## Что выяснено (прод, 2026-11-12, только чтение)
- `memory`: 4308 строк, все `context='group'`. Строк `context='private'` нет и не было ни в одной копии базы с 2026-07-26.
- `usage_log` с 2026-09-20: 5880 строк `extract_chat_memory` и ни одной `extract_memory`. В логах контейнера за 10 дней —
  ни «Memory updated for», ни «Memory extraction error».
- Личных тредов 50, всего 5802 реплики, самый длинный — 1156. Длина каждого треда чётная.
- **Причина:** условие в `handle_message` (`bot.py`, рядом с комментарием «Память: личка — из личного треда по каденсу»):
  `msg_count = len(messages)`; `msg_count % (MEMORY_EXTRACT_EVERY * 2) == 0`. `messages` здесь — `private_history(user_id)`
  (пары «вопрос–ответ», чётное число) плюс текущая реплика, то есть длина всегда нечётная и на 10 не делится никогда.
- Следствие: ветка `extract_memory` (промпт, разбор JSON, `profile_updates` для лички) на проде не исполнялась ни разу.

## Решения Алексея
1. Чинить. Личное извлечение должно работать, как описано в `docs/claude/memory.md`.
2. Старые треды обработать разово (часть 2), чтобы факты появились и их можно было чистить в dedup TUI.

## Часть 1. Починка — `fix/private-memory-extract`

### Что сделать
1. **Каденс по базе, а не по окну истории.** Новый помощник `_maybe_extract_private_memory(user_id)`:
   `n = db.count_conversation(user_id)`; запуск, если `n >= MEMORY_EXTRACT_EVERY * 2` и `n % (MEMORY_EXTRACT_EVERY * 2) < 2`
   (последняя пара пересекла кратное 10; условие верно при любой чётности треда). Окно истории для каденса не использовать:
   оно ходит шагами и немонотонно (тот же класс ошибки, что `count_chat_messages`, `.claude/rules/db.md`).
2. **Звать помощник после КАЖДОГО сохранения пары в личке** — во всех местах, где идут два `db.save_message(user_id, …)` подряд
   (основной диалог, ответ на фото и файлы `_finish_media_answer`, ветка рисования). Найти их grep'ом и перечислить в отчёте.
   Запуск — как сейчас: `_spawn_background_task(asyncio.to_thread(...))`. Режим разработчика (`dev_messages`) не трогать.
3. **Что отдаём модели.** Не `messages[-6:]` из окна, а последние `MEMORY_EXTRACT_EVERY * 2` строк треда из базы
   (`db.get_conversation`) — сейчас 4 реплики из каждых 10 модель не видела бы вовсе. **Лимит по размеру** (инвариант): каждая
   реплика режется до `MEMORY_EXTRACT_MSG_CHARS = 1500` знаков, всё вместе — не больше `MEMORY_EXTRACT_TOTAL_CHARS = 12000`.
4. **Промпт `extract_memory`:** добавить одно правило — факты брать только из реплик пользователя (`role=user`); реплики
   `assistant` — только контекст, из них ничего не записывать (в группе реплики бота из извлечения убраны по той же причине,
   инцидент 2026-09-28). Остальной текст промпта не менять.
5. Параметр `messages` у `extract_memory` оставить (его использует часть 2), параметры `is_group`/`chat_id` не трогать.

## Часть 2. Старые треды — `feat/memory-backfill`

Разовая обработка накопленных личных тредов: ~5800 реплик, около 300 вызовов Lite, по оценке 20–40 минут подряд.

### Предложения, которые Алексей подтверждает до начала (в ТЗ стоят значения по умолчанию)
- **Кто платит:** не пользователи. `usage_ctx` ставится явно на личный чат админа, запустившего команду; метка `memory_backfill`.
- **Глубина:** треды целиком, от старых реплик к новым. Устаревшее потом чистится в dedup TUI.
- **Профиль:** обработка пишет только факты; предложения профиля (`profile_updates`) отбрасывает, чтобы не завалить
  еженедельный дайджест сотнями предложений по старым репликам.

### Что сделать
1. **Команда админа бота `/memory_backfill`, только в личке:** без аргументов — справка и состояние; `dry` — сколько людей, реплик
   и вызовов предстоит, ничего не вызывая; `run` — старт в фоне (`_spawn_background_task`); `stop` — остановка после текущего вызова.
   Второй `run` при работающей обработке — отказ.
2. **Обработка:** люди по очереди, у каждого — строки `conversations` по возрастанию `id` кусками по `MEMORY_BACKFILL_CHUNK = 20`
   с теми же лимитами размера, что в части 1. Каждый кусок — тот же вызов и тот же промпт, что `extract_memory` (общая функция,
   не копия промпта), `DEFAULT_MODEL_ID`, через обёртку, фолбэк не отключать. Вызовы строго по одному, между ними пауза
   `MEMORY_BACKFILL_PAUSE = 1.0` с — бот в это время отвечает людям. Блокирующее — в `asyncio.to_thread`.
3. **Продолжение после перезапуска и защита от повтора:** отметка «до какого `id` обработан человек» в `data/memory_backfill.json`
   (запись через временный файл и `os.replace`). Повторный `run` продолжает с отметок; обработанное заново не оплачивается.
   Кусок с ошибкой модели — в лог, отметку не двигать, перейти к следующему человеку; три ошибки подряд — остановиться.
4. **Отчёт админу** в личку: при старте, каждые 50 вызовов и в конце — людей и кусков обработано, фактов добавлено, ошибок, расход.
   Сырой текст исключений не слать.
5. Запись фактов — `db.add_memory_facts(user_id, facts, "private", None)` (точные повторы она отсекает сама). Групповые факты,
   профиль и `conversations` не менять.
6. `ADMIN_HELP`, `README.md`. В `USER_HELP` не добавлять.

### Тесты
`scripts/test_memory_backfill.py`, без сети: `dry` ничего не вызывает; порядок кусков; отметка сохраняется и переживает «перезапуск»;
повторный `run` не трогает обработанное; `stop`; ошибка куска не двигает отметку; три ошибки подряд останавливают; предложения
профиля не пишутся; расход — на чат админа с меткой `memory_backfill`; команда не работает в группе и у не-админа.

`run` на 2–3 людях, `stop`, перезапуск контейнера, продолжение). **minor: v2.14.0** (если джоб чистки копий уже занял этот номер —

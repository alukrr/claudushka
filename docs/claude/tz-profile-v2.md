# ТЗ: профиль участника v2 — дополнять, а не затирать; профиль в разговоре и в `/memory`

Ветка `feat/profile-v2`. Перед работой прочитай `docs/claude/profile.md` (схема, дайджест, TUI) и `docs/claude/memory.md`.
Есть изменение схемы (новая колонка), поэтому нужен стенд. Чек-лист стенда — `docs/claude/staging-checklist-profile-v2.md`,
пишешь его сама по образцу соседних.

## Почему (замеры на проде 2026-11-22, только чтение)
1. **Многозначные поля затираются.** Модель предлагает в `value` только новое («есть дочь»), а `approve` пишет его вместо
   старого. Уже потеряны три значения у двух человек (поля `family` и `hobbies`; кто именно — у Алексея, в репозиторий не
   пишем). Пример формы: «Семья: муж; взрослая дочь» → после двух дайджестов «муж». В дайджесте #5 ещё 10 таких
   предложений ждут решения. Однажды модель сама дала полный список («A, B, C» поверх «A, B»), так что полагаться на
   промпт нельзя: склейку делает код.
2. **Профиль почти не виден модели.** Он идёт в system, но это ~30 знаков на человека (в самом большом чате ~600 знаков
   профилей на 20 человек против ~74 тыс. знаков фактов на 39 человек). Это одна строка в начале большого блока, и модель на
   неё не опирается: даже `name` и `communication` («как со мной общаться») не доходят до ответа.
3. `/memory` профиль не показывает, видно только командой `/profile`.

## Что сделать

### 1. Многозначные поля: дополнять (главное)
- Многозначные поля — `nicknames`, `hobbies`, `family`, `communication` (константа `db.PROFILE_LIST_FIELDS`).
  Остальные (`name`, `gender`, `birth_year`, `city`, `profession`) — заменяются, как сейчас.
- `profile_updates` получает необязательное `"op": "add" | "replace"`. Для многозначных по умолчанию `add`, для
  остальных всегда `replace` (`op` от модели игнорируется). Миграция: `ALTER TABLE profile_proposals ADD COLUMN op TEXT`
  (идемпотентно, рядом с остальными `ALTER`). `op IS NULL` у старых строк = значение по умолчанию для поля, поэтому
  дайджест #5 после выкатки можно подтверждать без потерь.
- Одна чистая функция склейки (в db.py, без БД — чтобы тестировать): `profile_merge(current, item) -> str`:
  - элементы — части по `;` и `,`, сравнение без регистра и лишних пробелов;
  - все элементы `item` уже есть в `current` → результат = `current` (ничего не меняется);
  - `item` содержит все элементы `current` (модель сама дала полный список) → `item`;
  - иначе `current + "; " + item`. Пустой `current` → `item`.
- **Применение (`apply_profile_ops`, approve):** `add` → `profile_merge(ТЕКУЩЕЕ значение, new_value)`. Проверку «профиль
  изменился после предложения» для `add` не делать: дополнение кладётся поверх того, что есть сейчас. Для `replace` проверка
  остаётся как была. С override из TUI — пишется override, как сейчас.
- **Переполнение:** результат длиннее `PROFILE_VALUE_MAX` (200) или профиль длиннее `PROFILE_TOTAL_MAX` → `failed`
  «поле переполнено (N знаков) — сократи в TUI», предложение остаётся `pending`. **Молча обрезать нельзя.** Сейчас
  `normalize_profile_value` режет до 200 и рвёт элемент посередине; для склеенного значения так не делать.
- **Создание предложения (`add_profile_proposals`):**
  - `add`, и все элементы уже есть в текущем значении → `same`, ничего не создаётся;
  - по полю уже висит `pending` → не терять его: новое `pending` со значением `profile_merge(pending.new_value, item)`
    (op старого, если тот `replace`, иначе `add`), старое → `superseded`. Сейчас второе предложение за неделю просто
    вытесняет первое.
  - `replace` ведёт себя как сейчас.
- **Дайджест (`format_profile_digest`) и TUI «Предложения»:** колонка «стало» показывает значение ПОСЛЕ применения
  (для `add` — склейку с текущим), у добавления пометка «＋» перед новым элементом. Админ должен видеть, что получится, а
  не кусок.
- **Промпт (`PROFILE_UPDATES_RULES`):** для многозначных полей `value` — только НОВОЕ, чего нет в профиле: оно добавится к
  имеющемуся. `"op": "replace"` с полным новым значением поля — только если человек явно отменил старое («развелась»,
  «бросил шахматы», «больше не…»), и evidence это показывает. Год рождения — только если из цитаты ясно, что речь о
  возрасте (в #5 есть предложение по голому «33»).

### 2. Ремонт уже затёртого
Отдельный скрипт не нужен: потерь три, Алексей поправит их в dedup TUI (F9 → «Профили») после выкатки. Значения — в отчёте
Клода от 2026-11-22. В чек-лист стенда добавь шаг: на копии прод-БД `/profile_ok 5` после выкатки ничего не затирает
(SELECT до и после по `user_profile` для 10 многозначных предложений #5).

### 3. Профиль в разговоре: карточка того, кто пишет
- В группе в `service_block` (хвост, последний user-turn) — новый параметр `speaker_profile`: строка
  «Сейчас пишет {имя}. Его проверенный профиль в этом чате: Имя: …; Как общаться: …. Обращайся так, как в профиле;
  пожелания из „Как общаться“ соблюдай.» Только если у автора текущего сообщения в ЭТОМ чате профиль не пустой.
- Профиль — `db.get_profile(user_id, "group", chat_id)`, лимит `PROFILE_SPEAKER_MAX_CHARS = 600` (инвариант размера).
- Где: все пути основного ответа в группе, где известен автор (текст, фото/файлы, голос/кружок, «нарисуй» через диалог). Найди
  все вызовы `service_block` grep'ом и перечисли в отчёте. **Не** в спонтанной реплике (`spontaneous=True`) и не в обзоре дня.
- В личке карточку не добавлять: там профиль один и уже в system.
- System и блок памяти НЕ трогать: карточка изменчивая, ей место только в хвосте (`docs/claude/prompt-cache.md`).
- Сам блок профилей в system остаётся как есть.

### 4. `/memory` и `/memory_full`: профиль перед фактами
- В `_send_memory`: сначала профиль (группа — `get_profile(uid, "group", chat_id)`, личка — `get_profile(uid, "private", 0)`)
  строками «Поле: значение» под заголовком «Профиль (проверен):», потом факты, как сейчас. Профиль виден без раскрытия
  свёрнутого блока.
- Фактов нет, профиль есть → показать профиль (не «Пока ничего не помню»).
- `/profile` оставить как есть.

### 5. Дайджест: решать по отдельным строкам
- `/profile_ok <N> <id> [<id>…]` и `/profile_no <N> <id> [<id>…]` — только перечисленные `id` (колонка `id` в .md).
  Без `id` — весь дайджест, как сейчас. `id` не из дайджеста N или уже решённый → в отчёте, не ошибка. Логику держи в db.py
  (`decide_digest(..., ids=None)`), правила «дайджест устарел» те же.
- Сценарий: `/profile_no 5 <id> <id>`, затем `/profile_ok 5` подтверждает остальное.
- Подпись к файлу дайджеста и `ADMIN_HELP` — упомянуть форму с `id`.

## Тесты (локально, без бота вживую)
- `profile_merge`: пусто; дубль без регистра; полный список от модели; обычное добавление; `,` и `;` вперемешку.
- `add_profile_proposals`: `add` уже есть → `same`; два `add` за неделю → одно pending со склейкой; `replace` вытесняет.
- `apply_profile_ops`: `add` поверх изменённого после предложения значения применяется склейкой; переполнение → `failed`,
  pending остаётся, ничего не обрезано; старая строка с `op=NULL` в `family` дополняет, а не заменяет.
- `decide_digest` с `ids`.
- `service_block(speaker_profile=…)` и обрезка до лимита.

## Не входит (на потом, отдельными задачами)
- Автодедуп, который видит профиль и удаляет факты, противоречащие ему (исходная цель профиля, `docs/claude/profile.md`
  → «Не входит»).
- Правило извлечения «не дублировать в facts то, что уже в профиле».
- Первичное заполнение профилей из long-фактов; правка профиля самим человеком.
